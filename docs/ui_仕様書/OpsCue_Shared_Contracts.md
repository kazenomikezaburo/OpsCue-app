## 1. 共通データ構造と責務

```text
取引先 → 案件 → 業務 → シフト
                     ├─ 募集・応募（Application）
                     ├─ 配置（Assignment）
                     ├─ 前日・当日確認
                     └─ 勤怠・確定
勤務先マスタ → 業務 → シフトの勤務先スナップショット
Worker → 勤務可能時間 / 希望条件 / スキル・資格 / 申請
ヘルプリクエスト → Worker / 関連Assignment / Admin担当
お知らせ → 公開時に固定した対象Worker集合
業務イベント → OpsCue内通知 → 任意のLINE補助配信
```

「シフト運用」は横断管理の画面でありデータ上の親ではない。応募の承認とAssignmentの確定、通知の既読と業務操作完了、希望条件と勤務可否は別の概念とする。

## 2. ロール・認可・データアクセス

| 主体 | 基本契約 | 状態 |
|---|---|---|
| Worker | 自身の応募・勤務・通知・問い合わせ・勤務条件のみ閲覧/許可された操作 | 確定（UI） |
| Manager | 管理対象の支店・案件・スタッフ等に限定 | 確定（UI） |
| System Admin | ロール名だけで全権限とみなさず、明示された権限・スコープに従う | 確定（UI） |
| サーバー処理 | 重要な状態変更をRPC等の認可された経路で実施 | 確定方針・要照合 |

- UIのボタン非表示は認可の代替にならない。RLS、RPC、サーバーで本人性・所属支店・状態・対象IDを検証する。
- 検索、件数、集計、CSV、通知ディープリンクでも権限外の存在や情報を漏らさない。
- 認証切れ、競合、権限不足、0件、取得失敗を区別する。

## 3. 募集・応募・審査・配置

### 3.1 基本フロー

```text
募集公開 → Worker応募 → Admin審査（承認/却下）
                              ↓
                        Admin配置（Assignment）
                              ↓
                   勤務予定・確認・勤怠・勤務結果
```

応募の承認は配置完了ではない。応募取下げと配置済み勤務の取消申請は別の操作。確定済み勤務の取消は正式な申請・判断経路を通す。

### 3.2 一括応募・DTO（既存のv1.0-RCとの照合が前提）

- 一括応募は**同じ案件の1〜10シフト**。全件成功または全件失敗で、部分成功はない。
- 結果は `success` / `failure` / `validation_error` / `unavailable` / `unknown` を区別する（実際のDTOの綴り・構造は要照合）。
- 結果不明 `unknown` の場合のみ照会・再送の対象とし、同じ `batchKey` を再利用する。
- 応募不可理由 `WITHDRAWN_REAPPLY_NOT_ALLOWED` と `PREVIOUS_APPLICATION_REJECTED` は別コード。
- 警告 `OVERLAPS_OWN_PENDING_APPLICATION` と `AVAILABILITY_NOT_CONFIRMED` は応募不可理由と混同しない。
- 日付判定は **Asia/Tokyoの勤務開始日**を基準とする。
- 10/31 UIデモでは `isDemo` 等で合成データを明示する。正式DTOとの差分を記録し、fixtureを二重管理しない。

### 3.3 審査RPC（PR-05）

**PM決定:** Adminの承認・却下を認可付きRPCに集約し、直接UPDATEによる状態遷移の迂回を閉じる。取消済みシフト・無効Workerの**承認は拒否**し、適法な応募の却下は可能とする。不要な直接INSERT権限も、既存RPCへの影響を隔離環境で検証したうえで閉じる。応募結果通知の追加実装はP1以降。

設計書のRPC案：

```sql
public.review_shift_application(
  p_shift_id uuid,
  p_application_id uuid,
  p_decision text,
  p_idempotency_key uuid,
  p_acknowledge_warnings boolean default false
) returns jsonb
```

- ロック取得の共通順序は原則 **シフト → Worker → 対象レコード → receipt**。具体的なロック範囲は既存RPCと照合する。
- 承認時の勤務重複は `OVERLAPS_OWN_ASSIGNMENT` / `OVERLAPS_OWN_ACCEPTED_APPLICATION` として**警告**。配置時の重複は別契約に従い**拒否**。
- 警告がある承認は**2段階確認**。最初の呼出しでは状態を変えず `confirmation_required` を返す。
- **要修正:** 添付PR-05案の「確認後に警告内容が変わっても承認する」は採用しない。再実行時に警告を再評価し、新しい/変化した警告があれば再確認する。確認対象の版・ハッシュ等の具体的な契約と冪等キーの扱いは要設計。
- 同一キー・同一要求の確定済み再送は同じ結果を返す。同一キーの別要求は競合扱い。`confirmation_required` の暫定応答を確定済みreceiptとして固定しない。
- **実装報告:** 隔離DBで修正前6/6の再現、修正後34/34 PASS、lint・型チェックOK、ローカルcommit済みとの担当者報告あり。実装済みcommit SHA・変更差分・テストログは別途確認。

## 4. 勤務可能時間・希望条件と応募/配置（P0-4）

### 4.1 Worker入力とDB判定

| DB状態 | 共通UI判定 | 意味 |
|---|---|---|
| `explicitly_available` | AVAILABLE | 対象時間を勤務可能で完全カバー |
| `consultation_required` | CONSULT | 勤務可能・相談可能で完全カバーし、相談を含む |
| `partially_available` | UNKNOWNを含む | 対象時間に未登録区間あり |
| `unknown` | UNKNOWN | 未登録 |
| `explicitly_unavailable` | UNAVAILABLE | 勤務不可と重なる |

- 登録区間は `[start,end)`。異なる状態間も重複を禁止し、隣接区間は許可する。日跨ぎは翌日終了を明示する。
- 過去・進行中の登録は閲覧のみ。確定済みAssignmentと矛盾する新規登録は警告確認後に保存可能だが、Assignmentを自動取消しない。
- 希望条件はソフト条件であり、単独の応募禁止要件ではない。

### 4.2 PM決定の判定表（既存実装への反映は11月工程）

| 勤務可否 | Worker応募 | Admin承認 | Admin配置 |
|---|---|---|---|
| AVAILABLE | 受付可 | 承認可 | 配置可 |
| CONSULT | 警告付き受付 | 明示確認後可 | 明示確認後可 |
| UNKNOWN（部分登録含む） | 警告付き受付 | 明示確認後可 | 明示確認後可 |
| UNAVAILABLE | 不可 | 不可 | 不可 |

**採用案:** W1 + R1 + A2 + K1。`AVAILABILITY_NOT_CONFIRMED` は警告。Admin配置の確認者・日時・判定時の勤務可否を、既存の `candidate_assignment_command_receipts` に記録する設計。確認フラグを受け取っただけで無条件に配置せず、RPCで最新状態・権限・競合を再検証する。

**仕様差分:** 従来の統合仕様14.2にある「UNKNOWNは配置をハードブロック」は、このPM判断に従い**明示確認が必要**へ改訂対象。既存実装は「UNAVAILABLE以外を確認なしで通す」と報告されており、現時点では新契約の実装完了とみなさない。11月の決勝向け工程で対応し、10/31のUI限定デモの前提にはしない。

## 5. Assignment・勤務・前日確認・勤怠

- Assignmentの有効性と応募状態を混同しない。勤務予定には勤務中、未来、結果未確定の勤務を含め、最終結果が確定したものを勤務履歴へ移す。
- Worker勤務詳細は「概要 → 次にやること → 集合・準備 → 前日確認 → タイムライン → 勤怠 → 連絡・サポート」。
- 前日確認の回答期限が過ぎた場合は自動欠勤扱いせず、サポート等の正式導線へ誘導する。
- 勤怠の勤務状態、訂正状態、Admin確定状態は別。Adminの個別・一括確定は権限・未処理申請・時間整合性を再検証する。
- シフトの勤務先情報は確定時のスナップショットを正とする。勤務先マスタの編集で過去/既存シフトを自動上書きしない。
- **要決定（SNAP-01）:** 業務の勤務先変更、シフト複製、日時変更、取消復旧、一括作成時のスナップショット再生成・手動上書き優先順位。

## 6. Worker申請とAdmin承認

| 対象 | Worker | Admin | 状態 |
|---|---|---|---|
| 電話番号変更 | 申請・状態確認・許可された取下げ | 審査・承認後に正式反映 | Worker確定 / Admin導線要照合 |
| スキル・資格の追加/更新 | 申請・履歴確認 | 審査・承認後に正式情報へ反映 | Worker確定 / Admin審査UI未具体化 |
| 勤務可能時間・希望条件 | 本人が登録・編集 | 原則閲覧 | 両UIで概ね一致 |
| 配置済み勤務の取消 | 正式な取消申請 | 権限・状態に応じ判断 | 既存契約と照合 |

- 申請中・未確認・期限切れのスキル/資格を正式な応募・配置資格に含めない。
- Admin側で申請一覧、承認、却下/差戻し、二重処理、反映時の監査、通知を具体化する必要がある。
- **要照合:** Adminの「System Adminによるスキル資格編集」と「Worker申請の審査」を権限・データモデルでどう両立するか。

## 7. サポート・SOS・お知らせ

- SOSと通常問い合わせはAdminヘルプリクエストへ統合。状態は **未対応 → 対応中 → 解決済み**。解決済みの再対応依頼はAdminの再開判断に従う。
- SOSは本人の有効な開始前・勤務中Assignmentに紐付ける。緊急の安全対応をアプリ内返信やLINE到達に依存させない。
- Worker/Admin間の返信とAdmin内部メモはUI・取得API・通知本文で分離する。
- お知らせは下書き → 公開中 → アーカイブ。公開時点で対象Worker集合を固定し、後から支店変更等で対象を自動追加しない。
- アーカイブ後はWorkerの直リンク閲覧も不可。お知らせ自体の個別閲覧・既読率集計はMVP対象外。
- **要照合:** 公開後の実質的変更に対する通知の自動/手動トリガーはWorkerとAdminの詳細仕様に差があるため、イベント契約として確定する。

## 8. OpsCue内通知・LINE補助通知

- OpsCue内通知は正本かつ常時有効。Workerが切り替えるのはLINEのカテゴリ別通知のみ。
- LINE通知は任意。LINE Loginの認証成功、Worker紐付け成功、公式アカウント友だち確認、送信可能性を別の状態として管理する。
- LINE連携状態：`UNLINKED` / `LINKING` / `FRIEND_REQUIRED` / `ACTIVE` / `UNAVAILABLE` / `RELINK_REQUIRED` / `UNLINKING`。
- LINE初期ON：応募結果、勤務確定・変更、前日確認、勤務リマインダー、サポート返信。初期OFF：重要なお知らせ。
- `ACTIVE` のWorker本人のみテスト通知を送信可。提案上限は60秒間隔・1日5回。テスト通知はOpsCue内通知を作成しない。
- LINEの受信・閲覧・リンクタップはOpsCue通知の既読を変更しない。OpsCue側で認可済み通知詳細を開き、既読更新が成功したときのみ既読にする。
- 業務イベントの確定とLINE送信は分離。Outbox/Queue、冪等性、再試行、送信直前の連携状態・カテゴリ再検証を行う。配信API成功は端末到達保証ではない。
- 連携解除でLINE送信を停止し、OpsCue内通知・業務履歴・カテゴリ設定は維持する。
- **要照合:** LINE公式APIの友だち状態確認、OAuth、Webhook、チャネル構成は実装時の公式仕様と既存環境で確認する。

## 9. 共通エラー・冪等性・監査

### 9.1 結果の表現

- `loading` / `empty` / `filtered_empty` / `error` / `forbidden` / `conflict` / `partial_success` 等のUI状態は区別する。ただし一括応募は**partial_successを許さない**。
- 応募、審査、配置、取消、確定、公開、通知は、サーバー側で認可・対象状態・競合・期限・重複を再確認する。
- 確定済み操作の同一キー再送は前回結果を返し、別内容へのキー流用は拒否する。通信途絶による結果不明と業務拒否を区別する。

### 9.2 監査の最低要素

`actor_id`、`action`、`target_type`、`target_id`、`occurred_at`、`request/correlation_id`、`before/after`（必要最小限）、`reason`、`outcome`、確認・警告の内容と判断結果。ログにトークン、シークレット、不要な個人情報、Admin内部メモを含めない。

### 9.3 変更・承認ゲート

- 既存のmain保護、Draft PR、隔離環境の境界を維持。
- ローカルDB・合成データ・ローカル確認ブランチでのテストと、クラウド/本番反映を区別。
- PR-02/03/05のローカル統合確認は、公開キーを `.env.local` に限定、Studioの正式なAuth経路で合成アカウントを作成、`127.0.0.1` で起動、pushしない、衝突時停止という条件付き承認。
- PR-05 migrationを適用したDBへ古い審査Actionを接続すると失敗するため、画面とDBの版を揃える。
