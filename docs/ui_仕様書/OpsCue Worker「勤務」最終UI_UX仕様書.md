### **2.2 勤務予定タブ**

対象は本人の有効なAssignmentに紐づく勤務のうち、勤務中・今後の勤務・結果未確定の勤務。

並び順は、勤務中または対応が必要な勤務を先頭、その後は開始日時の近い順とする。

各カードには勤務日、勤務時間、案件・業務名、勤務先、主要状態を表示する。

勤務開始時刻を過ぎただけでは、勤務履歴に自動移動させない。打刻漏れや未確定状態が残っている場合は、必要な対応を確認できるようにする。

### **2.3 勤務履歴タブ**

対象は勤務完了、欠勤、無断欠勤、本人取消、会社取消など、最終的な勤務結果が確定した勤務。

勤務日時の新しい順に並べる。

勤務が終了していても、勤怠のAdmin確認が未完了なら「勤務終了・勤怠確認中」のように区別する。

過去の勤務は削除せず、必要な範囲で履歴を閲覧できるようにする。

## **4\. 状態モデル**

画面上の状態を一つのDB列で無理に表現せず、複数の業務状態から導出する。

| 状態の種類 | 主な値 |
| ----- | ----- |
| Assignment | 有効・取消 |
| シフト | 予定・進行中・終了・取消 |
| 前日確認 | 受付前・受付中・確認済み・期限切れ・対象外 |
| 出発・到着 | 未報告・報告済み・対象外 |
| 勤怠 | 未開始・勤務中・終了記録済み・修正中・確定 |
| 勤務結果 | 未確定・完了・欠勤・無断欠勤・本人取消・会社取消 |
| 本人取消申請 | 未申請・申請中・承認・却下・取下げ |

「本人取消申請中」は、勤務そのものが取り消された状態ではない。

申請中もAssignmentは原則有効のままとし、勤務予定から消さない。Admin承認が成功した場合に限り、正式な取消状態へ変更する。

### **メイン状態の表示優先順位**

1. 確定済みの取消・欠勤などの最終結果  
2. 勤務中  
3. 要対応（前日確認、打刻漏れ、重要な連絡）  
4. 勤務予定  
5. 勤務終了・勤怠確認中  
6. 勤務完了

取消申請中は独立した補助バッジで表示し、メイン状態を上書きしない。

出発・到着は現場への移動状況を示すものであり、正式な勤怠時間には直接加算しない。

### **8.2 Workerの取消申請フォーム**

| 項目 | 仕様 |
| ----- | ----- |
| 対象勤務 | 自動表示・変更不可 |
| 勤務日時 | 自動表示 |
| 勤務先 | 自動表示 |
| 取消理由 | 必須 |
| 補足説明 | 任意 |
| 確認チェック | 申請だけでは取消が確定しない旨 |
| 操作 | 取消申請を送信 |

申請理由は、体調不良、私用、予定変更、その他などを想定する。理由分類はAdmin側と共通化する。

申請中は重複申請を防ぐ。申請の取下げを認める場合は、Adminがすでに処理していないかを確認し、競合時には最新状態を表示する。

### **8.3 Admin側の処理**

Adminは申請対象の勤務、理由、勤務開始までの時間、配置状況を確認する。

承認時はAssignment取消と関連状態の更新を一貫して実施し、必要な再配置対応を発生させる。

却下時はWorkerに結果と公開可能な理由を通知する。

勤務開始後や勤怠記録が存在する勤務は、通常の取消フローでは処理できない場合がある。その場合は例外処理としてAdminに誘導し、既存の勤怠や実績を消さない。

## **9\. 欠勤・無断欠勤・会社取消**

### **欠勤**

欠勤申告と欠勤確定を区別する。

Workerが欠勤を申し出た時点では、Admin側の処理が完了したとはみなさない。

確定後は「欠勤」と表示し、通常の打刻操作を停止する。

### **無断欠勤**

無断欠勤は、管理者による適切な判定が完了した場合のみ表示する。

単に勤務開始時刻を過ぎた、到着報告がない、打刻がないという理由だけで自動確定しない。

記録に相違がある場合は、対象勤務に紐付けたヘルプリクエストから問い合わせできる。

### **会社取消**

会社側で取消が確定した場合は「会社取消」と表示する。

取消日時とWorkerに公開可能な理由を確認できるようにし、通知から該当勤務詳細へ遷移できるようにする。

本人取消・会社取消・欠勤・無断欠勤の履歴は保持し、監査上必要な記録を削除しない。

## **10\. コンパクトタイムライン**

タイムラインは表示専用とし、操作ボタンを設置しない。

表示する主要イベントは、勤務確定、前日確認、出発・到着、勤務開始、勤務終了。

状態は「予定」「完了」「未記録」「対象外」「取消」などで表す。

予定時刻と実績時刻を同じイベント内に表示する場合は、必ずラベルを付ける。

履歴が多い場合は、初期表示を主要イベントに限定し、「すべての記録を見る」で展開する。

## **11\. 権限・認可**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 本人の勤務閲覧 | 可 | 権限範囲内で可 |
| 前日確認回答 | 受付中のみ | 管理権限に従う |
| 出発・到着報告 | 条件を満たす場合 | 閲覧・管理 |
| 勤務開始・終了打刻 | 条件を満たす場合 | 確認・修正 |
| 本人取消申請 | 可 | 審査 |
| 取消承認・却下 | 不可 | 権限保持者のみ |
| 勤怠確定 | 不可 | 権限保持者のみ |
| 他Workerの勤怠閲覧 | 不可 | 権限範囲内で可 |

Workerの認可は本人の有効なAssignmentと対象勤務へのアクセス権を基本とする。

ただし、取消済みや終了済みの履歴閲覧は、Assignmentが無効になっても本人に必要な範囲で許可する。

UIの非表示だけでアクセスを制限せず、RLS・RPCなどサーバー側で認可を実施する。

## **12\. 通知**

| イベント | 通知先 | 内容 |
| ----- | ----- | ----- |
| 勤務確定 | Worker | 勤務日時・勤務先 |
| 前日確認受付開始 | Worker | 回答依頼 |
| 前日確認期限切れ | Worker・必要なAdmin | 未確認の案内 |
| 本人取消申請 | 対応Admin | 申請内容・対象勤務 |
| 取消申請承認 | Worker | 取消確定 |
| 取消申請却下 | Worker | 却下結果・必要な案内 |
| 会社取消 | 対象Worker | 取消内容 |
| 重要な勤務条件変更 | 対象Worker | 変更点 |
| 勤怠修正結果 | 対象Worker | 修正・確定結果 |

通知は既存基盤と統合し、同一イベントの重複通知を防止する。

通知の既読状態と業務処理の完了状態は別管理とする。通知を開いただけで前日確認や取消申請が処理済みになることはない。

## **13\. 監査・履歴**

監査対象は、前日確認の回答、出発・到着報告、勤務開始・終了打刻、取消申請、取消承認・却下、勤怠修正、欠勤判定、会社取消など。

記録には、対象勤務、対象Worker、操作者、操作種別、操作日時、変更前後の状態、処理結果、必要に応じて理由を含める。

Workerに公開する履歴と、Admin専用の監査ログは区別する。

勤怠時刻を後から修正した場合も、元の打刻記録を消さずに変更履歴を保持する。

## **15\. エラー・競合状態**

| ケース | 処理 |
| ----- | ----- |
| データ取得失敗 | エラー表示・再試行 |
| 打刻二重送信 | サーバー側で重複防止 |
| 打刻中に勤務取消 | 最新状態を取得して操作停止 |
| 取消申請中にAdmin処理 | 最新状態を反映 |
| 取消承認と打刻が競合 | サーバー側で整合性検証 |
| 前日確認期限切れ | 回答不可・サポート誘導 |
| 権限不足 | 操作拒否・情報非公開 |
| 通信タイムアウト | 結果再取得・安全な再試行 |
| 勤怠記録と勤務結果が矛盾 | Admin確認対象として扱う |

通信失敗時に成功したように表示しない。また、同じ操作を再送した結果、二重の打刻・取消申請・通知が発生しないようにする。

## **16\. 実装順序**

| フェーズ | 作業 | 優先度 |
| ----- | ----- | ----- |
| 1 | 既存画面・DB・RPC・RLS・状態遷移の棚卸し | P0 |
| 2 | 勤務予定／勤務履歴の2タブ | P0 |
| 3 | 勤務状態と勤怠状態の表示分離 | P0 |
| 4 | 「次にやること」カード | P0 |
| 5 | 前日確認と期限切れサポート導線 | P0 |
| 6 | 勤務開始・終了の確認ダイアログ | P0 |
| 7 | 取消申請・Admin承認フロー | P0 |
| 8 | 欠勤・無断欠勤・会社取消の表示 | P0 |
| 9 | 通知・監査・競合制御の結合検証 | P0 |
| 10 | コンパクトタイムライン | P1 |
| 11 | レスポンシブ・アクセシビリティ | P1 |
| 12 | E2E・異常系テスト | P1 |

特に取消申請機能は、既存のAdmin側に対応する申請・承認機能があるか確認が必要。存在しない場合は、Worker UIだけを先行して「申請可能」と表示せず、DB・RPC・Admin UIを含む独立した実装単位として扱う。

PR-02・PR-03のDraft維持方針は変更しない。mainへのマージやクラウドDBへの適用は、別途承認が必要。

## **17\. 完了判定**

* 勤務予定・勤務履歴の2タブが正しく表示される。  
* 勤務詳細の上部に「次にやること」が表示される。  
* 前日確認の受付中・確認済み・期限切れが区別される。
