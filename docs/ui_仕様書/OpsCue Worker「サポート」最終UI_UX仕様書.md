## **3\. SOSの対象勤務**

### **3.1 対象条件**

SOSは、Worker本人がアクセスできる勤務のうち、勤務開始前または勤務中で、正式に取り消されていない勤務を対象とする。

| 勤務状態 | SOS送信 |
| ----- | ----- |
| 勤務確定・開始前 | 可能 |
| 当日・開始前 | 可能 |
| 勤務中 | 可能 |
| 勤務終了済み | 不可 |
| 本人取消確定 | 不可 |
| 会社取消確定 | 不可 |
| 欠勤確定 | 不可 |
| 無断欠勤確定 | 不可 |
| 取消申請中・未承認 | 原則可能 |

取消申請中であっても、正式に取消が確定していなければ勤務は有効なため、SOSを利用できる。

一方、勤務終了後の問題や取消済み勤務については、通常問い合わせから連絡できる。

### **3.2 対象勤務の選択**

勤務詳細からSOSを開いた場合は、対象勤務を自動設定する。

サポートトップから開いた場合は、本人の対象勤務を一覧表示し、1件選択する。

勤務カードには以下を表示する。

* 勤務日・開始終了時刻  
* 案件名・業務名  
* 勤務先  
* 勤務状態

対象勤務が0件の場合は、「SOSの対象となる勤務がありません」と表示し、通常問い合わせを案内する。

対象勤務が複数ある場合は、現在勤務中のものを先頭、その後は開始日時の近い順に並べる。

### **3.3 重要な認可条件**

SOS送信時には、選択したAssignmentが本人のものか、対象勤務が許可された状態か、勤務へのアクセス権があるかをサーバー側で再検証する。

URLの勤務IDを書き換えても、他Workerの勤務に紐付けたSOSを送信できないようにする。

## **4\. SOS作成画面**

既存のSOSモーダルにある分類を維持する。

### **4.1 入力項目**

| 項目 | 必須 | 内容 |
| ----- | ----- | ----- |
| 対象勤務 | 必須 | 自動設定または選択 |
| 困っていること | 必須 | 5分類から1つ |
| 状況 | 任意 | 最大500文字 |
| 緊急時の案内 | 表示 | 直接連絡が必要な場合の注意 |
| 送信確認 | 必須 | 送信内容の確認 |

### **4.2 SOS分類**

| 分類 | 説明 |
| ----- | ----- |
| 現場・集合場所 | 入口や集合場所が分からない |
| 配置・業務指示 | 担当場所や作業内容が分からない |
| 時間・移動 | 交通遅延や到着が難しい |
| 体調・安全 | 体調や安全について伝えたい |
| その他 | それ以外の勤務上の問題 |

状況入力は任意とする。

体調・安全の分類では、病名や詳細な医療情報の入力を要求しない。

### **4.3 SOS送信後**

送信成功時は、共通のヘルプリクエストを作成し、問い合わせ詳細へ遷移する。

初期状態は原則「未対応」、初期優先度は「高」。

画面には「SOSを受け付けました」と表示する。

ただし、受付完了は管理者が内容を確認したことを意味しない。

返信時間や対応開始時刻を保証する表示は行わない。

### **4.4 緊急時の注意**

SOSは緊急通報サービスではない。

差し迫った危険がある場合は、アプリ内の返信を待たずに、現場責任者や適切な緊急連絡先へ直接連絡するよう案内する。

連絡先が登録されている場合のみ表示し、存在しない電話番号は補完しない。

## **5\. 通常問い合わせ**

### **5.1 問い合わせ分類**

| 分類 | 対象勤務 |
| ----- | ----- |
| 勤務予定・配置 | 原則必要 |
| 前日確認 | 必要 |
| 勤怠 | 必要 |
| 勤務取消・欠勤 | 原則必要 |
| 登録情報・設定 | 不要 |
| その他 | 任意 |

対象勤務が必要な分類では、本人の閲覧可能な勤務から選択する。

終了済み・取消済みの勤務も、通常問い合わせでは選択可能とする。

### **5.2 入力項目**

| 項目 | 必須 |
| ----- | ----- |
| 問い合わせ種別 | 必須 |
| 対象勤務 | 分類に応じて必須 |
| 件名 | 必須 |
| 内容 | 必須 |
| 送信確認 | 必須 |

件名は最大120文字、内容は最大5000文字をUI上の契約案とする。実装前に既存のDB制約との一致を確認する。

### **5.3 勤務画面との連携**

以下の導線では、対象勤務と問い合わせ分類を引き継ぐ。

| 起点 | 初期分類 |
| ----- | ----- |
| 前日確認期限切れ | 前日確認 |
| 打刻漏れ | 勤怠 |
| 勤怠記録の相違 | 勤怠 |
| 取消申請の相談 | 勤務取消・欠勤 |
| 欠勤・無断欠勤への問い合わせ | 勤務取消・欠勤 |

問い合わせを送信しても、前日確認・勤怠・取消申請の業務状態は自動変更しない。

## **6\. 問い合わせ履歴**

### **6.1 表示対象**

本人が作成した通常問い合わせとSOSを同じ一覧に表示する。

### **6.2 一覧項目**

| 項目 | 内容 |
| ----- | ----- |
| 件名 | 問い合わせタイトル |
| 種別 | 通常・SOS |
| 状態 | 未対応・対応中・解決済み |
| 対象勤務 | 紐付けがある場合 |
| 作成日時 | 初回送信日時 |
| 最終更新日時 | Worker公開情報の更新日時 |
| 未読 | Adminからの未読返信 |

初期並び順は、Workerに公開された最終更新日時の新しい順とする。

Admin内部メモだけの更新で、Workerの一覧順序を変えない。

### **6.3 フィルター**

状態フィルターは「すべて」「未対応」「対応中」「解決済み」。

別途、SOSのみを表示する種別フィルターを設ける。

問い合わせ履歴から詳細へ移動し、戻った際にはフィルターとスクロール位置を復元する。

## **7\. 問い合わせ詳細**

問い合わせ詳細は通常問い合わせとSOSで共通化する。

### **7.1 表示項目**

| 領域 | 表示内容 |
| ----- | ----- |
| ヘッダー | 件名・SOSラベル・状態 |
| 基本情報 | 問い合わせ番号・作成日時・種別 |
| 対象勤務 | 勤務日・時間・勤務先・関連リンク |
| 対応状況 | 未対応・対応中・解決済み |
| メッセージ | WorkerとAdminの公開メッセージ |
| 操作 | 返信または再対応依頼 |

担当者が未割当の場合は「担当者確認中」と表示する。

Admin内部メモ、内部的な優先度変更理由、他Workerの情報は表示しない。

### **7.2 メッセージ表示**

メッセージは送信日時の古い順に表示する。

Worker送信とAdmin送信を視覚的に区別する。

送信日時、送信者区分、本文を表示する。

送信失敗時には入力内容を保持する。

## **8\. 問い合わせ状態と返信ルール**

### **8.1 状態遷移**

未対応

問い合わせ受付済み

Workerは追加返信可能

対応中

Adminが対応を開始

WorkerとAdminが返信可能

解決済み

通常返信は停止

Workerは再対応依頼を送信可能

Adminによる再オープン

理由を記録して対応中へ戻す

### **8.2 操作権限**

| 状態 | Worker返信 | Worker再対応依頼 | Admin状態変更 |
| ----- | ----- | ----- | ----- |
| 未対応 | 可 | 不要 | 可 |
| 対応中 | 可 | 不要 | 可 |
| 解決済み | 不可 | 可 | 可 |
| 再オープン後 | 可 | 不要 | 可 |

Workerからの返信は、問い合わせ状態を自動変更しない。

未対応の問い合わせに追加返信しても、状態は未対応のまま。

対応中の問い合わせに返信しても、状態は対応中のまま。

担当者の割当だけでも、状態を自動変更しない。

## **9\. 解決済みへの再対応依頼**

### **9.1 操作**

解決済みの問い合わせ詳細では、通常返信欄を非表示にし、「追加で連絡する」ボタンを表示する。

押すと再対応依頼フォームを開く。

### **9.2 入力項目**

| 項目 | 必須 | 内容 |
| ----- | ----- | ----- |
| 対象問い合わせ | 自動 | 変更不可 |
| 再連絡の内容 | 必須 | 追加対応が必要な理由 |
| 送信確認 | 必須 | 内容を確認 |

### **9.3 送信後の状態**

再対応依頼を送信しても、問い合わせ状態は「解決済み」のまま。

ただし、Workerには「再対応依頼を送信済み」と表示する。

Admin側には再対応依頼が届き、確認対象となる。

Adminが再オープンすると、状態を「対応中」に変更し、理由を監査に記録する。

### **9.4 重複防止**

未処理の再対応依頼が存在する場合、同じ問い合わせに対する重複申請を防ぐ。

Workerには「管理者の確認待ち」と表示する。

Adminが対応不要と判断した場合も、依頼の処理結果を記録し、Workerへ通知する。

再対応依頼の状態は、問い合わせ本体の3状態とは別に管理する。

## **10\. SOSと通常問い合わせの優先度**

| 種別 | 初期優先度 | 初期状態 |
| ----- | ----- | ----- |
| 通常問い合わせ | 通常 | 未対応 |
| SOS | 高 | 未対応 |

SOSであっても、送信しただけで「対応中」にはしない。

優先度はAdminが対応順を判断するための情報であり、Workerが自由に変更することはできない。

Adminが優先度を変更する場合は、変更理由や変更履歴を監査に残す。

### **Admin側の表示**

SOSは通常問い合わせと同じ一覧に表示し、SOSラベルと優先度で強調する。

Adminは種別・優先度・状態で絞り込めるようにする。

ただし、高優先度だからといって、対応開始・担当者割当・解決を自動実行しない。

## **11\. 通知仕様**

| イベント | 通知先 | 通知内容 |
| ----- | ----- | ----- |
| 通常問い合わせ作成 | 対応可能なAdmin | 新規問い合わせ |
| SOS作成 | 対応可能なAdmin | 高優先度SOS |
| Worker追加返信 | 担当Adminまたは対応可能なAdmin | 新しいメッセージ |
| Admin公開返信 | Worker | 管理者からの返信 |
| 対応開始 | Worker | 対応中への変更 |
| 解決 | Worker | 解決済みへの変更 |
| Worker再対応依頼 | 対応可能なAdmin | 再対応依頼 |
| Admin再オープン | Worker | 対応再開 |
| 再対応依頼の対応不要判断 | Worker | 依頼の処理結果 |

### **通知の原則**

* 通知と業務状態は別管理。  
* 通知の既読は問い合わせの解決を意味しない。  
* 同一イベントの重複通知を防止する。  
* 通知失敗によって問い合わせ本体を消さない。  
* 通知から対象問い合わせ詳細へ直接遷移する。  
* Admin内部メモの内容をWorker通知へ含めない。

SOSは通常問い合わせより目立つ通知にするが、通知が届いたこととAdminが対応を開始したことは区別する。

## **12\. 権限・セキュリティ**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 通常問い合わせ作成 | 可 | 管理権限に従う |
| SOS作成 | 対象勤務がある場合 | 管理・確認 |
| 本人問い合わせ閲覧 | 可 | 管理範囲内 |
| 他Worker問い合わせ閲覧 | 不可 | 管理範囲内 |
| 未対応・対応中への返信 | 可 | 可 |
| 解決済みへの通常返信 | 不可 | 状態管理に従う |
| 再対応依頼 | 可 | 受付・判断 |
| 再オープン | 不可 | 権限保持者のみ |
| 担当者変更 | 不可 | 権限保持者のみ |
| 優先度変更 | 不可 | 権限保持者のみ |
| 内部メモ閲覧 | 不可 | 権限保持者のみ |

### **セキュリティ要件**

認証・認可はUIだけでなく、RLS・RPCなどサーバー側で実施する。

Workerが閲覧できるのは本人の問い合わせと、その問い合わせに含まれる公開情報のみ。

勤務に紐付いた問い合わせでは、対象Assignmentへのアクセス権も検証する。

Adminの権限は既存の拠点・担当範囲に従う。

問い合わせの公開メッセージと内部メモは、保存・取得・通知の各段階で公開範囲を分離する。

## **13\. 監査・履歴**

監査対象は次の操作とする。

| 操作 | 記録する内容 |
| ----- | ----- |
| 問い合わせ作成 | 種別・対象・操作者・日時 |
| SOS作成 | SOS分類・対象勤務・日時 |
| 返信 | 送信者・日時・対象問い合わせ |
| 担当者割当・変更 | 変更前後・操作者 |
| 優先度変更 | 変更前後・理由 |
| 状態変更 | 変更前後・操作者 |
| 解決 | 解決日時・操作者 |
| 再対応依頼 | 依頼者・日時・内容 |
| 再オープン | 理由・操作者・日時 |
| 再対応不要判断 | 判断者・日時・結果 |

問い合わせのメッセージ履歴と監査ログは区別する。

Workerには公開メッセージと必要な状態変更履歴のみ表示し、内部監査情報は公開しない。

メッセージ本文などの機微情報は、汎用監査ログに無制限に複製しない。

## **15\. エラー・競合状態**

| ケース | UI・処理 |
| ----- | ----- |
| 問い合わせ履歴なし | 空状態を表示 |
| SOS対象勤務なし | 通常問い合わせを案内 |
| 必須項目未入力 | 項目別エラー |
| 送信中 | ボタン無効化 |
| 送信失敗 | 入力内容保持・再試行 |
| 送信結果不明 | サーバー状態を再取得 |
| SOS対象勤務が取消済みに変更 | SOS送信を停止 |
| 返信中に解決済みへ変更 | 最新状態を取得し、通常返信を停止 |
| 再対応依頼中にAdmin再オープン | 最新状態を表示 |
| 重複再対応依頼 | 既存の依頼状態を表示 |
| 権限不足 | 操作拒否・情報非公開 |
| 通知送信失敗 | 問い合わせ保存とは分離 |
| データ取得失敗 | エラー表示・再試行 |

特に、返信送信とAdminの解決処理が競合した場合は、サーバー側で状態を検証する。

UI上で返信可能に見えていても、送信時点で解決済みになっていれば通常返信を拒否し、最新の状態を表示する。
