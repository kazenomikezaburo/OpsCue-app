# **3\. LINE認証・友だち追加フロー**

1. OpsCueで本人認証  
   ログイン済みWorkerのセッションを確認する。  
2. LINE連携を開始  
   サーバー側で一時的な連携要求を作成し、LINE認証へ遷移する。  
3. LINEで認証・同意  
   LINE Loginを利用して本人のLINEアカウントを認証する。  
4. 認証結果を検証  
   コールバックで認証コード、`state`、`nonce`など必要な値を検証する。  
5. LINEアカウントを紐付け  
   検証済みLINEユーザーIDとOpsCue Workerを安全に紐付ける。  
6. 公式アカウントの友だち状態を確認  
   友だち追加済みで、通知送信の前提条件を満たしているか確認する。  
7. LINE通知を有効化  
   認証・紐付け・友だち状態の条件を満たした場合のみ通知利用可能にする。

### **3.1 重要な区別**

次の3つは別々の状態として管理する。

| 状態 | 意味 |
| ----- | ----- |
| 認証成功 | LINEアカウント本人の認証が成功 |
| 紐付け成功 | OpsCue Workerとの対応が確定 |
| 通知利用可能 | 友だち状態などの送信条件を満たす |

LINE認証成功だけで通知利用可能と表示しない。

友だち追加待ちの場合は紐付けを保持できるが、LINE通知は送信しない。

LINE側の友だち状態を確認できない場合も、通知利用可能と推定しない。

なお、友だち追加済みであっても、ネットワーク障害やLINE側の制限により、個々のメッセージの到達まで保証できるわけではない。

# **4\. 連携状態の最終仕様**

| 内部状態 | Worker表示 | LINE送信 |
| ----- | ----- | ----- |
| `UNLINKED` | 未連携 | 不可 |
| `LINKING` | 連携処理中 | 不可 |
| `FRIEND_REQUIRED` | 友だち追加が必要 | 不可 |
| `ACTIVE` | LINE通知を利用できます | 可 |
| `UNAVAILABLE` | LINE通知を受信できません | 不可 |
| `RELINK_REQUIRED` | 再連携が必要 | 不可 |
| `UNLINKING` | 解除処理中 | 不可 |

連携失敗は別途エラー理由として保持する。

一時的な配信エラーが発生しただけで、即座に`UNAVAILABLE`や`RELINK_REQUIRED`へ遷移させない。

### **状態遷移**

UNLINKED  
   │ 連携開始  
   ▼  
LINKING  
   │  
   ├─ 認証失敗 ───────→ UNLINKED  
   │  
   ├─ 認証・紐付け成功  
   ▼  
FRIEND\_REQUIRED  
   │  
   ├─ 友だち追加確認 → ACTIVE  
   └─ 連携解除 ─────→ UNLINKED

ACTIVE  
   ├─ 受信不可を確認 → UNAVAILABLE  
   ├─ 再認証が必要 → RELINK\_REQUIRED  
   └─ 解除 → UNLINKING → UNLINKED

`UNAVAILABLE`から友だち状態などが再確認できれば`ACTIVE`へ戻せる。

`RELINK_REQUIRED`では認証を再実行する。

# **5\. LINE通知設定**

## **5.1 基本方針**

OpsCue内通知は常時有効。

Workerが変更できるのは、LINE通知のカテゴリ別ON/OFFのみ。

### **初期設定**

「重要カテゴリのみON」は次のように具体化する。

| カテゴリ | 初期設定 | 理由 |
| ----- | ----- | ----- |
| 応募結果 | ON | 応募結果の見落とし防止 |
| 勤務確定・変更 | ON | 勤務に直接影響 |
| 前日確認 | ON | 確認期限の見落とし防止 |
| 勤務リマインダー | ON | 勤務忘れ防止 |
| サポート返信 | ON | 現場の問題対応 |
| 重要なお知らせ | OFF | 任意で受信を選択 |

重要なお知らせを初期OFFとするのは、業務連絡を優先し、LINE通知の過剰配信を避けるため。

ただし、OpsCue内のお知らせ・通知は従来どおり利用できる。

### **設定の保存ルール**

* LINE未連携でも設定値は保持できる。  
* LINE通知をOFFにしてもOpsCue内通知は生成する。  
* LINE連携解除後も設定値は保持する。  
* 再連携時は保存済み設定を復元する。  
* 新しい通知カテゴリが追加された場合は、既定値を明示して管理する。  
* 保存失敗時は変更前の状態へ戻すか、再試行を案内する。  
* 同時更新があれば最新設定を再取得する。

重要カテゴリであっても、WorkerがLINE通知をOFFにすることは可能。

# **6\. LINE通知の対象イベント**

LINE通知はOpsCue内通知に紐付けて生成する。

| 業務イベント | LINEカテゴリ |
| ----- | ----- |
| 応募承認・不承認 | 応募結果 |
| 勤務確定・重要変更 | 勤務確定・変更 |
| 勤務取消申請の承認・却下 | 勤務確定・変更 |
| 前日確認依頼 | 前日確認 |
| 勤務開始前リマインダー | 勤務リマインダー |
| サポート返信・重要な状態変更 | サポート返信 |
| お知らせ公開・重要更新 | 重要なお知らせ |

SOSに関係するサポート返信は優先度の高いイベントとして扱うが、LINEの即時到達を保証しない。

SOSの安全確保や緊急対応をLINE通知の到達だけに依存させない。

お知らせの軽微な編集では通知を生成しない。

同じ業務結果から重複した通知が作成されないよう、イベントIDで冪等性を担保する。

# **7\. LINEメッセージの内容**

LINEには必要最小限の情報だけを送信する。

OpsCue

勤務が確定しました

新しい勤務が確定しました。日時や集合場所などの詳細をOpsCueで確認してください。

OpsCueで確認する →

通知メッセージの構成例。実際のLINE画面ではありません。

### **メッセージのルール**

* タイトルは簡潔にする。  
* 個人情報や詳細な相談内容を含めない。  
* Admin内部メモを含めない。  
* 業務操作をLINE上で完了させない。  
* 詳細確認はOpsCueへのリンクを使用する。  
* リンク先では必ず認証・権限を再確認する。

通知に付けるリンクは、通知IDを基点にOpsCueへ遷移する方式を推奨する。

対象業務データへのアクセス権限が失われている場合は、適切な非公開・閲覧不可画面を表示する。

# **8\. LINE既読とOpsCue既読**

既読状態は完全に独立させる。

| 操作 | OpsCue通知の状態 |
| ----- | ----- |
| LINE通知を受信 | 変更なし |
| LINE通知を読む | 変更なし |
| LINE内のリンクを押す | 変更なし |
| OpsCueで通知を開く | 既読 |
| OpsCueで「すべて既読」 | 対象通知を既読 |

LINEのリンクを押しただけでは、OpsCue通知を既読にしない。

ログイン後に通知詳細を開き、通知の所有権確認と既読保存が成功した時点で既読とする。

また、通知が既読になっても、前日確認・打刻・取消申請・問い合わせ返信などの業務操作は完了しない。

# **9\. テスト通知**

## **9.1 利用条件**

連携状態が`ACTIVE`の場合のみ送信可能。

テスト通知はWorker本人がLINE通知を受信できるか確認するための機能。

### **UI**

テスト通知

LINEにテストメッセージを送信して、通知を受け取れるか確認できます。

テスト通知の内容

OpsCueのLINE通知テストです。メッセージが届いていれば、通知を受け取れる状態です。

テスト通知を送信するテスト通知のUI例。ボタンは仕様確認用で、実際のLINE送信は行いません。

### **9.2 送信制限**

乱用や不要な送信コストを防ぐため、次の制限を採用する。

| 項目 | 仕様 |
| ----- | ----- |
| 送信可能状態 | ACTIVEのみ |
| 連続送信 | 60秒以上の間隔 |
| 1日の上限 | 5回 |
| 送信先 | 連携中の本人LINEのみ |
| メッセージ内容 | 固定文 |
| OpsCue内通知 | 作成しない |
| 監査 | 送信要求・結果を記録 |

上限はサーバー側で強制する。

送信APIが成功しても、端末への実際の到達を保証しない。

### **9.3 テスト通知の結果**

| 結果 | Worker表示 |
| ----- | ----- |
| 送信要求受付 | テスト通知を送信しました |
| 一時的な失敗 | 送信できませんでした。時間をおいて再試行してください |
| 友だち状態に問題 | LINE公式アカウントの状態を確認してください |
| 上限超過 | 本日の送信上限に達しました |
| 未連携 | LINE連携が必要です |

UI上の「送信しました」は、送信処理が受け付けられたことを意味し、LINE端末への到達確認ではない。

# **10\. 配信失敗・再試行**

LINE配信はOpsCueの業務処理から分離する。

業務イベント  
    │  
    ▼  
OpsCue内通知作成  
    │  
    ▼  
LINE配信対象？  
    │  
    ├─ NO → 終了  
    ▼ YES  
LINE連携ACTIVE？  
    │  
    ├─ NO → 送信なし  
    ▼ YES  
カテゴリ設定ON？  
    │  
    ├─ NO → 送信なし  
    ▼ YES  
配信ジョブ作成  
    │  
    ▼  
送信直前に状態を再確認  
    │  
    ▼  
Messaging API送信  
    │  
    ├─ 成功 → 結果記録  
    └─ 失敗  
         ├─ 一時的 → 再試行  
         └─ 恒久的 → 停止・状態更新

### **配信ルール**

* 業務イベントとOpsCue内通知の作成を先に確定する。  
* LINE配信は非同期で実行する。  
* LINE送信失敗で勤務確定や問い合わせ返信をロールバックしない。  
* イベントIDと配信先で重複ジョブを防ぐ。  
* 送信直前に連携状態とカテゴリ設定を再確認する。  
* 解除済み・受信不可のアカウントには送信しない。  
* 一時的な失敗のみ、回数制限付きで再試行する。  
* 再試行が重複配信を生まないように設計する。

配信結果は、APIへの送信要求の成功・失敗と、実際の端末到達を区別する。

# **11\. LINE連携解除**

連携解除はWorker本人が実行できる。

解除前に確認ダイアログを表示する。

| 項目 | 解除後 |
| ----- | ----- |
| LINE通知 | 停止 |
| OpsCue内通知 | 継続 |
| 勤務予定・履歴 | 維持 |
| サポート履歴 | 維持 |
| 通知設定 | 保持 |
| LINE紐付け | 無効化 |
| 再連携 | 可能 |

解除処理はサーバー側で実行し、紐付け情報を無効化する。

送信待ちのLINE通知も、送信直前の再検証で停止する。

解除が失敗した場合は、実際の連携状態を再取得し、解除済みと誤表示しない。

# **12\. セキュリティ・権限**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 本人の連携状態閲覧 | 可 | 必要最小限 |
| LINE連携 | 本人のみ | 不可 |
| LINE解除 | 本人のみ | 原則不可 |
| LINE通知設定変更 | 本人のみ | 原則不可 |
| 他WorkerのLINE情報閲覧 | 不可 | 原則不可 |
| LINE通知送信 | 不可 | サーバー処理のみ |
| LINE認証情報取得 | 不可 | 不可 |
| テスト通知 | 本人のみ | 不可 |

### **必須の安全対策**

* OAuthの`state`と連携要求を紐付けて検証する。  
* IDトークンの署名、発行者、対象クライアント、期限、`nonce`を検証する。  
* 利用可能な認証方式に応じてPKCE等を採用する。  
* LINEユーザーIDをクライアント申告値だけで信用しない。  
* 同じLINEアカウントを複数Workerに同時紐付けしない。  
* チャネルシークレット・アクセストークンをブラウザへ公開しない。  
* Webhookを使用する場合は署名を検証する。  
* 認証コードやトークンをログに残さない。  
* 連携・解除・設定変更・テスト通知にレート制限を設ける。  
* 連携解除後に古い認証要求が再利用されないようにする。

LINE連携のアカウント紐付けと通知配信は、信頼されたサーバー処理で実施する。
