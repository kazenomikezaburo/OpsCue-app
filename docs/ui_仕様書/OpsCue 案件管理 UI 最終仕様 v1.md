# **OpsCue 案件管理 UI 最終仕様 v1.0**

今回の決定を反映して、案件一覧・案件詳細・案件作成・案件編集の4画面と、業務管理用の右ドロワーを確定しよう。

これまでのOpsCue管理画面と統一しつつ、案件管理とシフト運用の役割を明確に分ける設計にする。

今回確定した仕様

確定

案件 → 業務 → シフトの階層構造

業務の追加・編集は右ドロワー

勤務先は既存選択＋新規登録

業務未登録でも案件の下書き保存が可能

## **6\. 業務追加・編集ドロワー**

案件詳細・案件作成・案件編集で共通利用するコンポーネント。

| 項目 | 必須 | UI |
| ----- | ----- | ----- |
| 業務名 | ○ | テキスト入力 |
| 勤務先 | ○ | 検索可能なセレクト |
| 新しい勤務先 | 任意 | 新規登録ダイアログ |
| 仕事内容 | 任意 | 複数行テキスト |
| 注意事項 | 任意 | 複数行テキスト |
| 状態 | 編集時 | 有効・無効 |

ドロワーの構成は、上部にタイトルと閉じるボタン、中央にスクロール可能なフォーム、下部に固定の「キャンセル」「保存」ボタン。

勤務先を新規登録した場合は、登録完了後にその勤務先を自動選択する。登録途中でキャンセルした場合は、業務フォームの入力内容を保持する。

案件作成中に業務を追加する場合は、業務情報を一時保存し、案件の最終保存時にまとめて登録する。途中で案件作成をキャンセルした場合は、勤務先だけが意図せず残らないようにする必要がある。

## **7\. 画面遷移の最終仕様**

実際のルートは次の構成を推奨する。

| 画面 | URL |
| ----- | ----- |
| 案件一覧 | `/admin/projects` |
| 案件作成 | `/admin/projects/new` |
| 案件詳細 | `/admin/projects/[projectId]` |
| 案件編集 | `/admin/projects/[projectId]/edit` |
| 業務ドロワー | 案件画面内の状態として表示 |
| シフト作成 | `/admin/shifts/new?projectId=...` |
| シフト詳細 | `/admin/shifts/[shiftId]` |

業務ドロワーは独立したページにしない。案件の文脈を保持したまま編集できるようにする。

シフト作成時は案件を引き継ぎ、業務を選択すると勤務先が自動的に反映される。

## **8\. 実装時のルール**

特に以下の条件は、UIだけでなくバックエンド側でも守る。

* 案件名と取引先があれば、業務0件でも下書き保存可能。  
* 案件を進行中にするには、業務が1件以上必要。  
* シフト作成には有効な業務が必要。  
* 案件・業務・勤務先の関連付けはIDで管理する。  
* 業務に既存シフトがある場合、勤務先変更時に影響確認を行う。  
* 応募・配置などがある業務は、原則物理削除しない。  
* 変更履歴には実行者・日時・変更内容を記録する。  
* 保存中の二重送信、未保存変更の離脱、権限不足、通信エラーに対応する。

## **9\. 実装優先順位**

10月31日の発表に向けたUIデモを優先するなら、実装はこの順番がよい。

| 優先度 | 対象 | 内容 |
| ----- | ----- | ----- |
| P0 | 案件一覧 | 表示・検索・詳細遷移 |
| P0 | 案件詳細 | 概要・業務一覧・シフト一覧 |
| P0 | 案件作成 | 基本情報・下書き保存 |
| P0 | 業務ドロワー | 業務追加・編集・勤務先選択 |
| P0 | 案件編集 | 既存情報の編集 |
| P1 | 勤務先新規登録 | 業務編集から登録 |
| P1 | シフト連携 | 案件・業務を引き継いだシフト作成 |
| P2 | 履歴・影響確認 | 変更履歴・既存シフトへの影響管理 |

発表用デモでは、案件を作成し、業務と勤務先を登録し、シフト作成へ進む一連の操作が見せられることを優先する。バックエンドが未完成でも、モックデータによる操作デモとして成立させられる。
