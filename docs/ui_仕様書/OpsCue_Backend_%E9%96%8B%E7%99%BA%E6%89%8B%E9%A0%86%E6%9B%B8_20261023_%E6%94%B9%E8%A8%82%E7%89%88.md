## 3. P0-1 / PR-02：Managerの支店権限

**目的:** `private.has_branch_access`等の認可が、無効Managerや支店権限外アクセスを許さないこと。

- Managerの`is_active`、ロール、支店所属・権限を**サーバー側**で検証する。
- SELECTだけでなく、直接DML、RPC、一覧件数、詳細、通知/CSVでも権限外の存在を漏らさない。
- System Adminはロール名だけで無条件に全件許可せず、既存の明示権限契約に従う。
- 有効Manager、自支店・他支店、無効Manager、Worker、anonで回帰確認する。
- 権限変更後のセッション再取得・再ログインによる見え方を確認する。

**完了条件:** 認可修正とそのテストが一致し、PR-03/05から同じhelperを安全に利用できる。mainマージ済み・クラウド適用済みと推定しない。

## 4. P0-2 / PR-03：配置RPCの統一

**目的:** シフト詳細の配置ボタンが安全な配置RPCを使い、旧経路での条件迂回を防ぐ。

- 旧`create_assignment_from_application`と新`ensure_candidate_assignment`の呼び出し元・EXECUTE権限を棚卸しする。
- Workerの有効性、Manager支店権限、応募/シフト状態、資格、定員、勤務可否、他の有効Assignmentとの時間重複をDBで再検証する。
- lockは他writerと原則**シフト → Worker → 対象レコード → receipt**の順序で揃える。複数シフト時は安定したID順を検討する。
- 時間重複は配置時に**拒否**する。審査時の警告と混同しない。
- 旧RPCのEXECUTE閉鎖と新UI切替を同じ互換性検証の対象とする。PR-03の選択肢・実際の実装差分は担当者の最新版で確認する。

**注意:** PR-05 migration適用後の隔離DBに、旧審査ActionのままのPR-03画面を接続すると審査操作が失敗する。画面検証は3PR統合のローカル確認ブランチを使う。

## 5. P0-3 / PR-05：応募審査RPC化

### 5.1 PM決定

| 論点 | 決定 |
|---|---|
| 承認時の時間重複 | 2段階警告確認。確認前は更新しない |
| 取消済みシフト・無効Worker | 承認を拒否。正当な応募の却下は可能 |
| `shift_applications`直接UPDATE | 不要なUPDATEポリシーと権限を閉じる |
| 不要な直接INSERT権限 | 既存応募RPCへの影響を隔離検証してrevoke |
| 応募結果通知 | P1以降に延期。Worker UIで実通知を装わない |
| 警告の再評価 | 確認後の再呼び出しでも最新警告を評価し、変化した場合は再確認 |

### 5.2 RPC設計（候補、実DBシグネチャは要照合）

```sql
public.review_shift_application(
  p_shift_id uuid,
  p_application_id uuid,
  p_decision text, -- accepted / rejected
  p_idempotency_key uuid,
  p_acknowledge_warnings boolean default false
) returns jsonb
```

- 呼び出しは認証済み主体に限定し、内部でAdmin有効性・支店権限を再検証する。
- 同じシフトの配置済み、応募の現在状態、シフト取消、Worker無効等を判定する。
- `OVERLAPS_OWN_ASSIGNMENT`、`OVERLAPS_OWN_ACCEPTED_APPLICATION`を承認時警告として扱う。重複区間は`[start,end)`、隣接は重複しない。
- `confirmation_required`は状態変更なし。確認後も**最新警告を再評価**する。旧設計の「警告が変わっていても承認」は採用しない。
- **要設計:** 警告の版・ハッシュ・確認対象の紐付け、同一`p_idempotency_key`での2段階確認と異要求判定を矛盾なく成立させる方法。確認フラグだけで新警告を無条件承認しない。
- 確定した同一キー・同一要求は保存済み結果を再返却。異要求は競合。`confirmation_required`を確定receiptとして固定しない。
- 審査Actionの直接UPDATEを廃止し、RPCへ切り替える。migrationと画面を同じ互換性単位で検証する。
- `security definer`、固定`search_path`、権限grant/revoke、内部の認可と監査をレビューする。

### 5.3 検証証拠

担当者報告：修正前6/6の不正遷移再現、修正後34/34 PASS、lint・型チェックOK、ローカルcommit済み。**旧設計書は実装前の記述のため、最終SHA・差分・テストログ・新しい警告再確認仕様の検証結果を提出してもらう。** 既存34件PASSを、新しいPM追加条件までPASS済みとみなさない。

## 7. P0-5：案件単位の一括応募とFrontend DTO照合

### 7.1 共通契約

- 案件識別子は`projects.id`。案件名でまとめない。
- **同一案件の一意な1〜10シフト**を原子的に応募する。1件でも拒否なら**新規応募0件**。旧単一応募RPCの逐次呼出しで代用しない。
- 日付は**Asia/Tokyoでの勤務開始日**。時刻はオフセット付きISO 8601を使う。
- 応募受付は採用・配置確定と別。未確定応募との時間重複は`OVERLAPS_OWN_PENDING_APPLICATION`警告であり、原則選択不可にはしない。
- `WITHDRAWN_REAPPLY_NOT_ALLOWED`と`PREVIOUS_APPLICATION_REJECTED`は別コード。`AVAILABILITY_NOT_CONFIRMED`は警告。
- `null`報酬は不明/未設定であり0円ではない。空配列は該当なし、件数0は実数0。
- `unknown`は通信結果不明。照会・再送時は同じ`batchKey`を維持し、`not_found`を失敗確定とみなさない。

### 7.2 型の暫定例

```ts
type BatchRequest = {
  contractVersion: 1;
  projectId: string;
  shiftIds: string[]; // 同一案件、重複なし、1〜10件
  batchKey: string; // UUID
};

type BatchActionResult =
  | { kind: 'resolved'; replayed: boolean; result: StoredBatchResult }
  | { kind: 'validation_error'; code: string }
  | { kind: 'unavailable' }
  | { kind: 'idempotency_conflict' }
  | { kind: 'unknown'; batchKey: string };
```

**要照合:** Backend会話上の`success/failure/validation_error/unavailable/unknown`と、上記`resolved`内の`accepted/rejected`は異なる階層を指す可能性がある。フィールド名・列挙値・入れ子を正式なDTOとして突き合わせる。

**原則:** UI仕様で導線が存在しても、DB/RPCやAdmin審査機能が存在するとは限らない。未実装を「完了」と表示しない。

## 11. PR・migration・公開の判断ゲート

| Gate | 必要な証拠 | 未達時 |
|---|---|---|
| 設計合意 | API/DTO、状態遷移、警告/拒否、権限、冪等性、ロック順の差分解消 | 設計を修正 |
| ローカル実装 | 変更ファイル、branch/HEAD、影響範囲、他作業との衝突確認 | 作業停止・調整 |
| 隔離DB検証 | migration、適用前後の権限、合成データ、正常/異常/並行/回帰結果 | 不具合修正、再テスト |
| UI統合検証 | 画面とDBの版一致、ブラウザ証拠、失敗時の文言 | 接続見送り |
| push/Draft PR | 対象branch、差分、秘密情報混入なし、テスト、レビュー計画 | 別途PM承認待ち |
| mainマージ | レビュー、必須CI、保護ルール、依存PR順序、rollback | マージしない |
| クラウド/公開 | 接続先、migration適用計画、バックアップ、認可、監視、費用、PM Go/No-Go | UI限定デモを維持 |

- **PRの番号と依存関係:** PR-02/03/05という作業呼称と、GitHub上の実際のPR番号・状態は別途確認する。
- **migrationは原則forward-onlyで設計。** 既存権限を一時的に緩める安易なrollbackを前提にしない。復旧計画はデータ影響と互換性をレビューする。
- **セキュリティ:** `service_role`のクライアント露出、RLS無効化、直接DMLへの逃避、秘密情報のログ記録は禁止。

## 12. 受入テストマトリクス

| 領域 | 最低限のケース |
|---|---|
| 認可 | anon、Worker、無効Manager、他支店Manager、有効Manager、System Admin権限 |
| 審査 | 承認、却下、既決、取消済みシフト、無効Worker、同一キー再送、別要求競合 |
| 警告 | Assignment重複、承認済み応募重複、警告の追加・変更、隣接時間帯 |
| 配置 | 有効応募、定員、資格、勤務可否、重複、同時操作、旧RPC EXECUTE拒否 |
| 一括応募 | 0/1/10/11件、重複ID、別案件、既応募、取下げ後、却下後、全体rollback |
| receipt | 同一キー同一要求、異要求、通信断、`not_found`、同時再送、結果の整合 |
| 勤務可否 | AVAILABLE、CONSULT、UNKNOWN、部分登録、UNAVAILABLE、状態変化後の再確認 |
| データ境界 | 件数/検索/CSV/通知/ディープリンクの他人・他支店非漏洩 |
| 回帰 | 単一応募、取下げ、既存勤務予定、Admin審査、配置、勤怠 |
| 運用 | migration再適用、lock/deadlock、タイムアウト、LINE/cron停止 |

**報告は「実施済みPASS」「実施済みFAIL」「未実施」「環境要因で未判定」を区別する。** テスト設計を書いただけで合格扱いにしない。

## 14. 停止条件・禁止事項

- 予定外のDB接続先、秘密情報、既存データ、想定外の権限・migration差分を検知した。
- 作業branchや未コミット変更が事前報告と異なる。マージ衝突が生じた。
- 認可を弱めないとテストが通らない、旧RPCの権限が残る、データ不整合が見つかった。
- 同時処理で二重登録・部分成功・不正遷移・デッドロックが再現した。
- 予定外のファイル変更、依存追加、ネットワーク送信、クラウドリソース操作が必要になった。

**対応:** 現状保全 → 操作停止 → 差分・再現条件・影響を報告 → PMの追加判断。`git reset --hard`、強制push、勝手なDB reset、RLS緩和、旧環境への接続で解決しない。
