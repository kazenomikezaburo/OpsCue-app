# 第I部：全体統合仕様（実装・レビュー用）

## 1. プロダクトと業務データの関係

```text
取引先 → 案件 → 業務 → シフト
                       ├─ 募集 → 応募(Application) → Admin審査
                       ├─ 配置(Assignment) → 前日・当日確認
                       └─ 勤怠 → 訂正・確定 → 勤務履歴
勤務先マスタ → 業務 → シフトの勤務先スナップショット
Worker → 勤務可能時間・希望条件・スキル資格・変更申請
Worker SOS/問い合わせ → Adminヘルプリクエスト
Adminお知らせ → 公開時点の対象Worker
業務イベント → OpsCue内通知（正本）→ LINE補助配信（任意）
```

「シフト運用」は横断ワークスペースでありデータの親ではない。**応募承認≠配置確定、通知既読≠業務完了、勤務希望≠勤務可否、LINE送信受付≠端末到達**をすべての画面で守る。

## 4. 主要な画面遷移と状態

### 4.1 応募から勤務まで

```text
Worker募集一覧 → 募集詳細 → 応募確認 → 応募結果
                                      ↓
Adminシフト詳細・応募タブ → 審査（承認／却下）→ 配置（Assignment）
                                      ↓
Worker勤務予定 → 勤務詳細 → 前日確認 → 当日勤怠 → 結果確定 → 勤務履歴
```

応募取下げは未配置の応募に対する操作。配置済み勤務の取消は別の正式申請・審査経路。承認・配置・確定はサーバーで毎回権限・状態・競合を再検証する。

### 4.2 勤務可否と応募・審査・配置（PM決定、実装未照合）

| DB判定 | UI概念 | 応募 | Admin承認 | Admin配置 |
|---|---|---|---|---|
| `explicitly_available` | AVAILABLE | 可 | 可 | 可 |
| `consultation_required` | CONSULT | 警告付き可 | 明示確認後可 | 明示確認後可 |
| `partially_available` | UNKNOWNを含む | 警告付き可 | 明示確認後可 | 明示確認後可 |
| `unknown` | UNKNOWN | 警告付き可 | 明示確認後可 | 明示確認後可 |
| `explicitly_unavailable` | UNAVAILABLE | 不可 | 不可 | 不可 |

採用は**W1＋R1＋A2＋K1**。`AVAILABILITY_NOT_CONFIRMED` は警告。配置の確認者・日時・当時の判定を既存receiptに記録する設計。過去の統合仕様14.2の「UNKNOWNは配置禁止」は改訂対象。11月向けであり、10/31のUI限定デモには実装済みと表示しない。

### 4.3 PR-05審査RPC（PM決定、実装報告の独立検証前）

- 審査は直接UPDATEではなく`review_shift_application` RPCに集約。ロック順は原則シフト→Worker→対象レコード→receipt。
- 取消済みシフト・無効Workerへの承認は拒否。却下は既存の許可状態に従う。
- 承認時の重複は警告、配置時の時間重複は拒否。警告は2段階確認。
- **警告内容が確認後に変化したら再確認**する。警告セット版/ハッシュと同じ冪等キーの具体的設計は未確定。
- 不要な直接INSERT/UPDATE権限を閉じる前に既存RPCの回帰を隔離DBで確認する。
- 担当者報告の修正前6/6、修正後34/34 PASSは独立検証済みの証明として扱わない。

### 4.4 一括応募のUI契約（既存API/DTO v1.0-RCとの照合前）

同一案件の**1〜10シフト**を1バッチとし、**全件成功または全件失敗**。`success` / `failure` / `validation_error` / `unavailable` / `unknown` を区別し、`unknown`のときだけ同じ`batchKey`で照会・再送する。`WITHDRAWN_REAPPLY_NOT_ALLOWED`と`PREVIOUS_APPLICATION_REJECTED`は別理由、`OVERLAPS_OWN_PENDING_APPLICATION`と`AVAILABILITY_NOT_CONFIRMED`は警告。日付はAsia/Tokyoの勤務開始日を基準とする。

### 4.5 サポート・お知らせ・LINE

- サポート：未対応→対応中→解決済み。Workerの再対応依頼はAdminの再開判断へ。SOSは有効な勤務に紐付け、緊急安全対応をLINEやアプリ内返信に依存しない。
- お知らせ：下書き→公開中→アーカイブ。公開時の対象Worker集合を固定。アーカイブ後はWorker直リンクも不可。個別のお知らせ既読率はMVP対象外。
- LINE：`UNLINKED` / `LINKING` / `FRIEND_REQUIRED` / `ACTIVE` / `UNAVAILABLE` / `RELINK_REQUIRED` / `UNLINKING`。公式アカウント友だち確認が通知有効化の必須条件。OpsCue内通知は常時有効。
- LINEカテゴリ初期ON：応募結果、勤務確定・変更、前日確認、勤務リマインダー、サポート返信。初期OFF：重要なお知らせ。`ACTIVE`時のみ本人がテスト通知可（提案上限60秒間隔・5回/日）。LINEの既読・リンクタップはOpsCue通知の既読にならない。

## 5. 権限とセキュリティ

| 主体 | 認可の原則 |
|---|---|
| Worker | 自分の応募、勤務、申請、通知、勤務設定、サポートに限定 |
| Manager | 管轄支店・案件・スタッフなど明示されたスコープに限定 |
| System Admin | ロール名だけで無制限とせず、明示権限・スコープに従う |
| Server/RPC | 状態変更時に本人性、支店権限、対象状態、競合、期限、冪等性を再検証 |

UIの非表示は権限保護ではない。RLS・RPC・サーバー処理が実際の認可境界。検索結果、件数、CSV、通知リンク、監査表示にも同じ境界を適用。ログに秘密鍵、OAuthトークン、不要な個人情報、Admin内部メモを出さない。

## 6. 共通UI状態・操作契約

| 状態 | UI上の要件 |
|---|---|
| loading | 読込中を明示、二重送信を防ぐ |
| empty / filtered_empty | 元データ0件と絞込0件を区別 |
| error / unavailable | 通信失敗・業務上利用不可を区別し再試行可否を示す |
| forbidden | 情報を漏らさず、適切な導線を表示 |
| validation_error | 入力箇所と理由を表示し入力を保持 |
| conflict | 最新データを再取得して再確認 |
| confirmation_required | 状態を変えず警告内容を示し明示確認を待つ |
| unknown | 結果不明として重複実行を防ぎ、規定キーで照会 |
| partial_success | 複数件処理で必要なら内訳を表示。ただし一括応募では禁止 |

変更操作は成功・失敗・結果不明を混同しない。破壊的操作には確認と監査。色だけで意味を伝えず、フォーカス、キーボード、タッチ、レスポンシブ、スクリーンリーダー向けラベルを備える。

## 7. 共通コンポーネントとデザインの責務

Adminの`PageHeader`、`SummaryCard/KPICard`、`StatusBadge`、`DataTable`、`FilterBar`、`Drawer`、`ConfirmDialog`、`Toast/InlineAlert`、`Skeleton/Empty/Error/Forbidden`を基準に、状態・色・エラー表現を整える。Workerはカードと次の行動を優先。コンポーネント再利用は可だが、Admin/Workerのナビ寸法や権限を混ぜない。管理画面の配置・休憩ワークスペースは全幅の例外とする。

## 8. 監査・通知・データ整合

監査の最低要素：`actor_id`、`action`、`target_type`、`target_id`、`occurred_at`、`request/correlation_id`、必要最小限の`before/after`、`reason`、`outcome`、確認内容。通知は業務イベントを起点にOpsCue内通知を作り、LINEを非同期の補助配送とする。配信失敗で業務確定をロールバックしない。勤務先マスタ変更で過去・既存シフトの確定スナップショットを自動更新しない。

## 9. ルーティングと画面実装の扱い

Workerの候補：`/worker`、`/worker/support`、`/worker/notifications`、`/worker/announcements`、`/worker/mypage`以下の`profile`・`skills`・`availability`・`preferences`・`notification-settings`・`line`・`security`。Adminの候補：`/admin/attendance`、`/admin/staff`、`/admin/help-requests`、`/admin/announcements`、`/admin/clients`、`/admin/workplaces`。**いずれも添付資料中の推奨ルートであり、既存ルートの棚卸し前に新設を決定しない。** 全ルート詳細は第II部に収録。

## 1. 共通データ構造と責務

```text
取引先 → 案件 → 業務 → シフト
                     ├─ 募集・応募（Application）
                     ├─ 配置（Assignment）
                     ├─ 前日・当日確認
                     └─ 勤怠・確定
勤務先マスタ → 業務 → シフトの勤務先スナップショット
Worker → 勤務可能時間 / 希望条件 / スキル・資格 / 申請
ヘルプリクエスト → Worker / 関連Assignment / Admin担当
お知らせ → 公開時に固定した対象Worker集合
業務イベント → OpsCue内通知 → 任意のLINE補助配信
```

「シフト運用」は横断管理の画面でありデータ上の親ではない。応募の承認とAssignmentの確定、通知の既読と業務操作完了、希望条件と勤務可否は別の概念とする。

## 2. ロール・認可・データアクセス

| 主体 | 基本契約 | 状態 |
|---|---|---|
| Worker | 自身の応募・勤務・通知・問い合わせ・勤務条件のみ閲覧/許可された操作 | 確定（UI） |
| Manager | 管理対象の支店・案件・スタッフ等に限定 | 確定（UI） |
| System Admin | ロール名だけで全権限とみなさず、明示された権限・スコープに従う | 確定（UI） |
| サーバー処理 | 重要な状態変更をRPC等の認可された経路で実施 | 確定方針・要照合 |

- UIのボタン非表示は認可の代替にならない。RLS、RPC、サーバーで本人性・所属支店・状態・対象IDを検証する。
- 検索、件数、集計、CSV、通知ディープリンクでも権限外の存在や情報を漏らさない。
- 認証切れ、競合、権限不足、0件、取得失敗を区別する。

## 3. 募集・応募・審査・配置

### 3.1 基本フロー

```text
募集公開 → Worker応募 → Admin審査（承認/却下）
                              ↓
                        Admin配置（Assignment）
                              ↓
                   勤務予定・確認・勤怠・勤務結果
```

応募の承認は配置完了ではない。応募取下げと配置済み勤務の取消申請は別の操作。確定済み勤務の取消は正式な申請・判断経路を通す。

### 3.2 一括応募・DTO（既存のv1.0-RCとの照合が前提）

- 一括応募は**同じ案件の1〜10シフト**。全件成功または全件失敗で、部分成功はない。
- 結果は `success` / `failure` / `validation_error` / `unavailable` / `unknown` を区別する（実際のDTOの綴り・構造は要照合）。
- 結果不明 `unknown` の場合のみ照会・再送の対象とし、同じ `batchKey` を再利用する。
- 応募不可理由 `WITHDRAWN_REAPPLY_NOT_ALLOWED` と `PREVIOUS_APPLICATION_REJECTED` は別コード。
- 警告 `OVERLAPS_OWN_PENDING_APPLICATION` と `AVAILABILITY_NOT_CONFIRMED` は応募不可理由と混同しない。
- 日付判定は **Asia/Tokyoの勤務開始日**を基準とする。
- 10/31 UIデモでは `isDemo` 等で合成データを明示する。正式DTOとの差分を記録し、fixtureを二重管理しない。

### 3.3 審査RPC（PR-05）

**PM決定:** Adminの承認・却下を認可付きRPCに集約し、直接UPDATEによる状態遷移の迂回を閉じる。取消済みシフト・無効Workerの**承認は拒否**し、適法な応募の却下は可能とする。不要な直接INSERT権限も、既存RPCへの影響を隔離環境で検証したうえで閉じる。応募結果通知の追加実装はP1以降。

設計書のRPC案：

```sql
public.review_shift_application(
  p_shift_id uuid,
  p_application_id uuid,
  p_decision text,
  p_idempotency_key uuid,
  p_acknowledge_warnings boolean default false
) returns jsonb
```

- ロック取得の共通順序は原則 **シフト → Worker → 対象レコード → receipt**。具体的なロック範囲は既存RPCと照合する。
- 承認時の勤務重複は `OVERLAPS_OWN_ASSIGNMENT` / `OVERLAPS_OWN_ACCEPTED_APPLICATION` として**警告**。配置時の重複は別契約に従い**拒否**。
- 警告がある承認は**2段階確認**。最初の呼出しでは状態を変えず `confirmation_required` を返す。
- **要修正:** 添付PR-05案の「確認後に警告内容が変わっても承認する」は採用しない。再実行時に警告を再評価し、新しい/変化した警告があれば再確認する。確認対象の版・ハッシュ等の具体的な契約と冪等キーの扱いは要設計。
- 同一キー・同一要求の確定済み再送は同じ結果を返す。同一キーの別要求は競合扱い。`confirmation_required` の暫定応答を確定済みreceiptとして固定しない。
- **実装報告:** 隔離DBで修正前6/6の再現、修正後34/34 PASS、lint・型チェックOK、ローカルcommit済みとの担当者報告あり。実装済みcommit SHA・変更差分・テストログは別途確認。

## 4. 勤務可能時間・希望条件と応募/配置（P0-4）

### 4.1 Worker入力とDB判定

| DB状態 | 共通UI判定 | 意味 |
|---|---|---|
| `explicitly_available` | AVAILABLE | 対象時間を勤務可能で完全カバー |
| `consultation_required` | CONSULT | 勤務可能・相談可能で完全カバーし、相談を含む |
| `partially_available` | UNKNOWNを含む | 対象時間に未登録区間あり |
| `unknown` | UNKNOWN | 未登録 |
| `explicitly_unavailable` | UNAVAILABLE | 勤務不可と重なる |

- 登録区間は `[start,end)`。異なる状態間も重複を禁止し、隣接区間は許可する。日跨ぎは翌日終了を明示する。
- 過去・進行中の登録は閲覧のみ。確定済みAssignmentと矛盾する新規登録は警告確認後に保存可能だが、Assignmentを自動取消しない。
- 希望条件はソフト条件であり、単独の応募禁止要件ではない。

### 4.2 PM決定の判定表（既存実装への反映は11月工程）

| 勤務可否 | Worker応募 | Admin承認 | Admin配置 |
|---|---|---|---|
| AVAILABLE | 受付可 | 承認可 | 配置可 |
| CONSULT | 警告付き受付 | 明示確認後可 | 明示確認後可 |
| UNKNOWN（部分登録含む） | 警告付き受付 | 明示確認後可 | 明示確認後可 |
| UNAVAILABLE | 不可 | 不可 | 不可 |

**採用案:** W1 + R1 + A2 + K1。`AVAILABILITY_NOT_CONFIRMED` は警告。Admin配置の確認者・日時・判定時の勤務可否を、既存の `candidate_assignment_command_receipts` に記録する設計。確認フラグを受け取っただけで無条件に配置せず、RPCで最新状態・権限・競合を再検証する。

**仕様差分:** 従来の統合仕様14.2にある「UNKNOWNは配置をハードブロック」は、このPM判断に従い**明示確認が必要**へ改訂対象。既存実装は「UNAVAILABLE以外を確認なしで通す」と報告されており、現時点では新契約の実装完了とみなさない。11月の決勝向け工程で対応し、10/31のUI限定デモの前提にはしない。

## 5. Assignment・勤務・前日確認・勤怠

- Assignmentの有効性と応募状態を混同しない。勤務予定には勤務中、未来、結果未確定の勤務を含め、最終結果が確定したものを勤務履歴へ移す。
- Worker勤務詳細は「概要 → 次にやること → 集合・準備 → 前日確認 → タイムライン → 勤怠 → 連絡・サポート」。
- 前日確認の回答期限が過ぎた場合は自動欠勤扱いせず、サポート等の正式導線へ誘導する。
- 勤怠の勤務状態、訂正状態、Admin確定状態は別。Adminの個別・一括確定は権限・未処理申請・時間整合性を再検証する。
- シフトの勤務先情報は確定時のスナップショットを正とする。勤務先マスタの編集で過去/既存シフトを自動上書きしない。
- **要決定（SNAP-01）:** 業務の勤務先変更、シフト複製、日時変更、取消復旧、一括作成時のスナップショット再生成・手動上書き優先順位。

## 6. Worker申請とAdmin承認

| 対象 | Worker | Admin | 状態 |
|---|---|---|---|
| 電話番号変更 | 申請・状態確認・許可された取下げ | 審査・承認後に正式反映 | Worker確定 / Admin導線要照合 |
| スキル・資格の追加/更新 | 申請・履歴確認 | 審査・承認後に正式情報へ反映 | Worker確定 / Admin審査UI未具体化 |
| 勤務可能時間・希望条件 | 本人が登録・編集 | 原則閲覧 | 両UIで概ね一致 |
| 配置済み勤務の取消 | 正式な取消申請 | 権限・状態に応じ判断 | 既存契約と照合 |

- 申請中・未確認・期限切れのスキル/資格を正式な応募・配置資格に含めない。
- Admin側で申請一覧、承認、却下/差戻し、二重処理、反映時の監査、通知を具体化する必要がある。
- **要照合:** Adminの「System Adminによるスキル資格編集」と「Worker申請の審査」を権限・データモデルでどう両立するか。

## 7. サポート・SOS・お知らせ

- SOSと通常問い合わせはAdminヘルプリクエストへ統合。状態は **未対応 → 対応中 → 解決済み**。解決済みの再対応依頼はAdminの再開判断に従う。
- SOSは本人の有効な開始前・勤務中Assignmentに紐付ける。緊急の安全対応をアプリ内返信やLINE到達に依存させない。
- Worker/Admin間の返信とAdmin内部メモはUI・取得API・通知本文で分離する。
- お知らせは下書き → 公開中 → アーカイブ。公開時点で対象Worker集合を固定し、後から支店変更等で対象を自動追加しない。
- アーカイブ後はWorkerの直リンク閲覧も不可。お知らせ自体の個別閲覧・既読率集計はMVP対象外。
- **要照合:** 公開後の実質的変更に対する通知の自動/手動トリガーはWorkerとAdminの詳細仕様に差があるため、イベント契約として確定する。

## 8. OpsCue内通知・LINE補助通知

- OpsCue内通知は正本かつ常時有効。Workerが切り替えるのはLINEのカテゴリ別通知のみ。
- LINE通知は任意。LINE Loginの認証成功、Worker紐付け成功、公式アカウント友だち確認、送信可能性を別の状態として管理する。
- LINE連携状態：`UNLINKED` / `LINKING` / `FRIEND_REQUIRED` / `ACTIVE` / `UNAVAILABLE` / `RELINK_REQUIRED` / `UNLINKING`。
- LINE初期ON：応募結果、勤務確定・変更、前日確認、勤務リマインダー、サポート返信。初期OFF：重要なお知らせ。
- `ACTIVE` のWorker本人のみテスト通知を送信可。提案上限は60秒間隔・1日5回。テスト通知はOpsCue内通知を作成しない。
- LINEの受信・閲覧・リンクタップはOpsCue通知の既読を変更しない。OpsCue側で認可済み通知詳細を開き、既読更新が成功したときのみ既読にする。
- 業務イベントの確定とLINE送信は分離。Outbox/Queue、冪等性、再試行、送信直前の連携状態・カテゴリ再検証を行う。配信API成功は端末到達保証ではない。
- 連携解除でLINE送信を停止し、OpsCue内通知・業務履歴・カテゴリ設定は維持する。
- **要照合:** LINE公式APIの友だち状態確認、OAuth、Webhook、チャネル構成は実装時の公式仕様と既存環境で確認する。

## 9. 共通エラー・冪等性・監査

### 9.1 結果の表現

- `loading` / `empty` / `filtered_empty` / `error` / `forbidden` / `conflict` / `partial_success` 等のUI状態は区別する。ただし一括応募は**partial_successを許さない**。
- 応募、審査、配置、取消、確定、公開、通知は、サーバー側で認可・対象状態・競合・期限・重複を再確認する。
- 確定済み操作の同一キー再送は前回結果を返し、別内容へのキー流用は拒否する。通信途絶による結果不明と業務拒否を区別する。

### 9.2 監査の最低要素

`actor_id`、`action`、`target_type`、`target_id`、`occurred_at`、`request/correlation_id`、`before/after`（必要最小限）、`reason`、`outcome`、確認・警告の内容と判断結果。ログにトークン、シークレット、不要な個人情報、Admin内部メモを含めない。

### 9.3 変更・承認ゲート

- 既存のmain保護、Draft PR、隔離環境の境界を維持。
- ローカルDB・合成データ・ローカル確認ブランチでのテストと、クラウド/本番反映を区別。
- PR-02/03/05のローカル統合確認は、公開キーを `.env.local` に限定、Studioの正式なAuth経路で合成アカウントを作成、`127.0.0.1` で起動、pushしない、衝突時停止という条件付き承認。
- PR-05 migrationを適用したDBへ古い審査Actionを接続すると失敗するため、画面とDBの版を揃える。

## 1. 設計原則と情報構造

### 1.1 目的
管理者が募集から現場終了まで、案件・業務・シフト・応募・配置・勤怠・問い合わせを一貫して扱えること。ホームは状況把握、要対応は優先順位付け、各業務画面は実行と監査を担う。安全な権限境界を守り、操作結果を誤認させない。

### 1.2 正規の業務構造
```text
取引先マスタ（複数案件から参照可能）
  └─ 案件（1案件の取引先は原則1件）
       └─ 業務（各業務は勤務先マスタ1件を参照）
            └─ シフト（日時・人数・募集・応募・配置・確認）
                 ├─ Assignment（スタッフとシフトの紐付け）
                 ├─ 配置・ポジション・休憩ローテーション
                 ├─ 前日・当日確認
                 └─ 勤怠・打刻・訂正・確定
勤務先マスタ（複数業務から参照可能）→ 業務 → シフトの勤務先情報スナップショット
スタッフ → スキル・資格／勤務条件／勤務履歴
ヘルプリクエスト → スタッフ・関連勤務・管理者担当
お知らせ → 公開時点で確定した対象Worker集合
```

## 5. ホーム・要対応

### 5.1 ホーム
**目的：** 今日の稼働状況と管理者の直近の判断事項を素早く把握する。

表示順：①ページヘッダー ②「対応が必要」（最大5件、優先度順）③「今日のサマリー」④「今日の現場」。対応事項のカードから対象業務へ遷移し、ホーム上で状態を直接更新しない。現場の表示は権限内の本日対象シフトに限定し、勤務日・案件・業務・勤務先・時間・配置・不足・状況などを示す。日付・タイムゾーンの業務基準を明示する。

### 5.2 要対応
**目的：** 未対応・期限超過・不足・要確認など、管理者の処理が必要な項目を横断集約する。種類、件名、対象勤務、緊急度、発生日時、詳細遷移を表示。既存の業務状態を読み取って分類し、要対応画面だけの独立した真実の状態を作らない。権限外項目・件数は表示しない。解決操作は原則として元の業務画面で実行する。

## 6. 案件管理・業務管理

### 6.1 案件一覧
KPI：全案件・進行中・下書き。検索、状態・取引先・期間などの絞り込み。PC列：案件名＋コード／取引先／期間／業務数／シフト数／状態／操作。スマホカード。案件名から詳細へ。

### 6.2 案件詳細
独立ページ。ヘッダーに案件名・状態・取引先・編集。概要KPIの下に **概要／業務／シフト／履歴** の4タブ。業務タブから右ドロワーで追加・編集し、シフトタブからシフト詳細へ遷移。

### 6.3 案件作成・編集
基本情報：案件名（必須）、取引先（必須）、案件コード（自動）、開始・終了日、説明、状態。**業務0件でも下書き保存可**。進行中への遷移などは既存業務ルールに従って必要な業務・期間を検証。取引先は有効マスタから選択。業務は案件に紐づき、勤務先は有効マスタから選択または新規登録。

### 6.4 業務追加・編集
右ドロワー480〜560px。業務名・種別・勤務先・説明／業務条件を扱い、参照済み業務の削除・勤務先変更は関連シフトや応募への影響を確認。参照を持つ業務を安易に物理削除しない。案件内で作成した勤務先はマスタ登録後に業務フォームへ戻して選択状態を復元する（接続方式は実装時確認）。

## 7. シフト運用・配置・確認

### 7.1 シフト一覧
全案件を横断し、**一覧／週／月**を切替。KPI：対象シフト・募集不足・配置未完了・要確認。PC列：勤務日、案件・業務、勤務先、勤務時間、必要人数、応募、配置、人数不足、状態、操作。月表示は1日最大3件＋残件数。不足人数の基本式は `max(必要人数 - 有効配置人数, 0)`。時間帯別の充足は別途評価。

### 7.2 シフト作成
独立ページ。案件→業務を選択し勤務先を読み取り表示。単日・複数日・期間／曜日指定、開始・終了、休憩、必要人数、応募締切、募集状態、備考。重複日付・案件期間外・時刻矛盾を確認プレビューで検証してから確定。二重送信防止。

### 7.3 シフト詳細・編集
詳細は **概要／応募／配置／確認** タブ。編集は独立ページで1シフトずつ。日時・人数・募集条件の変更時は応募・配置・確認回答・通知への影響を事前に示す。シフトの勤務先は業務から継承するが、Worker向けの確定案内はシフトスナップショットを正とする。

### 7.4 配置・休憩回し（B案）
**専用の全幅ワークスペース**を採用。時間軸の15分／30分刻み、スタッフ行、ポジション配置、休憩ブロック、ドラッグ・リサイズ、競合・充足表示、右ドロワー編集。シフト詳細の配置タブは概要とワークスペースへの入口。スタッフとシフトのAssignmentと、シフト内のポジション・休憩を混同しない。

### 7.5 前日・当日確認
シフト運用内の横断タブから回答状況を一覧確認。確認状態と勤怠実績は別概念。Worker回答やAdminの対応は既存権限・監査契約に従う。

## 8. 勤怠管理

### 8.1 一覧
単日を基本に前日／今日／翌日ショートカット、勤務状態・確認状態・確認対象・スタッフ／案件／業務／勤務先検索。適用ボタンとURL条件復元。KPI：勤務予定・未確定・確定・訂正済み・欠勤／無断欠勤・要確認。**訂正済みと確定などは重複し得るため、KPIを単純合算しない。**

### 8.2 勤怠詳細
独立ページで「1人×1勤務」の実績を表示。予定／実績、打刻、休憩、実働、確認事項、打刻履歴、操作履歴。上部に「勤怠を修正」「勤怠を確定」、欠勤操作は一覧行・詳細の「…」メニュー。IDは既存DBの勤怠識別子と照合。

### 8.3 修正・申請・確定
修正ドロワーは約520px、出退勤・休憩・理由、変更前後比較。修正申請は専用一覧からレビュー用ドロワーへ。**個別確定と一括確定**を提供し、未処理申請・時刻矛盾等がある場合は確定を制限。複数件処理は対象件数・失敗件数・再試行可能な結果を表示。欠勤・確定・解除は確認と監査を必須にする。

### 8.4 勤怠集計
期間別・スタッフ別・案件別の実績とCSV。集計基準・タイムゾーン・権限スコープを明示する。CSVも同じ権限制御を適用。

## 9. スタッフ管理

### 9.1 一覧
既存登録・招待フローを維持。KPI：登録スタッフ／稼働可／休止・停止。検索：氏名・スタッフID、所属・状態フィルター。PC列：氏名＋ID、支店、状態、次回勤務、直近勤務、詳細。サーバーページング25件初期、25／50／100切替。取消済み配置は次回勤務に含めない。

### 9.2 詳細
独立ページ。共通ヘッダーと5タブ：**概要／スキル・資格／勤務条件／勤務履歴／基本情報**。タブはURLクエリで復元。
- 概要：次回勤務・直近勤務・勤務回数・欠勤等。
- スキル・資格：スキルと資格・期限を区別。Manager閲覧のみ、明示権限を持つSystem Adminが編集。
- 勤務条件：Worker本人が編集、Adminは閲覧のみ。「不明」を「勤務可能」とみなさない。
- 勤務履歴：PCテーブル・スマホカード、シフト／勤怠詳細へリンク。
- 基本情報：ID・氏名・所属・状態・登録・Auth/Profile連携状況。未確認の連絡先を捏造しない。

### 9.3 編集
右ドロワー480〜560px。権限に応じて編集項目を限定。稼働状態など重要変更は確認・監査。支店権限と個人情報の最小表示を徹底する。

## 10. ヘルプリクエスト管理

### 10.1 一覧
KPI：未対応・対応中・本日解決。初期状態フィルターは未解決。検索、カテゴリ・優先度・担当者・受付日時。PC列：受付日時／優先度／件名・冒頭／スタッフ／関連勤務／状態／担当者／最終更新／詳細。緊急かつ未対応を優先。

### 10.2 詳細・やり取り
独立ページ。左側に問い合わせとWorker/Adminの時系列メッセージ、右側約320pxに担当・状態・優先度・スタッフ・関連勤務。**双方向返信**と**管理者専用内部メモ**はUI・データ・取得APIを分離。返信失敗時は入力を保持し、二重送信を防止。

### 10.3 状態・担当
状態：**未対応 → 対応中 → 解決済み**、再オープンは解決済み→対応中。担当は管理者が手動指定。担当指定だけで状態を自動変更しない。対応開始・解決の条件、再オープン理由、優先度（通常／緊急）変更を監査する。解決済みの返信は再オープン後に許可。

### 10.4 通知
新規受付、緊急、担当変更、Admin返信、Worker返信、解決、再オープン。通知は権限確認付きで対象詳細へ遷移。内部メモをWorkerへ絶対に送信しない。

## 11. お知らせ管理

### 11.1 一覧・作成
一覧タブ：**すべて／下書き／公開中／アーカイブ**。PCテーブル・スマホカード。タイトル、本文概要、重要度、状態、支店、対象人数、作成者、公開・更新日時。

新規作成・編集は独立ページ。タイトル最大120文字、本文最大5,000文字、重要度通常／重要、公開対象支店、Worker向けプレビュー。下書きは空欄保存可。初期実装では下書き保存→詳細ページ→公開確認の二段階方式。

### 11.2 公開・対象固定
**公開時点の対象Workerをサーバー側で確定し、対象者IDの集合を固定する。** 公開確認で支店・対象人数・重要度を表示。対象0人は原則公開停止。公開後の支店・対象者変更は不可。新規登録Workerへ過去のお知らせを自動公開しない。アカウント停止等のアクセス制御は引き続き優先。

### 11.3 公開後編集・履歴
公開中でもタイトル・本文・重要度を編集可能。変更前後、変更者、時刻、バージョンを保存。対象者スナップショットは変えない。Workerには最新版と更新日時を表示。状態：**下書き→公開中→アーカイブ**。アーカイブからの再公開は初期実装対象外。公開中の物理削除は禁止。

### 11.4 通知・既読
初回公開と実質的な公開後編集で対象Workerへ通知。冪等性・再試行を確保。**既読人数・既読率・個別閲覧履歴は初期実装に含めない。**

## 12. 取引先・勤務先マスタ

### 12.1 共通
一覧は独立ページ、追加・編集・関連情報・履歴は右ドロワー。**独立詳細ページは作らない。** 状態は有効／無効。物理削除は原則しない。無効化前に影響件数と既存参照を警告し、権限のある管理者が確認後に無効化可能。無効化しても既存案件・業務・シフト・勤怠を消さない。新規参照候補から除外し、再有効化を許可。

### 12.2 取引先
一覧：取引先名・メモ・状態・関連案件数・更新日時・操作。登録：取引先名必須、メモ任意、支店・状態は既存フォーム／DB契約と照合。名称重複は警告するが、名称一致だけで同一法人と断定しない。関連案件は案件一覧の取引先フィルターへ遷移。

### 12.3 勤務先
一覧：勤務先名・住所・状態・関連業務数・未来シフト数・更新日時・操作。登録：勤務先名、住所、交通案内、アクセス補足、集合案内、状態。**要決定 MASTER-01：既存の勤務先画面にある支店・郵便番号を最終マスタ仕様の入力項目へどう復元するか。** 既存DBとの照合まで削除扱いにしない。支店は作成後に変更できない設計が元画面に存在するため、変更可否を調査して確定する。

### 12.4 スナップショット
シフト作成時に勤務先名・住所・交通・アクセス・集合案内・参照元バージョン等の確定値を保存。**マスタ編集だけで既存シフトを更新しない。** 未来シフトへは影響確認→対象選択→差分確認→反映確定。配置済みWorkerへの案内変更は通知。勤務開始済み・完了済み・取消済みは通常反映不可。過去記録の訂正は別の監査付き手順。

**要決定 SNAP-01：** 業務の勤務先変更、シフト複製、日時変更、取消復旧、複数日一括作成の際に、スナップショットを再作成する条件と手動上書きの優先順位。実装前に明文化する。

### 12.5 監査
マスタの作成・編集・無効化・再有効化は変更前後・操作者・時刻を記録。シフトへのスナップショット反映は、マスタ変更履歴と別にシフト側の変更履歴を記録。関連件数は権限外のデータを漏らさず、全影響を確認できない場合は高権限者による実行を要求する。

## 13. スキル・資格マスタ・設定

### 13.1 スキル・資格マスタ
**未確定。** ナビゲーション項目とスタッフ詳細での閲覧・編集方針は存在するが、マスタの一覧・登録・分類・有効期限・廃止・スタッフ付与・資格証明の取扱いについて独立した最終仕様がない。既存DB・権限・スタッフ詳細と整合するまで、新しい更新機能を勝手に確定しない。

### 13.2 設定
**未確定。** サイドバー最下部に入口を設ける方針はあるが、機能の内訳は未決定。未実装の設定を操作可能に見せない。

## 14. 権限・状態・監査・通知の横断規則

### 14.1 権限
- Manager：管理対象支店・業務・スタッフに限定。支店外の行・KPI・検索候補・集計値・エクスポートを漏らさない。
- System Admin：ロール名だけで無条件の全権限を仮定しない。明示的な権限・スコープを優先。
- Worker：自身の勤務・条件・対象通知・問い合わせ等、Worker側で許可された範囲のみ。
- UIのボタン非表示は補助策。実際の認可はサーバー/RPC/RLSで強制。安全な既存更新経路がなければ操作を有効化しない。

### 14.2 重要な状態
| 対象 | 主な状態・遷移 |
|---|---|
| 案件 | 下書き／進行中／終了（詳細条件は案件・Backend契約） |
| シフト | 募集中／締切／終了等（既存定義を優先） |
| 勤怠 | 勤務状態と確定状態を分離。訂正済みは別属性になり得る |
| スタッフ | 稼働可／休止／停止 |
| 問い合わせ | 未対応→対応中→解決済み、再オープン可 |
| お知らせ | 下書き→公開中→アーカイブ |
| 取引先・勤務先 | 有効⇄無効 |

### 14.3 監査・競合・通知
- 重大操作：操作者、対象ID、日時、変更前後、必要な理由、結果を記録。時刻はサーバー基準。
- 保存・公開・確定・配置更新・無効化は二重送信と同時編集を検出する。成功応答前に成功したように見せない。
- 通知は元データの保存結果と分けて再試行できるようにする。通知失敗を「元の処理も失敗」と誤表示しない。
- 通知からのディープリンクも再度認可する。非公開メモ・権限外の個人情報を通知本文に含めない。

## 15. エラー・空状態・アクセシビリティ

全画面で **Loading / Empty / Filtered-empty / Error / Forbidden / Conflict / Partial-success** を区別。取得エラーを0件として扱わない。保存失敗時は入力値・編集中の差分を保持。危険操作は対象・影響・結果を明示する。スマホの全画面ドロワーでキーボードに保存操作を隠さない。フォーカス表示、Escで閉じる場合の未保存確認、スクリーンリーダーのラベル、44pxタッチ領域、テキストと色の併用を守る。

# 第1部：Worker統合設計

## 1. プロダクトと共通UX原則

OpsCueのWorker画面は、募集の確認・応募から、勤務確定、準備、前日確認、勤怠、問い合わせ、プロフィール・勤務設定までを一貫して扱う。

1. **本人の次の行動が分かること。** ホームは対応が必要なことを優先し、勤務詳細には「次にやること」を設ける。
2. **業務の正本はOpsCue。** LINEは補助配信であり、既読やLINE受信だけで前日確認・勤怠・申請を完了させない。
3. **申請と正式変更を区別。** 電話番号・スキル・資格などはWorkerの申請後、所定のAdmin確認・承認を経て反映する。
4. **状態を混同しない。** 勤務可否、希望条件、応募、配置、勤務、通知既読、問い合わせ状態はそれぞれ独立して管理する。
5. **本人以外へのアクセスを許可しない。** 表示制御だけでなくサーバー側の認可・RLS・RPCで検証する。
6. **変更履歴を残す。** 業務上重要な作成・更新・承認・取消・送信・失敗を監査する。

## 4. 主要な業務横断フロー

### 4.1 募集から勤務まで

```text
募集を確認 → 応募 → 審査／結果通知 → Assignment確定
  → 勤務予定 → 前日確認 → 当日の出発／到着／勤怠
  → 勤務結果の確定 → 勤務履歴
```

応募条件・勤務可能時間・スキル資格の正式判定はサーバー側で行う。ホームに表示した応募可能募集も、応募実行時に再検証する。募集詳細・一括応募などの厳密な契約は独立募集仕様およびBackend契約との照合が必要。

### 4.2 勤務可能時間と配置

- 勤務可能時間は日時区間 `[開始, 終了)`。状態が異なっても重複禁止。隣接区間は許可。
- 日跨ぎは「翌日終了」を明示。日本時間で入力・表示し、保存は曖昧でない日時形式を使用。
- 未登録区間は `UNKNOWN`。代表判定の優先順位は `UNAVAILABLE → UNKNOWN → CONSULT → AVAILABLE`。区間別内訳も保持する。
- 確定済み勤務と矛盾する登録は警告して保存可能。ただし既存のAssignmentは自動取消しない。
- 希望条件は推薦・参考情報であり、単独の応募禁止条件ではない。

### 4.3 サポートと通知

```text
SOS／問い合わせ作成 → Adminヘルプリクエスト
 → 未対応 → 対応中 → 解決済み
                      └→ Worker再対応依頼 → Admin判断
```

SOSの対象は本人の有効な開始前・勤務中Assignment。差し迫った危険への対応はアプリ内返信を待たず直接連絡する。Adminの内部メモはWorkerへ公開しない。

### 4.4 通知とLINE

```text
業務イベント → OpsCue内通知を生成 → LINE送信可否を評価
                                         ├─ 対象外／設定OFF → 送信なし
                                         └─ ACTIVE・カテゴリON → 非同期配信
```

通知既読、LINEメッセージ閲覧、前日確認・打刻などの業務完了は独立。LINE配信失敗で業務トランザクションを取り消さない。

## 6. 権限・監査の共通契約

| 操作分類 | Worker | Admin／サーバー |
|---|---|---|
| 本人の募集・勤務・通知・問い合わせ閲覧 | 認可範囲内で可 | 管理権限に応じて可 |
| 本人の勤務可能時間・希望条件 | 原則本人が登録・変更 | 既存の管理者代理操作契約と照合 |
| 電話番号の正式更新 | 申請のみ | Admin確認・承認後に反映 |
| スキル・資格の正式更新 | 申請のみ | Admin承認後に反映 |
| 問い合わせの作成・返信 | 状態に応じて可 | 対応・解決・再開を管理 |
| LINEの本人紐付け・解除・設定 | 本人のみ | 認証済みサーバー処理 |
| 業務状態の確定 | 許可された操作のみ | サーバーで権限・状態・競合を再検証 |

監査は原則として、actor、対象ID、操作種別、変更前後、理由（必要な場合）、時刻、相関ID、成功／失敗を追跡可能にする。認証トークン、LINEシークレット、医療情報、不要な個人情報はログへ含めない。監査ログと通知配信ログは分離する。

## 7. 共通エラー・状態表示

- **空状態**：対象0件と取得失敗を区別する。
- **読み込み中**：スケルトン等で表示し、完了済みと誤認させない。
- **認証期限切れ**：再認証へ誘導する。
- **権限なし**：他人のIDや古いディープリンクから情報を漏らさない。
- **競合**：保存・承認・応募・配置・取消・既読処理などはサーバー側で再検証し、必要に応じ最新状態を再取得する。
- **期限切れ**：前日確認などの期限後操作は許可せず、適切なサポート導線を示す。
- **送信失敗**：業務上の受付成功とLINE配信結果を混同しない。
- **アクセシビリティ**：色だけで状態を表さず、ラベル・フォーカス・キーボード操作を備える。

## **3\. 今日やること**

本人が対応すべき、未完了のアクションを表示する。

表示対象は、既存のWorker業務仕様でアクションとして定義され、かつ本人が実行可能なものに限定する。

表示ルール

## **4\. 次の勤務**

今回の重要な決定として、進行中の勤務を未来の勤務より優先する。

### **表示優先順位**

1. 勤務中のシフト  
   勤務カードの見出しを「現在の勤務」に変更する。  
2. 本日これから開始するシフト

3. 翌日以降の最も近いシフト  
   見出しは「次の勤務」。勤務日時の近い順に選ぶ。

## **9\. 欠勤・無断欠勤・会社取消**

### **欠勤**

欠勤申告と欠勤確定を区別する。

Workerが欠勤を申し出た時点では、Admin側の処理が完了したとはみなさない。

確定後は「欠勤」と表示し、通常の打刻操作を停止する。

### **無断欠勤**

無断欠勤は、管理者による適切な判定が完了した場合のみ表示する。

単に勤務開始時刻を過ぎた、到着報告がない、打刻がないという理由だけで自動確定しない。

記録に相違がある場合は、対象勤務に紐付けたヘルプリクエストから問い合わせできる。

### **会社取消**

会社側で取消が確定した場合は「会社取消」と表示する。

取消日時とWorkerに公開可能な理由を確認できるようにし、通知から該当勤務詳細へ遷移できるようにする。

本人取消・会社取消・欠勤・無断欠勤の履歴は保持し、監査上必要な記録を削除しない。

## **10\. コンパクトタイムライン**

タイムラインは表示専用とし、操作ボタンを設置しない。

表示する主要イベントは、勤務確定、前日確認、出発・到着、勤務開始、勤務終了。

状態は「予定」「完了」「未記録」「対象外」「取消」などで表す。

予定時刻と実績時刻を同じイベント内に表示する場合は、必ずラベルを付ける。

履歴が多い場合は、初期表示を主要イベントに限定し、「すべての記録を見る」で展開する。

ただし、取消済みや終了済みの履歴閲覧は、Assignmentが無効になっても本人に必要な範囲で許可する。

UIの非表示だけでアクセスを制限せず、RLS・RPCなどサーバー側で認可を実施する。

## **13\. 監査・履歴**

監査対象は、前日確認の回答、出発・到着報告、勤務開始・終了打刻、取消申請、取消承認・却下、勤怠修正、欠勤判定、会社取消など。

Workerに公開する履歴と、Admin専用の監査ログは区別する。

勤怠時刻を後から修正した場合も、元の打刻記録を消さずに変更履歴を保持する。

| 無断欠勤確定 | 不可 |
| 取消申請中・未承認 | 原則可能 |

取消申請中であっても、正式に取消が確定していなければ勤務は有効なため、SOSを利用できる。

一方、勤務終了後の問題や取消済み勤務については、通常問い合わせから連絡できる。

### **3.2 対象勤務の選択**

勤務詳細からSOSを開いた場合は、対象勤務を自動設定する。

サポートトップから開いた場合は、本人の対象勤務を一覧表示し、1件選択する。

勤務カードには以下を表示する。

* 勤務日・開始終了時刻  
* 案件名・業務名  
* 勤務先  
* 勤務状態

対象勤務が0件の場合は、「SOSの対象となる勤務がありません」と表示し、通常問い合わせを案内する。

対象勤務が複数ある場合は、現在勤務中のものを先頭、その後は開始日時の近い順に並べる。

### **3.3 重要な認可条件**

SOS送信時には、選択したAssignmentが本人のものか、対象勤務が許可された状態か、勤務へのアクセス権があるかをサーバー側で再検証する。

URLの勤務IDを書き換えても、他Workerの勤務に紐付けたSOSを送信できないようにする。

## **4\. SOS作成画面**

既存のSOSモーダルにある分類を維持する。

### **4.1 入力項目**

| 項目 | 必須 | 内容 |
| ----- | ----- | ----- |
| 対象勤務 | 必須 | 自動設定または選択 |
| 困っていること | 必須 | 5分類から1つ |
| 状況 | 任意 | 最大500文字 |
| 緊急時の案内 | 表示 | 直接連絡が必要な場合の注意 |
| 送信確認 | 必須 | 送信内容の確認 |

### **4.2 SOS分類**

| 分類 | 説明 |
| ----- | ----- |
| 現場・集合場所 | 入口や集合場所が分からない |
| 配置・業務指示 | 担当場所や作業内容が分からない |
| 時間・移動 | 交通遅延や到着が難しい |
| 体調・安全 | 体調や安全について伝えたい |
| その他 | それ以外の勤務上の問題 |

状況入力は任意とする。

体調・安全の分類では、病名や詳細な医療情報の入力を要求しない。

### **4.3 SOS送信後**

送信成功時は、共通のヘルプリクエストを作成し、問い合わせ詳細へ遷移する。

初期状態は原則「未対応」、初期優先度は「高」。

画面には「SOSを受け付けました」と表示する。

ただし、受付完了は管理者が内容を確認したことを意味しない。

返信時間や対応開始時刻を保証する表示は行わない。

### **4.4 緊急時の注意**

SOSは緊急通報サービスではない。

差し迫った危険がある場合は、アプリ内の返信を待たずに、現場責任者や適切な緊急連絡先へ直接連絡するよう案内する。

連絡先が登録されている場合のみ表示し、存在しない電話番号は補完しない。

## **5\. 通常問い合わせ**

### **5.1 問い合わせ分類**

| 分類 | 対象勤務 |
| ----- | ----- |
| 勤務予定・配置 | 原則必要 |
| 前日確認 | 必要 |
| 勤怠 | 必要 |
| 勤務取消・欠勤 | 原則必要 |
| 登録情報・設定 | 不要 |
| その他 | 任意 |

対象勤務が必要な分類では、本人の閲覧可能な勤務から選択する。

終了済み・取消済みの勤務も、通常問い合わせでは選択可能とする。

### **5.2 入力項目**

| 項目 | 必須 |
| ----- | ----- |
| 問い合わせ種別 | 必須 |
| 対象勤務 | 分類に応じて必須 |
| 件名 | 必須 |
| 内容 | 必須 |
| 送信確認 | 必須 |

件名は最大120文字、内容は最大5000文字をUI上の契約案とする。実装前に既存のDB制約との一致を確認する。

### **5.3 勤務画面との連携**

以下の導線では、対象勤務と問い合わせ分類を引き継ぐ。

| 起点 | 初期分類 |
| ----- | ----- |
| 前日確認期限切れ | 前日確認 |
| 打刻漏れ | 勤怠 |

| 取消申請の相談 | 勤務取消・欠勤 |
| 欠勤・無断欠勤への問い合わせ | 勤務取消・欠勤 |

問い合わせを送信しても、前日確認・勤怠・取消申請の業務状態は自動変更しない。

## **6\. 問い合わせ履歴**

### **6.1 表示対象**

本人が作成した通常問い合わせとSOSを同じ一覧に表示する。

### **6.2 一覧項目**

| 項目 | 内容 |
| ----- | ----- |
| 件名 | 問い合わせタイトル |
| 種別 | 通常・SOS |
| 状態 | 未対応・対応中・解決済み |
| 対象勤務 | 紐付けがある場合 |
| 作成日時 | 初回送信日時 |
| 最終更新日時 | Worker公開情報の更新日時 |
| 未読 | Adminからの未読返信 |

初期並び順は、Workerに公開された最終更新日時の新しい順とする。

Admin内部メモだけの更新で、Workerの一覧順序を変えない。

### **6.3 フィルター**

状態フィルターは「すべて」「未対応」「対応中」「解決済み」。

別途、SOSのみを表示する種別フィルターを設ける。

問い合わせ履歴から詳細へ移動し、戻った際にはフィルターとスクロール位置を復元する。

## **7\. 問い合わせ詳細**

問い合わせ詳細は通常問い合わせとSOSで共通化する。

### **7.1 表示項目**

| 領域 | 表示内容 |
| ----- | ----- |
| ヘッダー | 件名・SOSラベル・状態 |
| 基本情報 | 問い合わせ番号・作成日時・種別 |
| 対象勤務 | 勤務日・時間・勤務先・関連リンク |
| 対応状況 | 未対応・対応中・解決済み |
| メッセージ | WorkerとAdminの公開メッセージ |
| 操作 | 返信または再対応依頼 |

担当者が未割当の場合は「担当者確認中」と表示する。

Admin内部メモ、内部的な優先度変更理由、他Workerの情報は表示しない。

### **7.2 メッセージ表示**

メッセージは送信日時の古い順に表示する。

Worker送信とAdmin送信を視覚的に区別する。

送信日時、送信者区分、本文を表示する。

送信失敗時には入力内容を保持する。

## **8\. 問い合わせ状態と返信ルール**

### **8.1 状態遷移**

未対応

問い合わせ受付済み

Workerは追加返信可能

対応中

Adminが対応を開始

WorkerとAdminが返信可能

解決済み

通常返信は停止

Workerは再対応依頼を送信可能

Adminによる再オープン

理由を記録して対応中へ戻す

### **8.2 操作権限**

| 状態 | Worker返信 | Worker再対応依頼 | Admin状態変更 |
| ----- | ----- | ----- | ----- |
| 未対応 | 可 | 不要 | 可 |
| 対応中 | 可 | 不要 | 可 |
| 解決済み | 不可 | 可 | 可 |
| 再オープン後 | 可 | 不要 | 可 |

Workerからの返信は、問い合わせ状態を自動変更しない。

未対応の問い合わせに追加返信しても、状態は未対応のまま。

対応中の問い合わせに返信しても、状態は対応中のまま。

担当者の割当だけでも、状態を自動変更しない。

## **9\. 解決済みへの再対応依頼**

### **9.1 操作**

解決済みの問い合わせ詳細では、通常返信欄を非表示にし、「追加で連絡する」ボタンを表示する。

押すと再対応依頼フォームを開く。

### **9.2 入力項目**

| 項目 | 必須 | 内容 |
| ----- | ----- | ----- |
| 対象問い合わせ | 自動 | 変更不可 |
| 再連絡の内容 | 必須 | 追加対応が必要な理由 |
| 送信確認 | 必須 | 内容を確認 |

### **9.3 送信後の状態**

再対応依頼を送信しても、問い合わせ状態は「解決済み」のまま。

ただし、Workerには「再対応依頼を送信済み」と表示する。

Admin側には再対応依頼が届き、確認対象となる。

Adminが再オープンすると、状態を「対応中」に変更し、理由を監査に記録する。

### **9.4 重複防止**

未処理の再対応依頼が存在する場合、同じ問い合わせに対する重複申請を防ぐ。

Workerには「管理者の確認待ち」と表示する。

Adminが対応不要と判断した場合も、依頼の処理結果を記録し、Workerへ通知する。

再対応依頼の状態は、問い合わせ本体の3状態とは別に管理する。

## **10\. SOSと通常問い合わせの優先度**

| 種別 | 初期優先度 | 初期状態 |
| ----- | ----- | ----- |
| 通常問い合わせ | 通常 | 未対応 |
| SOS | 高 | 未対応 |

SOSであっても、送信しただけで「対応中」にはしない。

優先度はAdminが対応順を判断するための情報であり、Workerが自由に変更することはできない。

Adminが優先度を変更する場合は、変更理由や変更履歴を監査に残す。

### **Admin側の表示**

SOSは通常問い合わせと同じ一覧に表示し、SOSラベルと優先度で強調する。

Adminは種別・優先度・状態で絞り込めるようにする。

ただし、高優先度だからといって、対応開始・担当者割当・解決を自動実行しない。

## **11\. 通知仕様**

| イベント | 通知先 | 通知内容 |
| ----- | ----- | ----- |
| 通常問い合わせ作成 | 対応可能なAdmin | 新規問い合わせ |
| SOS作成 | 対応可能なAdmin | 高優先度SOS |
| Worker追加返信 | 担当Adminまたは対応可能なAdmin | 新しいメッセージ |
| Admin公開返信 | Worker | 管理者からの返信 |
| 対応開始 | Worker | 対応中への変更 |
| 解決 | Worker | 解決済みへの変更 |
| Worker再対応依頼 | 対応可能なAdmin | 再対応依頼 |
| Admin再オープン | Worker | 対応再開 |
| 再対応依頼の対応不要判断 | Worker | 依頼の処理結果 |

### **通知の原則**

* 通知と業務状態は別管理。  
* 通知の既読は問い合わせの解決を意味しない。  
* 同一イベントの重複通知を防止する。  
* 通知失敗によって問い合わせ本体を消さない。  
* 通知から対象問い合わせ詳細へ直接遷移する。  
* Admin内部メモの内容をWorker通知へ含めない。

SOSは通常問い合わせより目立つ通知にするが、通知が届いたこととAdminが対応を開始したことは区別する。

## **12\. 権限・セキュリティ**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 通常問い合わせ作成 | 可 | 管理権限に従う |
| SOS作成 | 対象勤務がある場合 | 管理・確認 |
| 本人問い合わせ閲覧 | 可 | 管理範囲内 |
| 他Worker問い合わせ閲覧 | 不可 | 管理範囲内 |
| 未対応・対応中への返信 | 可 | 可 |
| 解決済みへの通常返信 | 不可 | 状態管理に従う |
| 再対応依頼 | 可 | 受付・判断 |
| 再オープン | 不可 | 権限保持者のみ |
| 担当者変更 | 不可 | 権限保持者のみ |
| 優先度変更 | 不可 | 権限保持者のみ |
| 内部メモ閲覧 | 不可 | 権限保持者のみ |

### **セキュリティ要件**

認証・認可はUIだけでなく、RLS・RPCなどサーバー側で実施する。

Workerが閲覧できるのは本人の問い合わせと、その問い合わせに含まれる公開情報のみ。

勤務に紐付いた問い合わせでは、対象Assignmentへのアクセス権も検証する。

Adminの権限は既存の拠点・担当範囲に従う。

問い合わせの公開メッセージと内部メモは、保存・取得・通知の各段階で公開範囲を分離する。

## **13\. 監査・履歴**

監査対象は次の操作とする。

| 操作 | 記録する内容 |
| ----- | ----- |
| 問い合わせ作成 | 種別・対象・操作者・日時 |
| SOS作成 | SOS分類・対象勤務・日時 |
| 返信 | 送信者・日時・対象問い合わせ |
| 担当者割当・変更 | 変更前後・操作者 |
| 優先度変更 | 変更前後・理由 |
| 状態変更 | 変更前後・操作者 |
| 解決 | 解決日時・操作者 |
| 再対応依頼 | 依頼者・日時・内容 |
| 再オープン | 理由・操作者・日時 |
| 再対応不要判断 | 判断者・日時・結果 |

問い合わせのメッセージ履歴と監査ログは区別する。

Workerには公開メッセージと必要な状態変更履歴のみ表示し、内部監査情報は公開しない。

メッセージ本文などの機微情報は、汎用監査ログに無制限に複製しない。

## **15\. エラー・競合状態**

## **6\. お知らせ更新通知**

今回の決定により、公開後の更新通知は重要な変更のみ送信する。

### **6.1 通知対象**

| 操作 | 通知 |
| ----- | ----- |
| 新規公開 | 原則送信 |
| 公開後の軽微な誤字修正 | 送信しない |
| 表現の微調整 | 原則送信しない |
| 勤務に影響する重要な変更 | 送信 |
| 必要な対応内容の変更 | 送信 |
| 重要な日時・場所の変更 | 送信 |
| アーカイブ | 原則送信しない |

### **6.2 重要な変更の判定**

自動的な文章差分だけで重要度を決めない。

Adminがお知らせを更新するときに、\*\*「対象Workerへ更新通知を送信する」\*\*という選択肢を設ける。

変更内容に応じてAdminが判断し、重要な変更では送信を選択する。

通知を送る場合は、変更内容の要約を入力させる。

更新通知の宛先は、公開時に確定した対象者スナップショットから決定する。公開後に新規登録されたWorkerへ自動拡大しない。

### **6.3 二重通知防止**

同じお知らせバージョン・同じWorker・同じ通知イベントに対して、重複通知を作成しない。

保存処理の再試行によって通知が複数件作成されないようにする。

## **9\. 通知の状態管理**

通知の状態は、原則として以下の2つとする。

未読

まだ開いていない

既読

開いた・既読操作済み

### **9.1 既読にするタイミング**

通知カードを選択した時点で、既読処理を実行する。

処理順序は次のとおり。

1. Workerが通知を選択する。  
2. 本人宛ての通知であることを検証する。  
3. 既読状態を保存する。  
4. 関連画面へ遷移する。

既読保存に失敗した場合は、成功したものとして確定表示せず、再試行可能にする。

関連画面が削除・アーカイブ・権限変更などで閲覧できなくても、通知を開いた事実は既読として保持する。

### **9.2 すべて既読**

「すべて既読」を押すと、本人の未読通知を一括で既読にする。

他Workerの通知は更新しない。

すでに既読の通知に対して再実行しても問題がない、冪等な処理とする。

一括処理が失敗した場合は、未読件数をサーバーから再取得する。

### **9.3 未読件数**

通知ベルには未読通知数を表示する。

| 件数 | 表示 |
| ----- | ----- |
| 0 | バッジなし |
| 1〜99 | 実件数 |
| 100以上 | `99+` |

未読件数は通知一覧と共通のデータを参照する。

別々のロジックで集計して件数が食い違うことを防ぐ。

## **11\. LINE連携**

LINEはOpsCueの補助通知チャネルとする。

業務イベント発生

OpsCue内通知を作成

アプリ内

本人の通知一覧

LINE

連携・配信条件を確認

### **11.1 LINE送信条件**

LINE配信は、以下をすべて満たす場合に行う。

* WorkerがLINEアカウントを連携済み。  
* 対象通知カテゴリのLINE配信が有効。  
* LINE配信に必要な連携状態が有効。  
* イベントがLINE配信対象。  
* 同一イベントの重複送信でない。

### **11.2 LINEの役割**

LINEには、通知の概要とOpsCueへのリンクを含める。

勤務の確定・変更・取消、前日確認、打刻、問い合わせ返信などの正式な操作はOpsCue内で行う。

LINEでメッセージを読んだだけでは、OpsCue内通知を既読にしない。

LINEからOpsCueの通知を開いた場合は、ログイン後に該当通知を開き、その時点で既読処理を行う。

### **11.3 配信失敗**

LINE配信に失敗しても、OpsCue内通知と業務イベントは保持する。

配信失敗をWorkerの勤務状態変更などに波及させない。

認証トークンやLINEの識別子を画面や通知本文に表示しない。

## **12\. 権限・セキュリティ**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 公開中のお知らせ閲覧 | 公開対象者のみ | 管理権限に従う |
| お知らせ作成 | 不可 | 権限保持者のみ |
| お知らせ編集 | 不可 | 権限保持者のみ |
| お知らせアーカイブ | 不可 | 権限保持者のみ |
| 本人宛て通知閲覧 | 可 | 管理権限に従う |
| 他Worker宛て通知閲覧 | 不可 | 原則不要、特別権限時のみ |
| 通知既読変更 | 本人のみ | 原則不可 |
| 通知イベント生成 | 不可 | 信頼されたサーバー処理 |
| LINE配信設定変更 | 本人のみ | 原則不可 |

### **必須のセキュリティ要件**

1. お知らせの閲覧権限は、公開対象スナップショットと現在の認証状態で判定する。  
2. 通知は宛先Worker IDで制限する。  
3. 既読更新は本人の通知にのみ許可する。  
4. 通知内の参照IDを変更しても、他Workerのデータを取得できない。  
5. 通知から遷移した先でも、独立して権限を再検証する。  
6. Admin内部メモや機密情報を通知本文に含めない。  
7. Workerに許可されていない管理画面のURLを通知リンクに使用しない。

## **16\. 実装順序**

Phase 1：既存実装の棚卸し（P0）

お知らせ、公開対象スナップショット、通知、既読、LINE連携のDB・RPC・RLS・画面を確認する。既存の契約を優先し、不必要なテーブルやRPCを増やさない。

Phase 2：お知らせ一覧・詳細（P0）

公開対象判定、一覧表示、詳細表示、アーカイブ非表示、更新表示を実装する。

Phase 3：通知基盤（P0）

通知イベント契約、宛先、参照先、重複防止、既読状態、未読件数を統一する。

Phase 4：通知一覧UI（P0）

すべて・未読タブ、通知カード、通知ベル、既読、一括既読、空状態を実装する。

Phase 5：各機能との連携（P0）

募集・勤務・前日確認・取消申請・サポート・お知らせのイベントと遷移先を接続する。

Phase 6：権限・監査・通知信頼性（P0）

RLS・RPC、公開対象、本人既読、重複イベント、失敗時再試行、監査を検証する。

Phase 7：LINE連携（P1）

### **2.2 カレンダーのルール**

* 1日に複数の時間帯を登録できる。  
* 複数状態がある日は複数マーカーを表示する。  
* 未登録日はマーカーなしとする。  
* 過去日は閲覧可能、追加・編集・削除不可。  
* 日跨ぎの登録は開始日と終了日の両方から確認できるようにする。  
* 色だけに依存せず、登録カードに状態名を表示する。  
* カレンダー上のマーカーは1日全体の可否を保証しない。

実装時には月境界と年境界を正しく扱う。表示する月に応じて年月を更新し、月末・閏年もカレンダー計算に反映する。

## **3\. 勤務可能時間の追加・編集フォーム**

| 項目 | 必須 | 仕様 |
| ----- | ----- | ----- |
| 開始日 | 必須 | 日付選択 |
| 開始時刻 | 必須 | 時刻選択 |
| 終了時刻 | 必須 | 時刻選択 |
| 翌日終了 | 必須の選択状態 | ONで終了日を翌日にする |
| 勤務可否 | 必須 | 3状態から選択 |
| 登録確認 | 必須 | 期間・状態を確認 |
| 保存 | 必須 | サーバー検証後に確定 |

時刻は日本時間 `Asia/Tokyo` で入力・表示する。保存時には、開始・終了の日時を曖昧さのない形式で保持する。

### **3.1 日跨ぎ**

例えば、10月24日22:00から10月25日06:00まで働ける場合。

開始日：10/24  
開始時刻：22:00  
終了時刻：06:00  
翌日終了：ON  
勤務可否：勤務可能

実際の登録期間  
10/24 22:00 ───────── 10/25 06:00

翌日終了OFFの場合は、終了時刻が開始時刻より後でなければ保存不可。

翌日終了ONの場合は、翌日の終了日時として解釈する。

終了日時は開始日時より後であることを必須とする。24時間以上の登録を許可するかは既存のAvailability契約に合わせ、初期仕様では1登録の期間を24時間以内に制限する。

### **3.2 過去日時の扱い**

現在時刻を基準として、開始日時が過去の登録は編集・削除不可とする。

登録期間が現在進行中の場合も、履歴整合性のためWorkerからの編集・削除は不可とする。

新規登録では、過去の開始日時を指定できない。

表示上のボタン非表示だけでなく、サーバー側でも制限する。

## **4\. 重複登録の禁止**

同じWorkerの勤務可能時間は、状態に関係なく重複を禁止する。

時間帯は `[開始日時, 終了日時)` の半開区間として扱う。

| 登録A | 登録B | 判定 |
| ----- | ----- | ----- |
| 09:00〜12:00 | 12:00〜18:00 | 許可 |
| 09:00〜15:00 | 13:00〜18:00 | 不可 |
| 22:00〜翌06:00 | 翌05:00〜09:00 | 不可 |
| 09:00〜18:00 | 09:00〜18:00 | 不可 |

重複は日付単位ではなく、実際の開始・終了日時で判定する。

同じ状態の時間帯でも重複登録は禁止する。

編集時は編集中のレコード自身を重複判定から除外する。

重複チェックはサーバー側で実施し、同時登録でも矛盾するレコードが作成されないようにする。

### **エラー表示**

> すでに登録されている時間帯と重複しています。登録内容を確認してください。

重複先の登録を閲覧できる場合は、その日時を表示して修正しやすくする。

# **5\. UNKNOWNと勤務可否判定**

勤務可能時間の判定は4種類に整理する。

| 判定 | 意味 |
| ----- | ----- |
| AVAILABLE | 対象時間帯全体が勤務可能 |
| CONSULT | 相談が必要な時間帯を含む |
| UNAVAILABLE | 勤務不可の時間帯を含む |
| UNKNOWN | 未登録の時間帯を含む |

### **5.1 判定優先順位**

1つの勤務時間帯に複数状態が含まれる場合、次の優先順位で代表判定する。

UNAVAILABLE → UNKNOWN → CONSULT → AVAILABLE

ただし、代表判定だけでは情報が失われるため、判定結果には各状態の該当区間も保持できる契約にする。

例えば、09:00〜18:00の勤務に対して、

| 登録 | 代表判定 |
| ----- | ----- |
| 09:00〜18:00 勤務可能 | AVAILABLE |
| 09:00〜12:00 勤務可能、12:00〜18:00 未登録 | UNKNOWN |
| 09:00〜12:00 勤務可能、12:00〜18:00 相談可能 | CONSULT |
| 09:00〜12:00 勤務可能、12:00〜18:00 勤務不可 | UNAVAILABLE |

### **5.2 勤務時間との照合**

勤務の開始・終了日時を対象区間とする。

集合時間や移動時間をAvailability判定に含める場合は、勤務開始時間との違いを明示し、Admin・Workerで共通の契約を使う。

WorkerのUI側で独自の判定式を作らず、サーバー側の共通判定結果を表示する。

# **6\. 応募・配置判定との関係**

Availabilityの状態と、実際の応募可否・配置可否は別概念とする。

| Availability | 応募・配置の扱い |
| ----- | ----- |
| AVAILABLE | 他条件を満たせば候補 |
| CONSULT | 要相談。自動確定しない |
| UNAVAILABLE | 原則不可 |
| UNKNOWN | 未確認。自動的に可能とは扱わない |

### **6.1 募集画面との整合**

既に確定した募集画面の仕様に従い、公開中の募集は、応募できない場合でも一覧に表示する。

応募できない場合は理由を表示する。

例：

* 勤務不可の時間帯が含まれています。  
* 勤務可能時間が未登録です。  
* 勤務可能時間の確認が必要です。  
* 必要な資格が確認されていません。

ただし、UNKNOWN・CONSULTを必ず応募禁止にするか、応募を受け付けてAdmin確認へ回すかは、既存の応募・配置契約との整合が必要。

本仕様では、UNKNOWN・CONSULTを自動的にAVAILABLEへ格上げしないことを確定し、最終的な応募受付ルールは共通のサーバー判定に委ねる。

これにより、Worker UIだけで応募可否を勝手に決定しない。

### **6.2 希望条件との関係**

希望条件は応募可否を直接制限しない。

例えば、希望曜日が土日でも、平日の募集は閲覧可能であり、希望曜日だけを理由に応募不可としない。

Admin側の配置候補検索では希望条件を絞り込みや参考情報に利用できるが、希望条件とAvailabilityを混同しない。

# **7\. 確定済み勤務との競合**

確定済み勤務と矛盾する勤務可能時間も、警告後に保存可能とする。

例として、10月25日09:00〜18:00に確定済み勤務がある場合、その時間帯を勤務不可として登録することもできる。

ただし、保存前に確認ダイアログを表示する。

## **確定済み勤務があります**

登録する時間帯に、確定済みの勤務が含まれています。

イベント運営スタッフ

10月25日 09:00〜18:00

勤務可能時間を変更しても、確定済みの勤務は取り消されません。勤務できなくなった場合は、勤務詳細から取消申請または管理者への連絡を行ってください。

戻って確認  
理解して保存  
警告ダイアログのイメージ。実際の勤務データや保存処理には接続していません。

### **保存時のルール**

* 競合する確定済み勤務をサーバーで再確認する。  
* 対象勤務の概要を表示する。  
* Workerの明示的な確認後に保存する。  
* 保存してもAssignment状態を変更しない。  
* 勤務取消申請を自動作成しない。  
* 勤務変更が必要な場合は勤務詳細へ案内する。  
* 警告を確認して保存した事実を監査に残す。

警告後に保存できることと、確定済み勤務から離脱できることは別である。

# **8\. 希望条件の最終UI**

希望条件は1ページのフォームとして設計する。

## **8.1 表示・入力項目**

| 項目 | 必須 | 仕様 |
| ----- | ----- | ----- |
| 希望曜日 | 任意 | 月〜日、複数選択 |
| 希望開始時刻 | 任意 | 時刻 |
| 希望終了時刻 | 任意 | 時刻 |
| 翌日終了 | 条件付き | 深夜帯の希望 |
| 希望エリア | 任意 | マスタから複数選択 |

| 交通手段 | 任意 | 既存選択肢に従う |
| 最終更新日時 | 自動 | 表示 |

### **8.2 入力ルール**

希望曜日、エリア、業務は未選択でも保存可能。

開始・終了時刻は両方入力するか、両方未設定とする。

希望時間帯の日跨ぎは、勤務可能時間と同様に翌日終了を明示する。

希望時間帯は日常的な希望なので、特定の日付と結びつけない。

希望条件をすべて未設定に戻すことも可能とする。

### **8.3 希望条件の保存**

Workerが「保存」を押すと、サーバー側で入力内容とマスタの有効性を検証する。

保存成功後は最新データを表示し、最終更新日時を更新する。

保存失敗時は入力内容を保持する。

別端末やAdminによって同時変更が発生した場合は、競合を検出して最新情報を再取得する。

# **3\. LINE認証・友だち追加フロー**

1. OpsCueで本人認証  
   ログイン済みWorkerのセッションを確認する。  
2. LINE連携を開始  
   サーバー側で一時的な連携要求を作成し、LINE認証へ遷移する。  
3. LINEで認証・同意  
   LINE Loginを利用して本人のLINEアカウントを認証する。  
4. 認証結果を検証  
   コールバックで認証コード、`state`、`nonce`など必要な値を検証する。  
5. LINEアカウントを紐付け  
   検証済みLINEユーザーIDとOpsCue Workerを安全に紐付ける。  
6. 公式アカウントの友だち状態を確認  
   友だち追加済みで、通知送信の前提条件を満たしているか確認する。  
7. LINE通知を有効化  
   認証・紐付け・友だち状態の条件を満たした場合のみ通知利用可能にする。

### **3.1 重要な区別**

次の3つは別々の状態として管理する。

| 状態 | 意味 |
| ----- | ----- |
| 認証成功 | LINEアカウント本人の認証が成功 |
| 紐付け成功 | OpsCue Workerとの対応が確定 |
| 通知利用可能 | 友だち状態などの送信条件を満たす |

LINE認証成功だけで通知利用可能と表示しない。

友だち追加待ちの場合は紐付けを保持できるが、LINE通知は送信しない。

LINE側の友だち状態を確認できない場合も、通知利用可能と推定しない。

なお、友だち追加済みであっても、ネットワーク障害やLINE側の制限により、個々のメッセージの到達まで保証できるわけではない。

# **4\. 連携状態の最終仕様**

| 内部状態 | Worker表示 | LINE送信 |
| ----- | ----- | ----- |
| `UNLINKED` | 未連携 | 不可 |
| `LINKING` | 連携処理中 | 不可 |
| `FRIEND_REQUIRED` | 友だち追加が必要 | 不可 |
| `ACTIVE` | LINE通知を利用できます | 可 |
| `UNAVAILABLE` | LINE通知を受信できません | 不可 |
| `RELINK_REQUIRED` | 再連携が必要 | 不可 |
| `UNLINKING` | 解除処理中 | 不可 |

連携失敗は別途エラー理由として保持する。

一時的な配信エラーが発生しただけで、即座に`UNAVAILABLE`や`RELINK_REQUIRED`へ遷移させない。

### **状態遷移**

UNLINKED  
   │ 連携開始  
   ▼  
LINKING  
   │  
   ├─ 認証失敗 ───────→ UNLINKED  
   │  
   ├─ 認証・紐付け成功  
   ▼  
FRIEND\_REQUIRED  
   │  
   ├─ 友だち追加確認 → ACTIVE  
   └─ 連携解除 ─────→ UNLINKED

ACTIVE  
   ├─ 受信不可を確認 → UNAVAILABLE  
   ├─ 再認証が必要 → RELINK\_REQUIRED  
   └─ 解除 → UNLINKING → UNLINKED

`UNAVAILABLE`から友だち状態などが再確認できれば`ACTIVE`へ戻せる。

`RELINK_REQUIRED`では認証を再実行する。

# **5\. LINE通知設定**

## **5.1 基本方針**

OpsCue内通知は常時有効。

Workerが変更できるのは、LINE通知のカテゴリ別ON/OFFのみ。

### **初期設定**

「重要カテゴリのみON」は次のように具体化する。

| カテゴリ | 初期設定 | 理由 |
| ----- | ----- | ----- |
| 応募結果 | ON | 応募結果の見落とし防止 |

| 前日確認 | ON | 確認期限の見落とし防止 |
| 勤務リマインダー | ON | 勤務忘れ防止 |

重要なお知らせを初期OFFとするのは、業務連絡を優先し、LINE通知の過剰配信を避けるため。

ただし、OpsCue内のお知らせ・通知は従来どおり利用できる。

### **設定の保存ルール**

* LINE未連携でも設定値は保持できる。  
* LINE通知をOFFにしてもOpsCue内通知は生成する。  
* LINE連携解除後も設定値は保持する。  
* 再連携時は保存済み設定を復元する。  
* 新しい通知カテゴリが追加された場合は、既定値を明示して管理する。  
* 保存失敗時は変更前の状態へ戻すか、再試行を案内する。  
* 同時更新があれば最新設定を再取得する。

重要カテゴリであっても、WorkerがLINE通知をOFFにすることは可能。

# **6\. LINE通知の対象イベント**

LINE通知はOpsCue内通知に紐付けて生成する。

| 業務イベント | LINEカテゴリ |
| ----- | ----- |
| 応募承認・不承認 | 応募結果 |
| 勤務確定・重要変更 | 勤務確定・変更 |
| 勤務取消申請の承認・却下 | 勤務確定・変更 |
| 前日確認依頼 | 前日確認 |
| 勤務開始前リマインダー | 勤務リマインダー |
| サポート返信・重要な状態変更 | サポート返信 |
| お知らせ公開・重要更新 | 重要なお知らせ |

SOSに関係するサポート返信は優先度の高いイベントとして扱うが、LINEの即時到達を保証しない。

SOSの安全確保や緊急対応をLINE通知の到達だけに依存させない。

お知らせの軽微な編集では通知を生成しない。

同じ業務結果から重複した通知が作成されないよう、イベントIDで冪等性を担保する。

# **7\. LINEメッセージの内容**

LINEには必要最小限の情報だけを送信する。

OpsCue

勤務が確定しました

新しい勤務が確定しました。日時や集合場所などの詳細をOpsCueで確認してください。

通知メッセージの構成例。実際のLINE画面ではありません。

### **メッセージのルール**

* タイトルは簡潔にする。  
* 個人情報や詳細な相談内容を含めない。  
* Admin内部メモを含めない。  
* 業務操作をLINE上で完了させない。  
* 詳細確認はOpsCueへのリンクを使用する。  
* リンク先では必ず認証・権限を再確認する。

通知に付けるリンクは、通知IDを基点にOpsCueへ遷移する方式を推奨する。

対象業務データへのアクセス権限が失われている場合は、適切な非公開・閲覧不可画面を表示する。

# **8\. LINE既読とOpsCue既読**

既読状態は完全に独立させる。

| 操作 | OpsCue通知の状態 |
| ----- | ----- |
| LINE通知を受信 | 変更なし |
| LINE通知を読む | 変更なし |
| LINE内のリンクを押す | 変更なし |
| OpsCueで通知を開く | 既読 |
| OpsCueで「すべて既読」 | 対象通知を既読 |

LINEのリンクを押しただけでは、OpsCue通知を既読にしない。

ログイン後に通知詳細を開き、通知の所有権確認と既読保存が成功した時点で既読とする。

また、通知が既読になっても、前日確認・打刻・取消申請・問い合わせ返信などの業務操作は完了しない。

# **9\. テスト通知**

## **9.1 利用条件**

連携状態が`ACTIVE`の場合のみ送信可能。

テスト通知はWorker本人がLINE通知を受信できるか確認するための機能。

### **UI**

テスト通知

LINEにテストメッセージを送信して、通知を受け取れるか確認できます。

テスト通知の内容

OpsCueのLINE通知テストです。メッセージが届いていれば、通知を受け取れる状態です。

テスト通知を送信するテスト通知のUI例。ボタンは仕様確認用で、実際のLINE送信は行いません。

### **9.2 送信制限**

乱用や不要な送信コストを防ぐため、次の制限を採用する。

| 項目 | 仕様 |
| ----- | ----- |
| 送信可能状態 | ACTIVEのみ |
| 連続送信 | 60秒以上の間隔 |
| 1日の上限 | 5回 |
| 送信先 | 連携中の本人LINEのみ |
| メッセージ内容 | 固定文 |
| OpsCue内通知 | 作成しない |
| 監査 | 送信要求・結果を記録 |

上限はサーバー側で強制する。

送信APIが成功しても、端末への実際の到達を保証しない。

| 結果 | Worker表示 |
| ----- | ----- |
| 送信要求受付 | テスト通知を送信しました |
| 一時的な失敗 | 送信できませんでした。時間をおいて再試行してください |
| 友だち状態に問題 | LINE公式アカウントの状態を確認してください |
| 上限超過 | 本日の送信上限に達しました |
| 未連携 | LINE連携が必要です |

UI上の「送信しました」は、送信処理が受け付けられたことを意味し、LINE端末への到達確認ではない。

# **10\. 配信失敗・再試行**

LINE配信はOpsCueの業務処理から分離する。

業務イベント  
    │  
    ▼  
OpsCue内通知作成  
    │  
    ▼  
LINE配信対象？  
    │  
    ├─ NO → 終了  
    ▼ YES  
LINE連携ACTIVE？  
    │  
    ├─ NO → 送信なし  
    ▼ YES  
カテゴリ設定ON？  
    │  
    ├─ NO → 送信なし  
    ▼ YES  
配信ジョブ作成  
    │  
    ▼  
送信直前に状態を再確認  
    │  
    ▼  
Messaging API送信  
    │  
    ├─ 成功 → 結果記録  
    └─ 失敗  
         ├─ 一時的 → 再試行  
         └─ 恒久的 → 停止・状態更新

### **配信ルール**

* 業務イベントとOpsCue内通知の作成を先に確定する。  
* LINE配信は非同期で実行する。  
* LINE送信失敗で勤務確定や問い合わせ返信をロールバックしない。  
* イベントIDと配信先で重複ジョブを防ぐ。  
* 送信直前に連携状態とカテゴリ設定を再確認する。  
* 解除済み・受信不可のアカウントには送信しない。  
* 一時的な失敗のみ、回数制限付きで再試行する。  
* 再試行が重複配信を生まないように設計する。

配信結果は、APIへの送信要求の成功・失敗と、実際の端末到達を区別する。

| OpsCue内通知 | 継続 |
| 勤務予定・履歴 | 維持 |

| 通知設定 | 保持 |
| LINE紐付け | 無効化 |
| 再連携 | 可能 |

解除処理はサーバー側で実行し、紐付け情報を無効化する。

送信待ちのLINE通知も、送信直前の再検証で停止する。

解除が失敗した場合は、実際の連携状態を再取得し、解除済みと誤表示しない。

# **12\. セキュリティ・権限**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 本人の連携状態閲覧 | 可 | 必要最小限 |
| LINE連携 | 本人のみ | 不可 |
| LINE解除 | 本人のみ | 原則不可 |
| LINE通知設定変更 | 本人のみ | 原則不可 |
| 他WorkerのLINE情報閲覧 | 不可 | 原則不可 |
| LINE通知送信 | 不可 | サーバー処理のみ |
| LINE認証情報取得 | 不可 | 不可 |
| テスト通知 | 本人のみ | 不可 |

### **必須の安全対策**

* OAuthの`state`と連携要求を紐付けて検証する。  
* IDトークンの署名、発行者、対象クライアント、期限、`nonce`を検証する。  
* 利用可能な認証方式に応じてPKCE等を採用する。  
* LINEユーザーIDをクライアント申告値だけで信用しない。  
* 同じLINEアカウントを複数Workerに同時紐付けしない。  
* チャネルシークレット・アクセストークンをブラウザへ公開しない。  
* Webhookを使用する場合は署名を検証する。  
* 認証コードやトークンをログに残さない。  
* 連携・解除・設定変更・テスト通知にレート制限を設ける。  
* 連携解除後に古い認証要求が再利用されないようにする。

LINE連携のアカウント紐付けと通知配信は、信頼されたサーバー処理で実施する。
