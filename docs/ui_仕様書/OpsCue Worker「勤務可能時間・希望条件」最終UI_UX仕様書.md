# **OpsCue Worker「勤務可能時間・希望条件」最終UI/UX仕様書**

| 項目 | 最終仕様 |
| ----- | ----- |
| 画面構成 | 勤務可能時間・希望条件は独立ページ |
| 勤務可能時間の重複 | 原則禁止 |
| 確定済み勤務との矛盾 | 警告後に保存可能 |
| 過去の勤務可能時間 | 閲覧のみ |
| 勤務可否 | 勤務可能・相談可能・勤務不可 |
| 未登録 | `UNKNOWN` として扱う |
| 日跨ぎ | 翌日終了を明示して登録 |
| 希望条件 | 参考情報。単独では応募不可にしない |
| 確定済み勤務 | Availability変更では自動取消ししない |
| 権限 | Workerは本人のデータのみ操作 |
| 監査 | 登録・編集・削除・判定に関わる重要操作を記録 |

最重要原則：勤務可能時間は「その日時の勤務可否」、希望条件は「普段の働き方の希望」であり、両者を同じ判定値として扱わない。

本書は設計上の確定仕様であり、既存DB・RPC・RLSへの実装適合性は別途確認する。

### **2.2 カレンダーのルール**

* 1日に複数の時間帯を登録できる。  
* 複数状態がある日は複数マーカーを表示する。  
* 未登録日はマーカーなしとする。  
* 過去日は閲覧可能、追加・編集・削除不可。  
* 日跨ぎの登録は開始日と終了日の両方から確認できるようにする。  
* 色だけに依存せず、登録カードに状態名を表示する。  
* カレンダー上のマーカーは1日全体の可否を保証しない。

実装時には月境界と年境界を正しく扱う。表示する月に応じて年月を更新し、月末・閏年もカレンダー計算に反映する。

## **3\. 勤務可能時間の追加・編集フォーム**

| 項目 | 必須 | 仕様 |
| ----- | ----- | ----- |
| 開始日 | 必須 | 日付選択 |
| 開始時刻 | 必須 | 時刻選択 |
| 終了時刻 | 必須 | 時刻選択 |
| 翌日終了 | 必須の選択状態 | ONで終了日を翌日にする |
| 勤務可否 | 必須 | 3状態から選択 |
| 登録確認 | 必須 | 期間・状態を確認 |
| 保存 | 必須 | サーバー検証後に確定 |

時刻は日本時間 `Asia/Tokyo` で入力・表示する。保存時には、開始・終了の日時を曖昧さのない形式で保持する。

### **3.1 日跨ぎ**

例えば、10月24日22:00から10月25日06:00まで働ける場合。

開始日：10/24  
開始時刻：22:00  
終了時刻：06:00  
翌日終了：ON  
勤務可否：勤務可能

実際の登録期間  
10/24 22:00 ───────── 10/25 06:00

翌日終了OFFの場合は、終了時刻が開始時刻より後でなければ保存不可。

翌日終了ONの場合は、翌日の終了日時として解釈する。

終了日時は開始日時より後であることを必須とする。24時間以上の登録を許可するかは既存のAvailability契約に合わせ、初期仕様では1登録の期間を24時間以内に制限する。

### **3.2 過去日時の扱い**

現在時刻を基準として、開始日時が過去の登録は編集・削除不可とする。

登録期間が現在進行中の場合も、履歴整合性のためWorkerからの編集・削除は不可とする。

新規登録では、過去の開始日時を指定できない。

表示上のボタン非表示だけでなく、サーバー側でも制限する。

## **4\. 重複登録の禁止**

同じWorkerの勤務可能時間は、状態に関係なく重複を禁止する。

時間帯は `[開始日時, 終了日時)` の半開区間として扱う。

| 登録A | 登録B | 判定 |
| ----- | ----- | ----- |
| 09:00〜12:00 | 12:00〜18:00 | 許可 |
| 09:00〜15:00 | 13:00〜18:00 | 不可 |
| 22:00〜翌06:00 | 翌05:00〜09:00 | 不可 |
| 09:00〜18:00 | 09:00〜18:00 | 不可 |

重複は日付単位ではなく、実際の開始・終了日時で判定する。

同じ状態の時間帯でも重複登録は禁止する。

編集時は編集中のレコード自身を重複判定から除外する。

重複チェックはサーバー側で実施し、同時登録でも矛盾するレコードが作成されないようにする。

### **エラー表示**

> すでに登録されている時間帯と重複しています。登録内容を確認してください。

重複先の登録を閲覧できる場合は、その日時を表示して修正しやすくする。

# **5\. UNKNOWNと勤務可否判定**

勤務可能時間の判定は4種類に整理する。

| 判定 | 意味 |
| ----- | ----- |
| AVAILABLE | 対象時間帯全体が勤務可能 |
| CONSULT | 相談が必要な時間帯を含む |
| UNAVAILABLE | 勤務不可の時間帯を含む |
| UNKNOWN | 未登録の時間帯を含む |

### **5.1 判定優先順位**

1つの勤務時間帯に複数状態が含まれる場合、次の優先順位で代表判定する。

UNAVAILABLE → UNKNOWN → CONSULT → AVAILABLE

ただし、代表判定だけでは情報が失われるため、判定結果には各状態の該当区間も保持できる契約にする。

例えば、09:00〜18:00の勤務に対して、

| 登録 | 代表判定 |
| ----- | ----- |
| 09:00〜18:00 勤務可能 | AVAILABLE |
| 09:00〜12:00 勤務可能、12:00〜18:00 未登録 | UNKNOWN |
| 09:00〜12:00 勤務可能、12:00〜18:00 相談可能 | CONSULT |
| 09:00〜12:00 勤務可能、12:00〜18:00 勤務不可 | UNAVAILABLE |

### **5.2 勤務時間との照合**

勤務の開始・終了日時を対象区間とする。

集合時間や移動時間をAvailability判定に含める場合は、勤務開始時間との違いを明示し、Admin・Workerで共通の契約を使う。

WorkerのUI側で独自の判定式を作らず、サーバー側の共通判定結果を表示する。

# **6\. 応募・配置判定との関係**

Availabilityの状態と、実際の応募可否・配置可否は別概念とする。

| Availability | 応募・配置の扱い |
| ----- | ----- |
| AVAILABLE | 他条件を満たせば候補 |
| CONSULT | 要相談。自動確定しない |
| UNAVAILABLE | 原則不可 |
| UNKNOWN | 未確認。自動的に可能とは扱わない |

### **6.1 募集画面との整合**

既に確定した募集画面の仕様に従い、公開中の募集は、応募できない場合でも一覧に表示する。

応募できない場合は理由を表示する。

例：

* 勤務不可の時間帯が含まれています。  
* 勤務可能時間が未登録です。  
* 勤務可能時間の確認が必要です。  
* 必要な資格が確認されていません。

ただし、UNKNOWN・CONSULTを必ず応募禁止にするか、応募を受け付けてAdmin確認へ回すかは、既存の応募・配置契約との整合が必要。

本仕様では、UNKNOWN・CONSULTを自動的にAVAILABLEへ格上げしないことを確定し、最終的な応募受付ルールは共通のサーバー判定に委ねる。

これにより、Worker UIだけで応募可否を勝手に決定しない。

### **6.2 希望条件との関係**

希望条件は応募可否を直接制限しない。

例えば、希望曜日が土日でも、平日の募集は閲覧可能であり、希望曜日だけを理由に応募不可としない。

Admin側の配置候補検索では希望条件を絞り込みや参考情報に利用できるが、希望条件とAvailabilityを混同しない。

# **7\. 確定済み勤務との競合**

確定済み勤務と矛盾する勤務可能時間も、警告後に保存可能とする。

例として、10月25日09:00〜18:00に確定済み勤務がある場合、その時間帯を勤務不可として登録することもできる。

ただし、保存前に確認ダイアログを表示する。

## **確定済み勤務があります**

登録する時間帯に、確定済みの勤務が含まれています。

イベント運営スタッフ

10月25日 09:00〜18:00

勤務可能時間を変更しても、確定済みの勤務は取り消されません。勤務できなくなった場合は、勤務詳細から取消申請または管理者への連絡を行ってください。

戻って確認  
理解して保存  
警告ダイアログのイメージ。実際の勤務データや保存処理には接続していません。

### **保存時のルール**

* 競合する確定済み勤務をサーバーで再確認する。  
* 対象勤務の概要を表示する。  
* Workerの明示的な確認後に保存する。  
* 保存してもAssignment状態を変更しない。  
* 勤務取消申請を自動作成しない。  
* 勤務変更が必要な場合は勤務詳細へ案内する。  
* 警告を確認して保存した事実を監査に残す。

警告後に保存できることと、確定済み勤務から離脱できることは別である。

# **8\. 希望条件の最終UI**

希望条件は1ページのフォームとして設計する。

## **8.1 表示・入力項目**

| 項目 | 必須 | 仕様 |
| ----- | ----- | ----- |
| 希望曜日 | 任意 | 月〜日、複数選択 |
| 希望開始時刻 | 任意 | 時刻 |
| 希望終了時刻 | 任意 | 時刻 |
| 翌日終了 | 条件付き | 深夜帯の希望 |
| 希望エリア | 任意 | マスタから複数選択 |
| 希望業務 | 任意 | マスタから複数選択 |
| 交通手段 | 任意 | 既存選択肢に従う |
| 最終更新日時 | 自動 | 表示 |

### **8.2 入力ルール**

希望曜日、エリア、業務は未選択でも保存可能。

開始・終了時刻は両方入力するか、両方未設定とする。

希望時間帯の日跨ぎは、勤務可能時間と同様に翌日終了を明示する。

希望時間帯は日常的な希望なので、特定の日付と結びつけない。

希望条件をすべて未設定に戻すことも可能とする。

### **8.3 希望条件の保存**

Workerが「保存」を押すと、サーバー側で入力内容とマスタの有効性を検証する。

保存成功後は最新データを表示し、最終更新日時を更新する。

保存失敗時は入力内容を保持する。

別端末やAdminによって同時変更が発生した場合は、競合を検出して最新情報を再取得する。

# **9\. 権限・認可**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 本人Availability閲覧 | 可 | 管理範囲内 |
| 本人Availability追加 | 可 | 権限に従う |
| 本人Availability編集 | 可、過去不可 | 権限に従う |
| 本人Availability削除 | 可、過去不可 | 権限に従う |
| 他WorkerのAvailability閲覧 | 不可 | 管理範囲内 |
| 他WorkerのAvailability変更 | 不可 | 権限に従う |
| 本人希望条件閲覧 | 可 | 管理範囲内 |
| 本人希望条件変更 | 可 | 権限に従う |
| 他Workerの希望条件変更 | 不可 | 権限に従う |

### **サーバー側の必須条件**

Worker IDをリクエストで差し替えても、他Workerの情報を取得・変更できないこと。

過去日時の変更禁止、重複登録禁止、日跨ぎ検証、競合勤務の再確認をサーバー側で実施すること。

Adminの権限は既存の拠点・担当範囲に従うこと。

RLSだけに依存せず、業務上の不変条件をDB制約または信頼されたサーバー処理で担保する。

# **10\. 監査・履歴**

| 操作 | 記録内容 |
| ----- | ----- |
| 勤務可能時間追加 | 操作者・対象・期間・状態 |
| 勤務可能時間編集 | 変更前後・日時 |
| 勤務可能時間削除 | 削除対象・日時 |
| 確定済み勤務との競合保存 | 警告対象・確認事実 |
| 希望条件更新 | 変更項目・変更前後 |
| 更新失敗 | エラー分類・対象 |
| Adminによる変更 | 管理者・対象・理由 |
| 権限違反 | 必要なセキュリティログ |

勤務可能時間の削除は、監査上の変更履歴を保持する。

過去データはWorker UIから編集できないようにし、監査履歴の整合性を維持する。

通常の保存成功時は画面内で完了表示を行い、毎回Workerへ通知を送らない。

Admin側も、希望条件が更新されるたびに通知する必要はない。

# **11\. エラー・例外処理**

| ケース | UI・処理 |
| ----- | ----- |
| 開始日時が過去 | 登録不可 |
| 終了日時が開始以前 | 保存不可 |

| 登録期間が上限超過 | 入力エラー |

| セッション切れ | 再ログイン |
| 通信失敗 | 入力内容保持・再試行 |

# **13\. 実装順序**

| Phase | 実装内容 | 優先度 |
| ----- | ----- | ----- |
| 1 | 既存Availability・Preferences・Assignment契約の棚卸し | P0 |
| 2 | 日跨ぎ・半開区間・重複禁止のデータ契約 | P0 |
| 3 | UNKNOWN・CONSULT等の共通判定契約 | P0 |
| 4 | Availabilityの認可・競合・監査 | P0 |
| 5 | 勤務可能時間カレンダー | P0 |
| 6 | 追加・編集・削除フォーム | P0 |
| 7 | 確定済み勤務との競合警告 | P0 |
| 8 | 希望条件フォーム | P0 |
| 9 | Preferencesの保存・認可・監査 | P0 |
| 10 | 募集・Admin配置との連携検証 | P0 |
| 11 | 日跨ぎ・過去日・同時更新のテスト | P0 |

実装はUIから先に作り込まず、Availabilityのサーバー契約と応募・配置判定の整合性を先に確認する。

特に、`UNKNOWN` と `CONSULT` を既存の応募RPCがどのように扱うかは、実装前の必須確認事項とする。
