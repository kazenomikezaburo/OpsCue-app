# **OpsCue Admin ホーム・要対応 UI/UX仕様書**

**Version:** 1.0  
**作成日:** 2026年10月22日  
**対象:** OpsCue Admin（管理者向けWebアプリ）  
**ステータス:** UI/UX設計案確定・実装前確認あり  
**関連文書:** OpsCue Admin 共通ナビゲーション UI/UX 最終仕様書 v1.0

---

## **1\. 目的・基本方針**

管理者が日々の業務状況を把握し、対応が必要な問題を迅速に発見・処理できる画面を構築する。

### **1.1 画面の役割**

**ホーム**

管理者が最初に開くダッシュボード。

本日の稼働状況、対応事項、現場状況を簡潔に確認できる。

**要対応**

管理者による判断や対応が必要な業務状態を集約する画面。

緊急度と重要度に基づいて対応事項を確認し、関連する業務画面へ移動できる。

### **1.2 設計原則**

* 既存のOpsCueの白・ライトグレー・青を基調としたデザインを維持する。  
* 必要な情報を優先順位順に配置する。  
* 同じ情報を複数画面で過剰に重複させない。  
* ホームは概要表示、要対応は詳細確認・処理導線に特化する。  
* 情報の取得元と業務状態を明確にする。  
* 実データがない場合も自然な空状態を表示する。  
* PC・タブレット・スマホのすべてで操作可能にする。  
* 既存のDB・RLS・RPC・業務ロジックは本仕様だけで変更しない。

## **2\. 共通レイアウト**

ヘッダー、サイドバー、通知、アカウントメニューは、既存の共通ナビゲーション最終仕様書に従う。

### **2.1 メインコンテンツ**

| 項目 | 推奨仕様 |
| ----- | ----- |
| 背景 | `#F9FAFB` |
| 最大幅 | 1440px |
| PC左右余白 | 32px |
| タブレット左右余白 | 24px |
| スマホ左右余白 | 16px |
| セクション間隔 | 32px |
| カード間隔 | 12〜16px |
| カード背景 | `#FFFFFF` |
| カード境界線 | `#E5E7EB` |
| カード角丸 | 12px |
| カード内部余白 | PC 20〜24px、スマホ16px |

最大幅・余白・角丸はメインコンテンツの新規提案値とし、全画面共通仕様に取り込む前に実機で確認する。

### **2.2 ページヘッダー**

基本構成：

1. ページタイトル  
2. ページの説明  
3. 必要な場合のみ右側に補助情報・操作

ホームと要対応では、同じページ名のパンくずを重複表示しない。

### **2.3 データ表示状態**

すべての主要セクションは次の状態を考慮する。

* 読み込み中  
* 正常表示  
* 0件・空状態  
* 取得エラー  
* 権限不足

読み込み中はSkeletonなどでレイアウトの大きな変動を防ぐ。

エラー時に0件として誤表示しない。

# **3\. ホーム画面**

## **3.1 目的**

本日の稼働状況と、管理者が確認すべき事項を一目で把握できるようにする。

ホームから各業務画面へ移動できるが、複雑な業務処理は原則として関連画面で実施する。

## **3.2 画面構成**

上から次の順序とする。

1. ページヘッダー  
2. 対応が必要  
3. 今日のサマリー  
4. 今日の現場

### **3.3 ページヘッダー**

**タイトル：** ホーム

**説明：** 今日の稼働状況と、いま対応が必要なことを確認できます。

日付を表示する場合は、業務上の基準日を明確にする。

## **3.4 対応が必要**

### **目的**

未解消の対応事項から、優先度の高いものをすぐ確認できるようにする。

### **表示内容**

* セクション名「対応が必要」  
* 未対応件数  
* 説明文  
* 「すべて確認」リンク  
* 対応事項の簡易一覧

### **一覧の表示項目**

* 種類  
* 件名  
* 対象現場または対象業務  
* 必要に応じて発生日時  
* 緊急度  
* 詳細への導線

### **表示件数**

最大5件。

優先度の高いものから表示する。

件数が5件を超える場合も、全件は要対応画面で確認する。

### **操作**

* 「すべて確認」から要対応画面へ移動する。  
* 各項目を選択すると、該当する業務画面または対応事項の詳細へ移動する。  
* ホーム上で業務状態を直接変更しない。

### **空状態**

「現在、対応が必要な項目はありません」

0件の場合は一覧を表示せず、空状態メッセージを表示する。

---

## **3.5 今日のサマリー**

### **目的**

本日の稼働状況を数値で把握する。

### **KPIカード**

既存の4項目を維持する。

| 指標 | 表示単位 | 意味 |
| ----- | ----- | ----- |
| 本日の稼働 | 名 | 本日の稼働予定スタッフ数 |
| 正常稼働 | 名 | 正常な稼働状態にあるスタッフ数 |
| 要確認 | 件 | 確認・対応が必要な勤務関連事項 |
| SOS | 件 | 未解消のSOS関連事項 |

### **KPI表示**

各カードには次を表示する。

* 指標名  
* 件数  
* 単位  
* 補足説明

既存の色分けを維持する。

ただし、色だけで正常・異常を判断させない。

### **操作**

対応する業務画面が存在する場合は、カードから関連画面へ移動できる。

クリック可能なカードとクリックできないカードは見た目で区別する。

### **集計上の注意**

* スタッフ数と勤務件数を混同しない。  
* 同じスタッフが複数シフトに入っている場合の数え方を確定する。  
* 正常稼働の判定条件を既存の勤怠・勤務状態と照合する。  
* SOSと要確認の重複集計を許すか明確にする。  
* 業務定義が未確定の指標は、既存の算出方法を勝手に変更しない。

---

## **3.6 今日の現場**

### **目的**

本日稼働予定の現場と配置状況を確認する。

### **表示項目**

各現場には次の情報を表示する。

* 現場名または案件名  
* 勤務日  
* 開始・終了時刻  
* 必要人数  
* 配置済み人数  
* 稼働状態  
* 要対応の有無

既存データから取得できない情報は無理に追加しない。

### **表示形式**

PCでは横長カードまたは簡潔な一覧。

タブレットでは情報を整理したカード。

スマホでは縦長カード。

### **並び順**

原則として勤務開始時刻順。

緊急対応が必要な現場は、状態を目立たせる。

### **操作**

現場を選択すると、該当するシフト運用画面へ移動する。

### **空状態**

「本日の勤務予定はありません」

### **表示件数**

ホームでは最大5〜10件を目安とし、すべての現場はシフト運用画面で確認する。

# **4\. 要対応画面**

## **4.1 目的**

管理者が対応すべき業務上の問題を一覧化し、優先順位を判断して関連業務へ移動できるようにする。

通知の未読一覧とは区別する。

## **4.2 画面構成**

1. ページヘッダー  
2. 対応状況サマリー  
3. フィルター  
4. 対応事項一覧  
5. 空状態・エラー状態

## **4.3 ページヘッダー**

**タイトル：** 要対応

**説明：** 判断や対応が必要な業務状態を、優先度順に確認します。

右側に未対応件数を表示する場合、一覧と同じ集計条件を使用する。

---

## **4.4 対応状況サマリー**

既存の4項目を維持する。

| 項目 | 主な対象 |
| ----- | ----- |
| 緊急 | SOSなど緊急性の高い問題 |
| 配置 | 人員不足・配置に関する問題 |
| 確認 | 勤怠・勤務などの確認事項 |
| 当日 | 本日対応が必要な事項 |

### **重要な集計ルール**

「緊急」「配置」「確認」は種類による分類であり、「当日」は期限・対象日による分類とする。

したがって、同じ対応事項が「緊急」と「当日」の両方に該当する場合がある。

4カードの合計を未対応総数として扱わない。

未対応総数は、重複を除いた対応事項数とする。

### **操作**

カードを選択すると、対応事項一覧の絞り込み条件が変わる。

選択中のカードは背景や枠線で区別する。

---

## **4.5 フィルター**

### **基本フィルター**

* 種類：すべて／緊急／配置／確認  
* 期間：すべて／今日／期限超過  
* 状態：未対応／対応済み

初期状態は「未対応」とする。

### **並び順**

初期表示は優先度順。

同じ優先度の場合は、期限や発生日時を考慮する。

### **検索**

将来的には現場名・案件名などで検索できる構成とする。

10/31向けの初期実装では必須としない。

---

## **4.6 対応事項一覧**

### **表示情報**

| 項目 | 内容 |
| ----- | ----- |
| 種類 | 緊急・配置・確認など |
| 件名 | 問題の概要 |
| 対象 | 現場・案件・シフトなど |
| 発生日時 | 問題を検出した日時 |
| 対応期限 | 存在する場合のみ |
| 状態 | 未対応・対応済みなど |
| 操作 | 詳細・対応 |

### **表示方式**

PCでは一覧テーブルまたは横長カード。

タブレットでは簡略化した一覧。

スマホでは縦カードを使用する。

### **詳細操作**

「詳細・対応」を選択すると、関連する業務画面へ移動する。

例：

* SOS：関連するヘルプリクエストまたは対応画面  
* 配置不足：該当シフトの配置画面  
* 勤怠確認：該当する勤怠記録

遷移先が未実装の場合、動作しないボタンを設置しない。

---

## **4.7 対応事項の解消**

### **原則**

対応事項は、元となる業務状態から導出する。

対応が必要な原因が解消された場合、一覧から自動的に除外する。

### **禁止事項**

* 通知を既読にしただけで対応済みにしない。  
* 表示上のボタンだけで業務問題を解消した扱いにしない。  
* 未解決のSOSや配置不足を、単純な一覧操作で非表示にしない。

### **対応済み表示**

対応済みの履歴を表示する場合は、既存データから状態を確認できるものに限定する。

履歴取得機能が未実装の場合、10/31向けデモでは対応済みタブを省略してよい。

---

## **4.8 空状態**

未対応事項がない場合：

**「現在、要対応はありません」**

補足：

「対象期間の業務状態に対応が必要な項目はありません。」

フィルター結果が0件の場合：

「条件に一致する対応事項はありません。」

データ取得エラーの場合：

「対応事項を取得できませんでした。」

取得エラーを0件として表示しない。

---

# **5\. レスポンシブ対応**

共通ナビゲーションの1024px切り替え条件は維持する。

メインコンテンツ内のカード・一覧は、表示可能な幅に応じて再配置する。

## **5.1 PC**

対象目安：1024px以上。

* KPIカードは横4列を基本とする。  
* 対応事項は横長一覧またはテーブル。  
* 今日の現場は横長カード。  
* フィルターは横並び。  
* コンテンツの最大幅を設ける。

サイドバー展開時にカードが窮屈になる場合は、本文の幅を基準に2列へ切り替える。

## **5.2 タブレット**

対象目安：768〜1023px。

* KPIカードは2列。  
* 対応事項は簡略化した一覧またはカード。  
* フィルターは折り返しを許可する。  
* 長い情報は複数行表示する。  
* サイドバーは共通仕様に従いドロワーとする。

## **5.3 スマホ**

対象目安：767px以下。

* KPIカードは原則1列。幅に余裕があれば2列も可。  
* 対応事項は縦カード。  
* 現場情報は重要度順に縦配置。  
* フィルターはコンパクトにまとめる。  
* 主要操作は見つけやすい位置に置く。  
* 水平方向のページスクロールを発生させない。  
* タッチ対象は原則44px程度を確保する。

## **5.4 検証対象幅**

* 1440px：PC  
* 1024px：切り替え境界  
* 768px：タブレット  
* 390px：一般的なスマホ  
* 320px：狭いスマホ

# **6\. 共通UIコンポーネント**

今回の2画面では次のコンポーネントを共通化する。

| コンポーネント | 用途 |
| ----- | ----- |
| PageHeader | ページタイトル・説明 |
| SectionHeader | セクション見出し・補助リンク |
| SummaryCard | KPI・件数表示 |
| AttentionItem | 対応事項の表示 |
| StatusBadge | 状態・緊急度の表示 |
| EmptyState | 0件・該当なし |
| ErrorState | 取得失敗 |
| LoadingSkeleton | 読み込み中 |
| FilterControls | 一覧の絞り込み |
| SiteSummaryCard | 現場概要 |

既存の共通コンポーネントがある場合は再利用を優先し、重複した実装を避ける。

# **7\. データ・権限・安全性**

* 既存の認証・認可を維持する。  
* 画面上の非表示だけで権限制御を実現した扱いにしない。  
* BackendのRLS・RPC・業務状態を変更しない。  
* 権限のない情報を表示しない。  
* 件数と一覧の集計条件を一致させる。  
* 取得エラー時に正常な0件として表示しない。  
* 個人情報や秘密情報を合成デモデータへ含めない。

# **8\. 10/31向け実装範囲**

## **8.1 優先実装**

* ホームの3セクション  
* 今日のサマリー4指標  
* 対応事項の簡易一覧  
* 要対応の4集計カード  
* 種類別フィルター  
* 対応事項一覧  
* 既存の関連画面への遷移  
* 空状態・エラー状態  
* PC・スマホの主要レイアウト

## **8.2 後続実装**

* 高度な検索  
* 複数条件の保存  
* 対応履歴の高度な表示  
* リアルタイム更新  
* 詳細な監査履歴  
* 新規Backend集計API  
* 未実装の業務処理

## **8.3 デモデータ**

実データ接続が難しい場合は、合成fixtureを利用する。

デモでは次の2状態を用意する。

1. 0件の正常な空状態  
2. SOS・配置不足・勤怠確認が存在する状態

合成データであることを明示し、実際にDBへ書き込んだかのような誤表示を避ける。

# **9\. 完了条件**

* 共通ナビゲーション仕様と矛盾しない。  
* ホームと要対応の役割が明確に分かれている。  
* KPIカードの表示が既存仕様と整合する。  
* 対応事項の優先順位が分かる。  
* 関連業務画面への遷移が正しい。  
* 0件・正常・エラー状態を区別できる。  
* PC・タブレット・スマホで表示が崩れない。  
* 既存の業務処理・認証・権限に回帰不具合がない。  
* デモの合成データと実データを混同しない。

# **10\. 実装前に確認する事項**

次の項目は、既存実装・Backend契約との照合が必要。

1. KPI4項目の正確な集計定義  
2. 対応事項の種類・優先度・重複除外ルール  
3. 対応事項の発生・解消条件  
4. ホームの現場一覧に使用するデータ  
5. 各対応事項の詳細遷移先  
6. 既存の権限による表示範囲  
7. 既存コンポーネントの再利用可否

これらが未確定の場合、実データ連携部分を保留し、合成データによるUI実装を先行する。
