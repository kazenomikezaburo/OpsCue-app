## 2. 10/31 UIデモのスコープ

### 2.1 必須のユーザー体験

```text
募集一覧（案件単位）
  → JST勤務開始日で絞り込み
  → 案件詳細
  → 応募可能なシフトを1〜10件選択
  → 応募確認Bottom Sheet
  → 合成された応募結果の表示例（受付／全体拒否／結果不明）
```

- 案件は `projectId` / `projects.id` 単位で扱い、**同名案件をまとめない**。
- 日付判定は **Asia/Tokyoでの勤務開始日**。日付境界のサンプルを用意する。
- 選択対象は**同一案件・重複しないシフトID・1〜10件**。11件目は選択不可、解除は可能。
- `blockingReasons[]` があるシフトは選択不可。`warnings[]` は原則選択可能のまま注意を表示。
- 未確定応募同士の時間重複は警告 `OVERLAPS_OWN_PENDING_APPLICATION` であり、それだけで選択を禁止しない。
- 既応募などの拒否条件を含む一括応募は**全件失敗**。部分成功を表示しない。
- 不明な報酬は「未設定」「要確認」等とし、`null` を0円と表示しない。
- `isDemo` 等の表示に加え、**「合成データ／実際の応募は送信されません」**を明示する。
- Worker共通Shell・既存ルート・Auth・DB・実Server Actionへの接続はこのデモ追加作業の範囲外。

### 2.2 デモで扱う状態

| 種類 | 表示の方針 |
|---|---|
| 応募受付の表示例 | 「応募受付（デモ・未送信）」 |
| 全体拒否の表示例 | 原因シフトと理由を示し、新規応募は0件 |
| `validation_error` | 入力・選択内容の不正として表示 |
| `unavailable` | 対象が利用不可／権限等の状況を推測で断定しない |
| `unknown` | 結果不明として扱い、**成功・失敗と断定しない** |
| `idempotency_conflict` | 同じキーの別要求を拒否する契約候補。実API未接続なら表示例に限定 |

**注意:** Backend共有の「success/failure/validation_error/unavailable/unknown」と、10/20手順書の`resolved`内の`accepted/rejected`は階層が異なる可能性がある。DTO上の正規の名称・ネストを照合するまで独自に一本化しない。

## 4. PR-UI-01 Phase 2（PM条件付き承認済み）

### 4.1 対象2ファイル

```text

```

**許可された目的:** 既存UIのProps/callback接続、応募可能な合成データ追加、TypeScript fixtureによるデモ用表示。新しい実API呼び出し・ルート追加・共通Shell変更ではない。

### 4.2 実装上の条件

1. **fixtureは1か所を正本**とし、コンポーネントに別の巨大なハードコードデータを重複させない。
2. `recruitment-demo.tsx` は既存UIの公開Props・callbackを接続する薄い統合層とする。API、Auth、DB、LINE、既存応募Actionをimportしない。
3. 合成データは実在する氏名・電話番号・顧客情報・鍵を使わない。
4. `blockingReasons`と`warnings`を分け、以下の区別を維持する。
   - `WITHDRAWN_REAPPLY_NOT_ALLOWED`（取下げ後の再応募不可）
   - `PREVIOUS_APPLICATION_REJECTED`（却下後の再応募不可）
   - `OVERLAPS_OWN_PENDING_APPLICATION`（未確定応募との重複警告）
   - `AVAILABILITY_NOT_CONFIRMED`（勤務可否が未登録・要相談等の警告）
5. 応募結果は**全件成功／全件失敗**。結果不明のときのみ照会・再送対象となる契約を表示例として守る。実際の再送・照会は実装しない。
6. `batchKey` は実API用の冪等性契約であり、デモ中に永続保存や実RPC照会を追加しない。
7. Phase 1の14ファイルのうち、上記fixture以外は今回編集しない。予期しない変更が必要なら停止してPMに申請。
8. **今回の承認に含まれない:** テスト・lint・型チェック・ビルド・プレビュー起動・ブラウザ確認・push・PRマージ・既存ルート変更・Worker Shell・`proxy.ts`・DB/Auth/クラウド。

- ブランチ名、HEAD、変更前後のGit状態。
- 2ファイルの差分要約と対象外ファイル変更がない証拠。

## 9. Git・変更範囲・テスト・プレビューの安全ゲート

### 9.1 作業前の読み取り確認例

```powershell
git status --short
git branch --show-current
git rev-parse HEAD
git diff --name-only
git diff --cached --name-only
```

- 既存の未コミット差分・他担当の変更を保全する。

- 新規依存、設定、共有CSS、ルート、`proxy.ts`、DB/Authに触れる必要があれば停止して変更申請。
- Phase 2で承認されたファイル外の変更は別承認。commit済みの既存14ファイルを「新規のみ」と誤認しない。

### 9.2 次の承認申請に必要な情報
