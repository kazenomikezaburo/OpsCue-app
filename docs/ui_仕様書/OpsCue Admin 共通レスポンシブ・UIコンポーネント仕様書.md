**Version:** 1.0

# **1\. 目的**

OpsCue Adminの各画面で、デザイン・操作方法・レスポンシブ対応を統一する。

本仕様書では、共通ナビゲーション以外のメインコンテンツ領域について、以下を定義する。

* PC・タブレット・スマートフォンの表示ルール  
* レイアウト・余白・タイポグラフィ  
* カラー・状態表示  
* ボタン・カード・テーブル・フォーム  
* フィルター・検索・ページネーション  
* モーダル・ドロワー・通知  
* 読み込み・空状態・エラー  
* アクセシビリティ  
* 実装優先順位・検証基準

## **1.1 関連仕様**

1. Admin 共通ナビゲーション UI/UX 最終仕様書 v1.0  
2. Admin ホーム・要対応 UI/UX仕様書 v1.0  
3. 各業務画面の個別UI/UX仕様書

## **1.2 仕様の優先順位**

共通ナビゲーションについては、既存の最終仕様書を優先する。

業務データ・権限・状態遷移については、既存のBackend・業務仕様を優先する。

本仕様書は画面表示と操作の共通ルールを定義するものであり、既存のDB・RLS・RPC・API契約を変更しない。

# **2\. デザイン原則**

## **2.1 基本方針**

OpsCueは、管理者が日々の業務を正確かつ効率的に処理するための業務アプリケーションである。

そのため、装飾性よりも以下を優先する。

1. 情報の見つけやすさ  
2. 操作の分かりやすさ  
3. 状態の判別しやすさ  
4. 入力ミス・誤操作の防止  
5. 画面間の一貫性  
6. さまざまな画面幅での操作性

## **2.2 UIの方向性**

* 白とライトグレーを基調とした落ち着いたデザイン  
* 青を主要操作・選択状態に使用  
* 緊急度の高い情報は赤やオレンジで区別  
* カードと余白による情報のグルーピング  
* 過度な影・グラデーション・アニメーションを避ける  
* アイコンと文字を組み合わせて意味を伝える

## **2.3 画面の基本構造**

各画面は原則として次の順序で構成する。

1. ページヘッダー  
2. 主要操作・検索・フィルター  
3. サマリー・集計情報（必要な画面のみ）  
4. メインコンテンツ  
5. 補助情報・ページネーション

画面ごとに不要な要素は省略できる。

# **3\. レスポンシブ設計**

## **3.1 ブレークポイント**

| 区分 | 画面幅 | 基本方針 |
| ----- | ----- | ----- |
| スマートフォン | 〜767px | 1列中心・タッチ操作 |
| タブレット | 768〜1023px | 1〜2列・ドロワーナビ |
| PC | 1024px〜 | 複数列・一覧表示 |

1024px未満では、既存の共通ナビゲーション仕様に従ってサイドバーをドロワー表示とする。

ただし、本文の列数は画面幅だけでなく、実際に利用可能なコンテンツ幅で決定する。

## **3.2 コンテンツ領域**

| 項目 | PC | タブレット | スマホ |
| ----- | ----- | ----- | ----- |
| 左右余白 | 32px | 24px | 16px |
| セクション間隔 | 32px | 24px | 24px |
| カード間隔 | 16px | 12〜16px | 12px |
| カード内余白 | 20〜24px | 20px | 16px |
| 基本列数 | 2〜4列 | 1〜2列 | 1列 |

メインコンテンツの推奨最大幅は1440pxとする。

ただし、シフト管理や大規模テーブルなど情報密度の高い画面では、必要に応じてより広い表示を許可する。

## **3.3 スマートフォン対応**

スマートフォンでは次を守る。

* ページ全体の横スクロールを発生させない。  
* 重要情報を上部に配置する。  
* 主要操作を見つけやすい位置に配置する。  
* 複数列テーブルを無理に縮小しない。  
* 長いラベルは折り返し、または省略表示する。  
* タッチ操作の対象サイズは原則44×44px以上とする。  
* ホバー操作だけに依存しない。  
* 入力時にキーボードで重要操作が隠れないようにする。

## **3.4 タブレット対応**

タブレットは単純なPC縮小版にしない。

* KPIカードは2列を基本とする。  
* フィルターは折り返しを許可する。  
* テーブルは重要列を優先する。  
* 横幅が足りない場合はカード表示に切り替える。  
* タッチ操作を前提とした間隔を確保する。

## **3.5 PC対応**

* 利用可能な横幅を効率的に使用する。  
* KPIカードは原則4列。  
* テーブルは必要な列を表示する。  
* 複数の操作を横並びに配置できる。  
* 詳細情報は必要に応じて右側パネルを利用できる。

既存のOpsCueのカラーを基本とする。

| Primary | `#2563EB` |
| Primary Hover | `#1D4ED8` |
| Primary Light | `#EAF2FF` |
| Main Background | `#F9FAFB` |
| Surface | `#FFFFFF` |
| Sidebar Background | `#F8FAFC` |

| Danger | `#B91C1C` |
| Info | `#1D4ED8` |

状態色は単独で意味を表さず、ラベルやアイコンを併用する。

文字色と背景色の組み合わせは、必要なコントラスト比を満たすように調整する。

## **4.2 タイポグラフィ**

日本語・英数字を自然に表示できるシステムフォントを使用する。

推奨フォント：

`Inter, Noto Sans JP, system-ui, sans-serif`

| 用途 | PC | スマホ | 太さ |
| ----- | ----- | ----- | ----- |
| ページタイトル | 24px | 24px | 700 |
| セクションタイトル | 18〜20px | 18px | 600 |
| カードタイトル | 16px | 16px | 600 |
| 本文 | 14px | 14px | 400 |
| 補足文 | 12〜13px | 12〜13px | 400 |
| KPI数値 | 28〜32px | 28px | 600〜700 |
| ボタン | 14px | 14px | 500〜600 |

本文の行間は1.5程度を基本とする。

数値の一覧では桁位置がそろうようにする。

## **4.3 余白スケール**

基本スケール：

`4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48px`

原則としてこのスケールを使用し、画面ごとに独自の余白値を乱立させない。

## **4.4 角丸**

| 要素 | 推奨値 |
| ----- | ----- |
| 小さな入力・バッジ | 6px |
| ボタン・入力欄 | 8px |
| カード | 12px |
| モーダル | 12〜16px |
| 丸型アイコン | 9999px |

## **4.5 境界線・影**

* 通常のカードは1pxの境界線を基本とする。  
* 影はドロワー・ポップオーバー・モーダルなどに限定する。  
* 境界線と影を過度に重ねない。

# **5\. 共通UIコンポーネント**

## **5.1 PageHeader**

ページ上部のタイトル・説明・主要操作を表示する。

### **構成**

* ページタイトル  
* 補足説明  
* 主要操作（必要な場合）

### **レスポンシブ**

PC：タイトルと操作を横並びにできる。

スマホ：タイトルと説明の下に操作を配置する。

ページ名だけの重複したパンくずは原則省略する。

---

## **5.2 Button**

### **種類**

| 種類 | 用途 |
| ----- | ----- |
| Primary | 保存・作成・確定 |
| Secondary | 補助操作 |
| Outline | 詳細・フィルターなど |
| Ghost | 軽量な操作 |
| Destructive | 削除・取消など |

### **サイズ**

| サイズ | 高さ |
| ----- | ----- |
| Small | 32px |
| Medium | 40px |
| Large | 44px |

スマホの主要操作は原則44px以上とする。

### **状態**

* Default  
* Hover  
* Focus  
* Active  
* Disabled  
* Loading

送信中は二重送信を防止する。

破壊的操作は通常操作と視覚的に区別する。

---

## **5.3 SummaryCard / KPICard**

集計値や重要な状態を表示する。

### **構成**

* 指標名  
* 数値  
* 単位  
* 補足説明  
* 必要に応じてアイコン

### **レイアウト**

PC：原則4列。

タブレット：2列。

スマホ：原則1列。情報量が少なく幅に余裕がある場合は2列も許可する。

### **操作**

クリック可能な場合は、ホバー・フォーカス・カーソルなどで区別する。

単なる集計表示の場合はクリックできるように見せない。

---

## **5.4 StatusBadge**

状態を簡潔に表示する。

### **用途**

* 募集中  
* 募集終了  
* 配置済み  
* 稼働中  
* 要確認  
* 緊急  
* 完了

### **ルール**

* 状態名を明示する。  
* 色だけで意味を伝えない。  
* 同じ状態には同じ色を使用する。  
* 業務状態と緊急度を混同しない。  
* 状態名は既存のBackend契約に合わせる。

---

## **5.5 DataTable**

案件・スタッフ・勤怠などの一覧に使用する。

### **PC**

* 列見出しを表示する。  
* 行単位の選択・操作を可能にする。  
* 重要な情報を左側に配置する。  
* 行の操作ボタンは原則右側に配置する。  
* 必要に応じてソート・ページネーションを設ける。

### **タブレット**

* 重要な列を優先する。  
* 補足情報は省略または詳細表示へ移動する。  
* 情報量に応じてカードへ切り替える。

### **スマホ**

* 原則カード一覧へ切り替える。  
* 重要な項目をカード上部に配置する。  
* 操作をカード下部などにまとめる。  
* 横スクロールテーブルは、業務上必要な場合に限る。

### **共通**

* 行全体がクリック可能か明確にする。  
* ソート状態を表示する。  
* 空状態・読み込み・エラーに対応する。  
* 権限のない操作を表示しない。  
* 大量データはページネーションなどで制御する。

---

## **5.6 ListCard**

スマホやタブレットでの業務一覧に使用する。

### **構成**

1. タイトル  
2. ステータス  
3. 主要情報  
4. 補足情報  
5. 操作

表示順序は業務ごとに定義する。

すべての項目を無理に表示せず、詳細画面への導線を用意する。

---

## **5.7 SearchField**

検索対象がある一覧画面で使用する。

### **仕様**

* 検索アイコンを表示する。  
* プレースホルダーで検索対象を示す。  
* 入力内容を消去できる。  
* 検索結果が0件の場合は専用の空状態を表示する。

入力中の自動検索を採用する場合は、不要な通信を抑制する。

---

## **5.8 FilterControls**

一覧の絞り込みに使用する。

### **PC**

検索・主要フィルター・補助操作を横並びにする。

### **タブレット**

横並びを基本とし、必要に応じて折り返す。

### **スマホ**

主要フィルターのみ表示し、詳細条件はSheetや折りたたみ領域に格納する。

### **共通ルール**

* 現在の条件を確認できる。  
* フィルター解除手段を用意する。  
* 適用中の条件を分かりやすく表示する。  
* 件数が変化する場合は一覧と整合させる。

---

## **5.9 FormField**

### **対象**

* TextInput  
* Textarea  
* Select  
* DatePicker  
* TimeInput  
* Checkbox  
* Radio  
* Switch

### **共通構成**

* ラベル  
* 入力欄  
* 補足説明  
* エラーメッセージ

### **ルール**

* プレースホルダーをラベルの代わりにしない。  
* 必須項目を明示する。  
* 入力エラーは対象項目の近くに表示する。  
* エラー理由と修正方法を伝える。  
* 送信失敗時に入力内容を失わない。  
* 日付・時刻・人数などの単位を明確にする。  
* 数値入力では範囲・形式を検証する。

### **レスポンシブ**

PC：関連する項目を2列にできる。

スマホ：原則1列。

---

## **5.10 Modal / Dialog**

重要な確認・短い入力に使用する。

### **PC**

中央表示。

### **タブレット**

画面幅に応じた中央表示。

### **スマホ**

内容に応じて全画面または画面内に収まるダイアログとする。

### **共通**

* タイトルを表示する。  
* 閉じる方法を用意する。  
* 背景操作を防止する。  
* フォーカスを適切に管理する。  
* 破壊的操作では対象と影響を明示する。

重要な保存処理中に誤って閉じないようにする。

---

## **5.11 Sheet / Drawer**

フィルター・補助情報・詳細表示に使用する。

### **PC**

右側から表示するパネルを基本とする。

### **スマホ**

画面下部または全画面表示を選択する。

### **ルール**

* 開閉状態を明確にする。  
* 閉じる操作を用意する。  
* 背景スクロールを必要に応じて制御する。  
* 長い内容は内部スクロール可能にする。

共通ナビゲーションのドロワー仕様とは独立して扱い、表示の競合を避ける。

---

## **5.12 Tabs**

同一業務内の情報切り替えに使用する。

* 選択中のタブを明確にする。  
* タブ名は短くする。  
* スマホでは必要に応じてタブ領域のみ横スクロールを許可する。  
* タブ変更によって未保存データが失われる場合は警告する。

---

## **5.13 Toast / Feedback**

操作結果を利用者へ通知する。

### **種類**

* Success  
* Error  
* Warning  
* Info

### **ルール**

* 成功・失敗を簡潔に伝える。  
* エラー時は必要に応じて再試行方法を示す。  
* 重要なエラーをToastだけで済ませない。  
* 画面上の操作結果と表示内容を一致させる。

Toastの表示位置・時間は既存の実装と整合させる。

---

## **5.14 EmptyState**

### **種類**

**データなし**

例：「登録されている案件はありません」

**検索結果なし**

例：「条件に一致する案件はありません」

**対応事項なし**

例：「現在、要対応はありません」

**権限なし**

例：「この情報を表示する権限がありません」

### **ルール**

* 何がないのかを明確にする。  
* 必要な場合のみ次の操作を提示する。  
* エラーを空状態として表示しない。

---

## **5.15 Loading / Error**

### **Loading**

* Skeletonを基本とする。  
* レイアウトの大きな変動を防ぐ。  
* 保存処理中は重複送信を防止する。

### **Error**

* 原因が分かる範囲で説明する。  
* 再試行可能な場合は再試行ボタンを用意する。  
* 入力済みの内容を保持する。  
* 認証・権限エラーと通信エラーを区別する。

---

# **6\. 操作・状態管理**

## **6.1 共通状態**

各操作コンポーネントは必要に応じて以下の状態を持つ。

* Default  
* Hover  
* Focus  
* Active  
* Selected  
* Disabled  
* Loading  
* Error

## **6.2 操作の一貫性**

* 同じ種類の操作には同じラベルを使用する。  
* 保存と確定など、意味の異なる操作を混同しない。  
* 操作後の結果を明示する。  
* 取り消し可能な操作と不可逆な操作を区別する。

## **6.3 破壊的操作**

削除・取消・配置解除などは、既存の業務仕様に従う。

確認ダイアログを表示する場合は、対象と影響を具体的に示す。

画面上の確認だけでBackend側の権限制御を代替しない。

# **7\. アクセシビリティ**

## **7.1 基本方針**

WCAG 2.2 AAを目標とする。

### **主な基準**

* 本文のコントラスト比は原則4.5:1以上  
* 大きな文字は原則3:1以上  
* 色だけに依存しない状態表示  
* キーボード操作に対応  
* フォーカス位置を視認できる  
* フォームラベルを明確にする  
* エラー内容を文章で伝える  
* アイコンのみのボタンにはアクセシブルな名前を付ける  
* モーダルではフォーカス移動・復帰を管理する  
* 動きを減らす設定を尊重する

## **7.2 拡大表示**

* 200%拡大時にも主要操作を利用できること。  
* 狭い画面で文字が重ならないこと。  
* 固定高さによる文字の切れを避けること。

# **8\. 技術・実装方針**

## **8.1 想定技術**

既存のOpsCueの構成に合わせる。

* Next.js  
* TypeScript  
* Tailwind CSS  
* shadcn/ui  
* Lucide Icons

既存コンポーネントを優先して再利用する。

## **8.2 推奨コンポーネント構成**

共通UIの候補：

* PageHeader  
* SectionHeader  
* SummaryCard  
* StatusBadge  
* DataTable  
* ListCard  
* SearchField  
* FilterControls  
* FormField  
* ConfirmDialog  
* EmptyState  
* ErrorState  
* LoadingSkeleton

既存のディレクトリ構造を確認してから配置先を決める。

新規コンポーネントを作る前に、同等の実装が存在しないか確認する。

## **8.3 業務ロジックとの分離**

* 共通UIに業務固有の認可ロジックを直接埋め込まない。  
* 表示コンポーネントとデータ取得処理を分離する。  
* APIレスポンス型は既存契約を優先する。  
* モックデータは実データと区別できる構成にする。  
* 権限チェックをUIだけで完結させない。

# **10\. 品質確認**

## **10.1 表示確認**

以下の画面幅で検証する。

| 幅 | 用途 |

## **10.2 共通チェック**

* 横スクロールが発生しない。  
* 文字がカードやボタンからはみ出さない。  
* 主要操作が隠れない。  
* 選択状態が分かる。  
* タッチ操作が可能。  
* キーボード操作が可能。  
* 0件・読み込み・エラー状態が正しい。  
* 入力エラーが分かりやすい。  
* 不要な二重送信が起きない。  
* 既存ナビゲーションに影響しない。

## **10.3 変更時の確認**

共通コンポーネントを変更した場合は、そのコンポーネントを使用する主要画面を確認する。

特に、余白・文字サイズ・幅・高さ・色の変更は、複数画面への影響を確認する。

# **11\. 変更管理**

## **11.1 共通仕様の変更**

共通トークン・共通コンポーネントの仕様を変更する場合は、影響する画面を明記する。

## **11.2 個別画面の例外**

個別画面で共通仕様と異なるUIが必要な場合は、理由と適用範囲を個別仕様書に記録する。

## **11.3 既存仕様との整合**

本仕様書によって、既存の共通ナビゲーション最終仕様書を暗黙に変更しない。

---

# **12\. 完了条件**

次の条件を満たした場合、共通レスポンシブ・UIコンポーネントの実装を完了とする。

1. 主要コンポーネントが再利用可能である。  
2. PC・タブレット・スマホで操作できる。  
3. 共通デザイントークンが適用されている。  
4. 状態表示・エラー表示が統一されている。  
5. 主要操作がキーボード・タッチで利用できる。  
6. 既存のヘッダー・サイドバーに影響しない。  
7. 既存のBackend・権限・業務ロジックを変更していない。  
8. 対象画面で表示崩れや重大な操作不具合がない。

---

# **13\. 実装前の確認事項**

* 既存のTailwind設定とデザイントークン  
* shadcn/uiの導入状況と既存コンポーネント  
* 既存画面の共通UI利用状況  
* フォントの読み込み方法  
* モーダル・Toast・テーブルの既存実装  
* 画面ごとのデータ量とレスポンシブ要件

未確認事項については、既存実装を調査してから適用する。
