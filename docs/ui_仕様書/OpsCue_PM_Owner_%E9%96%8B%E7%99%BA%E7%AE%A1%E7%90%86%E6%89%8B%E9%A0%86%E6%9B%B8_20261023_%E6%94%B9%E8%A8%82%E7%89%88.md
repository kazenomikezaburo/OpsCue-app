### 2.1 直近の確定ルール

- 募集は案件ID `projects.id` で識別。日付は **Asia/Tokyoの勤務開始日**。
- 一括応募は同一案件の重複しない**1〜10シフト**。全件成功または0件、部分成功なし。
- `unknown` は結果不明。成功・失敗を断定せず、同じbatchKeyで照会・必要時再送。
- `WITHDRAWN_REAPPLY_NOT_ALLOWED` と `PREVIOUS_APPLICATION_REJECTED` は別の応募不可理由。
- `OVERLAPS_OWN_PENDING_APPLICATION` と `AVAILABILITY_NOT_CONFIRMED` は非ブロック警告。
- PR-05は審査をRPC化し、承認警告は2段階確認。取消済みシフト・無効Workerの承認は拒否。
- 警告の内容が変わったら再確認が必要。確認対象の版・ハッシュと冪等キーの整合は**未完了の設計課題**。
- P0-4は **W1（応募警告付き可）＋R1（審査確認後可）＋A2（配置確認後可）＋K1（receipt記録）**。`UNAVAILABLE`は拒否、部分登録はUNKNOWN扱い。11月実装予定。
- 応募結果通知の追加実装はP1以降。LINE送信は10/31デモの前提にしない。

## 4. Backend担当への管理項目

### 4.1 PR-02・03・05

| PR | PMが見る受入証拠 | 重要な停止条件 |
|---|---|---|
| PR-02 | 有効Managerは自支店のみ、無効Manager・他支店は不可。権限変更後の再ログイン検証 | 支店情報の漏洩、RLS迂回 |
| PR-03 | 配置ボタンが新RPCを使用。時間重複・資格・状態・支店をサーバーで拒否。旧RPCの権限閉鎖 | 旧経路で不正配置可能、既存呼出しの破損 |
| PR-05 | 承認・却下、直接UPDATE閉鎖、34/34 PASS報告の再確認、警告再確認、冪等・回帰 | 警告変更の無確認承認、権限抜け、状態遷移迂回 |

**確認する報告形式:** 対象ブランチ、commit SHA、migration名、実行環境、テストケース数・PASS/FAIL、lint/型検査、既知の制限、ロールバック手順。ローカルcommitはmainへのマージを意味しない。

### 4.2 隔離画面確認（条件付き承認済み）

- `.env.local`にローカルSupabaseの公開キー・URLのみ。秘密鍵や本番キーを含めない。
- StudioのAuth経由で`@example.invalid`の合成アカウントを作成。`auth.users`直接INSERT禁止。
- 合成データを隔離DBへ投入し、確認中のみ保持。`127.0.0.1`に限定して開発サーバー起動。
- PR-02/03/05をまとめた**ローカル専用確認ブランチ**でDB版とUI版を一致させる。push禁止、衝突時停止。
- 画面確認のPASS/FAILとスクリーンショットを回収。未確認は未確認のまま報告。

### 4.3 P0-4・一括応募

P0-4のW1/R1/A2/K1は**11月実装計画**。配置確認を単なるUIダイアログで済ませず、最新状態・権限・競合をRPCで再検証し、receiptに確認者・日時・状態を残す。旧仕様14.2は改訂対象。

一括応募P0-5は、既存単一応募RPCの繰り返しでは代替不可。認可、原子性、receipt、unknown回復、並行実行、既存writerとの共通lockを確認してから実接続を判断する。10/31に無理に接続しない。

## 5. GitHub・PR統合管理

- main保護、CI、レビュー条件を維持し、管理者権限で無断バイパスしない。
- 各PRのbase/head SHA、変更ファイル、migration依存、重複編集、テスト証拠を一覧化する。
- PR-03とPR-05はDBの権限変更とUI Actionの切替を整合させる。片方だけmainに入れる場合の動作不能リスクを確認する。
- Frontend PR-UI-01のfixtureを唯一のデモ用データ正本とし、Backend側に競合するfixtureを維持しない。
- `dispatch-os`、旧`dispatch-os-dev`、既存の未commit差分は保全。`reset --hard`、force push、無断復元・削除をしない。
- **マージは別の明示判断。** ローカル検証成功はpush・PR作成・merge・クラウド反映を許可しない。

## 6. AWS・公開環境：オーナー自身の担当

### 6.1 現状把握と境界

過去の報告ではAWS CLIプロファイル`miku-admin`、東京リージョン`ap-northeast-1`、MFA、月額予算アラート、OpsCue用IAMロール、CloudWatchロググループ等の準備がある。ただし**現在のAWSリソース・請求・IAM権限を本書作成時に再検証していない**。新規作成、権限変更、デプロイ、外部送信は個別承認が必要。

### 6.2 10/31までにすること

1. **公開するかを先に判断する。** UI限定デモならAWS構築は必須でない。発表用にローカル録画・静止画を用意する選択肢を残す。
2. クラウド公開案が必要なら、Vercel・Supabase・AWSの役割、データフロー、認証境界、費用、管理者、停止方法を**設計だけ**整理。
3. 既存IAMやAWSの過去の安全審査・保留事項を、期限を理由に迂回しない。
4. 実利用者・実会社・実案件のデータはデモに使わない。LINEやメールの外部送信はOFFを前提にする。

### 6.3 11月以降の候補工程（別承認）

- 構成・費用・アカウント分離を再レビュー。個人開発環境、隔離試験環境、公開デモ環境を区別。
- 最小権限IAM、Secrets、監査ログ、バックアップ、監視、アラート、障害停止、復旧手順を定義。
- SupabaseのAuth・RLS・migration適用先・シークレット管理を確認。
- Vercel/その他のホスティングとAWSの責務分担を選定。AWSを使うこと自体を目的化しない。
- デプロイ、データ投入、LINE通知の有効化はそれぞれ独立したGo/No-Goを設ける。

- [ ] 一括応募が原子的に全件成功／0件を保証
