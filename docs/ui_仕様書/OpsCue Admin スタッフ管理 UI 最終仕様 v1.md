新規登録ボタンは追加せず、既存の登録・招待フローへ誘導する。既存フローの入口がこの画面に存在しない場合、勝手に新規作成処理を追加しない。

### **基本情報カード**

所属、稼働状態、アカウント連携状態を表示する。

次回勤務カードをクリックするとシフト詳細へ移動できる。直近勤務は勤務履歴の該当箇所、または該当シフト詳細へ移動する。

概要では編集操作を極力置かず、情報の確認を優先する。

### **スキル・資格の編集**

編集権限のあるSystem Adminには、各カード右上に「追加」ボタン、各項目に「…」メニューを表示する。

「追加」「編集」は右ドロワーで行う。

スキルは既存のスキルマスターから選択し、必要な補足情報を設定する。資格は資格マスター、取得日、有効期限など既存スキーマで扱える項目を入力する。

削除は物理削除ではなく、既存の付与履歴・監査要件に沿って取り消し・無効化を検討する。

資格の期限切れは表示するが、自動で稼働状態を停止しない。

## **8\. タブ④ 勤務履歴**

ここは今回の主要な変更点。

現在の横長カード一覧を、PCではテーブルに変更する。スマホではカードを維持する。

### **PC版テーブル**

| 勤務日時 | 案件・業務 | 勤務先 | 配置状態 | 勤怠 | 操作 |
| ----- | ----- | ----- | ----- | ----- | ----- |
| 10/20 09:00–18:00 | 案件A / 受付 | 名古屋会場 | 完了 | 確定 | シフト・勤怠 |
| 10/18 10:00–19:00 | 案件B / 誘導 | 豊田会場 | 完了 | 未確定 | シフト・勤怠 |
| 10/25 09:00–18:00 | 案件C / 案内 | 名古屋会場 | 配置済み | 対象前 | シフト |

### **フィルター**

勤務履歴には次の絞り込みを提供する。

* 日付範囲  
* 案件名・業務名  
* 配置状態  
* 勤怠状態

初期表示は新しい勤務から順に表示し、1ページ20件とする。

勤務が日をまたぐ場合は開始日と終了日を両方表示する。

### **遷移**

「シフト」はシフト運用の詳細ページへ、「勤怠」は勤怠管理の独立詳細ページへ移動する。

勤怠記録が未作成の場合は、存在しない詳細リンクを生成せず「未作成」などの状態を表示する。

スマホでは、日時・案件・状態・操作をカード内にまとめる。

## **10\. 右ドロワー仕様**

右ドロワーの幅はPCで480〜560px、推奨520px。スマホでは全画面表示とする。

| ドロワー | 入力項目 | 操作 |
| ----- | ----- | ----- |
| 基本情報編集 | 編集可能な氏名・所属等 | 保存・キャンセル |
| スキル追加・編集 | スキル選択・補足情報 | 保存・取消 |
| 資格追加・編集 | 資格・取得日・期限 | 保存・取消 |
| 稼働状態変更 | 変更後の状態・理由 | 確認して変更 |

### **共通仕様**

ドロワー上部にはタイトルと対象スタッフ名、下部には固定の「キャンセル」「保存」ボタンを配置する。

未保存の変更がある状態で閉じようとした場合は、破棄確認を表示する。

保存時には入力チェックとサーバー側の権限・最新状態の再検証を行う。

状態変更など影響の大きい操作は、ドロワー内で入力後に確認ダイアログを挟む。

## **11\. スタッフ状態と遷移**

稼働状態は、稼働可・休止・停止をUI上の区分として扱う。

稼働可

通常の稼働対象

休止

一時的に稼働停止

停止

管理上の利用制限

状態遷移の概念図。実際に許可する遷移と再開条件は既存のスタッフ状態管理契約に従う。

状態変更では、既存の配置・応募・勤務予定への影響を確認できるようにする。

状態を休止・停止へ変更しただけで、過去の勤怠・配置履歴を削除してはならない。

また、将来の配置を自動取消する処理も、明示された業務ルールがない限り実行しない。

## **12\. 権限仕様**

現在のスタッフ詳細に表示されているManager閲覧専用の方針を維持する。

| 操作 | Manager | System Admin | Worker |
| ----- | ----- | ----- | ----- |
| スタッフ一覧 | 自支店の許可範囲 | 許可範囲 | 不可 |
| スタッフ詳細 | 自支店の許可範囲 | 許可範囲 | 自分の情報のみ別画面 |
| スキル・資格閲覧 | 可 | 可 | 自分の情報 |
| スキル・資格編集 | 不可 | 専用権限で可 | 不可 |
| 勤務条件閲覧 | 可 | 可 | 自分の情報 |
| 勤務条件編集 | 不可 | 不可 | 自分の情報 |
| 勤務履歴閲覧 | 可 | 可 | 自分の履歴 |
| 基本情報編集 | 不可 | 専用権限で可 | 別途本人用機能 |
| 稼働状態変更 | 不可 | 専用権限で可 | 不可 |

System Adminであっても無条件に全情報を編集できる設計にはしない。

また、Managerのアクセス範囲は支店アクセス権限と整合させ、RLS・RPC側で強制する。

PR-02の権限修正がクラウドDBへ適用済みであるとは扱わない。 UI実装時には、最新のマージ・適用状況を確認する。

## **15\. 実装順序**

Phase 1

既存UI・権限の棚卸し

P0

既存ルート、5タブ、スタッフ情報の取得元、編集権限、登録・招待フローを確認

Phase 2

スタッフ一覧の改善

P0

テーブル列、検索・フィルター、件数カード、次回勤務・直近勤務の導線

Phase 3

スタッフ詳細の整理

P0

共通ヘッダー、概要・スキル・資格・勤務条件・基本情報の表示統一

Phase 4

勤務履歴の再設計

P1

PCテーブル、スマホカード、検索・ページング、勤怠・シフト詳細へのリンク

Phase 5

編集ドロワー

P1

既存の権限で許可された編集機能、入力検証、変更確認、監査履歴

Phase 6

追加の利便性改善

P2

資格期限の視認性、詳細な検索、必要に応じたCSVなど

### **実装時のルール**

Phase 1〜4は、既存の取得機能を利用した読み取り中心のUI改善として進める。

Phase 5の編集機能は、実装済みの安全な更新経路が存在することを確認してから着手する。存在しなければ、UIを先行しても本番操作は有効化しない。

既存のAuth・Staff Domain・RLSを変更する場合は、UI変更とは別に影響分析とレビューを行う。

## **16\. 完了条件**

* スタッフ一覧の検索・状態・所属フィルターが正しく機能する。  
* 閲覧権限外のスタッフが一覧・件数・検索結果に表示されない。  
* 既存の5タブを維持し、タブ間を移動できる。  
* 勤務条件はAdminから編集できない。  
* 勤務履歴がPCではテーブル、スマホではカードで表示される。  
* 勤務履歴からシフト詳細・勤怠詳細へ移動できる。  
* スキル・資格の未登録・有効期限が正しく表示される。  
* 編集ドロワーが権限に応じて表示・操作制御される。  
* 編集内容が監査要件に従って記録される。  
* 既存の登録・招待フローが壊れていない。  
* 読み込み・空状態・権限エラー・保存失敗が適切に表示される。
