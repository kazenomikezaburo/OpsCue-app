# 第1部：Worker統合設計

## 1. プロダクトと共通UX原則

OpsCueのWorker画面は、募集の確認・応募から、勤務確定、準備、前日確認、勤怠、問い合わせ、プロフィール・勤務設定までを一貫して扱う。

1. **本人の次の行動が分かること。** ホームは対応が必要なことを優先し、勤務詳細には「次にやること」を設ける。
2. **業務の正本はOpsCue。** LINEは補助配信であり、既読やLINE受信だけで前日確認・勤怠・申請を完了させない。
3. **申請と正式変更を区別。** 電話番号・スキル・資格などはWorkerの申請後、所定のAdmin確認・承認を経て反映する。
4. **状態を混同しない。** 勤務可否、希望条件、応募、配置、勤務、通知既読、問い合わせ状態はそれぞれ独立して管理する。
5. **本人以外へのアクセスを許可しない。** 表示制御だけでなくサーバー側の認可・RLS・RPCで検証する。
6. **変更履歴を残す。** 業務上重要な作成・更新・承認・取消・送信・失敗を監査する。

## 3. 画面別の責務・最重要ルール

| 画面 | 主な表示・操作 | 確定したルール |
|---|---|---|
| ホーム | 今日やること／次の勤務／応募可能な募集 | Action最大3件、勤務1件、募集2件。勤務中優先。ホームで業務を独自完了扱いしない |
| 募集 | 募集一覧・詳細／応募履歴 | 他画面に記載の募集連携は取り込むが、独立仕様の全文確認は未実施 |
| 勤務 | 予定・履歴／勤務詳細／前日確認／勤怠／取消申請 | 取消申請中も勤務は有効。期限切れ前日確認はサポートへ。結果確定と勤怠確認中を区別 |
| サポート | SOS／通常問い合わせ／返信／再対応依頼 | SOSは有効な勤務が対象。受付はAdmin確認完了ではない。解決済みの再開はAdmin判断 |
| お知らせ | 公開済み対象者向けの運営案内 | 公開時の対象者スナップショット。アーカイブは詳細直リンクも閲覧不可。お知らせ自体の既読はMVPで管理しない |
| 通知 | すべて／未読、通知ベル、すべて既読 | 通知を開くと既読。通知既読と業務完了は別。OpsCue内通知が正本 |
| 基本情報 | 連絡先・所属など／変更申請 | 電話番号は申請してAdmin承認。氏名・所属はWorker直接変更不可。メール変更は認証基盤で本人確認 |
| スキル・資格 | 承認済み情報／追加・更新申請 | スキル・資格の両方でAdmin承認が必要。未承認の申告は応募資格・配置条件の正式情報にしない |
| 勤務可能時間 | 月間カレンダー／時間帯の登録・編集・削除 | 勤務可能・相談可能・勤務不可・UNKNOWN。重複原則禁止。過去と進行中は閲覧のみ。確定済み勤務との矛盾は警告後に保存可能で、自動取消なし |
| 希望条件 | 曜日・時間帯・エリア・業務・交通手段など | 普段の希望を表し、単独では応募不可判定にしない |
| 通知設定 | LINEカテゴリ別ON/OFF | OpsCue内通知は常時ON。LINEは応募結果／勤務確定・変更／前日確認／勤務リマインダー／サポート返信を初期ON、重要なお知らせは初期OFF |
| LINE連携 | 認証・友だち追加・テスト通知・解除 | 友だち追加確認が通知有効化の必須条件。ACTIVE時のみテスト通知可。LINEの既読はOpsCue既読に影響しない |

## 4. 主要な業務横断フロー

### 4.1 募集から勤務まで

```text
募集を確認 → 応募 → 審査／結果通知 → Assignment確定
  → 勤務予定 → 前日確認 → 当日の出発／到着／勤怠
  → 勤務結果の確定 → 勤務履歴
```

応募条件・勤務可能時間・スキル資格の正式判定はサーバー側で行う。ホームに表示した応募可能募集も、応募実行時に再検証する。募集詳細・一括応募などの厳密な契約は独立募集仕様およびBackend契約との照合が必要。

### 4.2 勤務可能時間と配置

- 勤務可能時間は日時区間 `[開始, 終了)`。状態が異なっても重複禁止。隣接区間は許可。
- 日跨ぎは「翌日終了」を明示。日本時間で入力・表示し、保存は曖昧でない日時形式を使用。
- 未登録区間は `UNKNOWN`。代表判定の優先順位は `UNAVAILABLE → UNKNOWN → CONSULT → AVAILABLE`。区間別内訳も保持する。
- 確定済み勤務と矛盾する登録は警告して保存可能。ただし既存のAssignmentは自動取消しない。
- 希望条件は推薦・参考情報であり、単独の応募禁止条件ではない。

### 4.3 サポートと通知

```text
SOS／問い合わせ作成 → Adminヘルプリクエスト
 → 未対応 → 対応中 → 解決済み
                      └→ Worker再対応依頼 → Admin判断
```

SOSの対象は本人の有効な開始前・勤務中Assignment。差し迫った危険への対応はアプリ内返信を待たず直接連絡する。Adminの内部メモはWorkerへ公開しない。

### 4.4 通知とLINE

```text
業務イベント → OpsCue内通知を生成 → LINE送信可否を評価
                                         ├─ 対象外／設定OFF → 送信なし
                                         └─ ACTIVE・カテゴリON → 非同期配信
```

通知既読、LINEメッセージ閲覧、前日確認・打刻などの業務完了は独立。LINE配信失敗で業務トランザクションを取り消さない。

## 6. 権限・監査の共通契約

| 操作分類 | Worker | Admin／サーバー |
|---|---|---|
| 本人の募集・勤務・通知・問い合わせ閲覧 | 認可範囲内で可 | 管理権限に応じて可 |
| 本人の勤務可能時間・希望条件 | 原則本人が登録・変更 | 既存の管理者代理操作契約と照合 |
| 電話番号の正式更新 | 申請のみ | Admin確認・承認後に反映 |
| スキル・資格の正式更新 | 申請のみ | Admin承認後に反映 |
| 問い合わせの作成・返信 | 状態に応じて可 | 対応・解決・再開を管理 |
| LINEの本人紐付け・解除・設定 | 本人のみ | 認証済みサーバー処理 |
| 業務状態の確定 | 許可された操作のみ | サーバーで権限・状態・競合を再検証 |

監査は原則として、actor、対象ID、操作種別、変更前後、理由（必要な場合）、時刻、相関ID、成功／失敗を追跡可能にする。認証トークン、LINEシークレット、医療情報、不要な個人情報はログへ含めない。監査ログと通知配信ログは分離する。

## 7. 共通エラー・状態表示

- **空状態**：対象0件と取得失敗を区別する。
- **読み込み中**：スケルトン等で表示し、完了済みと誤認させない。
- **認証期限切れ**：再認証へ誘導する。
- **権限なし**：他人のIDや古いディープリンクから情報を漏らさない。
- **競合**：保存・承認・応募・配置・取消・既読処理などはサーバー側で再検証し、必要に応じ最新状態を再取得する。
- **期限切れ**：前日確認などの期限後操作は許可せず、適切なサポート導線を示す。
- **送信失敗**：業務上の受付成功とLINE配信結果を混同しない。
- **アクセシビリティ**：色だけで状態を表さず、ラベル・フォーカス・キーボード操作を備える。

## **3\. 今日やること**

本人が対応すべき、未完了のアクションを表示する。

表示対象は、既存のWorker業務仕様でアクションとして定義され、かつ本人が実行可能なものに限定する。

例えば勤務前日確認・当日確認などが該当する。単なる通知や閲覧済みのお知らせは含めない。

表示ルール

* 最大3件。期限超過、当日期限、期限が近い順に表示する。  
* 完了済み、取消済み、現在は操作できないものは表示しない。  
* 各項目には内容・対象勤務・期限・遷移先を表示する。  
* 4件以上ある場合は、残件数と確認先を表示する。  
* 0件の場合は「現在、対応が必要なことはありません」とコンパクトに表示する。

アクションの完了判定はサーバー側の業務状態を正とし、ホーム独自の完了フラグは作らない。

## **4\. 次の勤務**

今回の重要な決定として、進行中の勤務を未来の勤務より優先する。

### **表示優先順位**

1. 勤務中のシフト  
   勤務カードの見出しを「現在の勤務」に変更する。  
2. 本日これから開始するシフト  
   見出しは「次の勤務」。確認待ちなどの状態を表示する。  
3. 翌日以降の最も近いシフト  
   見出しは「次の勤務」。勤務日時の近い順に選ぶ。  
4. 対象シフトなし  
   「今後の勤務予定はありません」と表示する。

勤務中かどうかは、現在時刻だけで断定せず、既存の勤怠状態や勤務状態と整合する判定を使用する。打刻漏れなどで状態が不明な場合は、誤って「勤務中」と表示しない。

勤務カードには、勤務日、時間、案件・業務、勤務先、確認状態を表示する。勤務先情報はシフトに保持されたスナップショットを参照する。

カードを押すと勤務詳細に遷移する。ホームから直接配置変更や勤怠確定は行わない。

## **5\. 募集中の仕事**

本人が実際に応募可能な募集のみを表示する。

公開中であっても、応募締切済み、取消済み、応募済みで再応募できないもの、既存の応募資格条件を満たさないものは対象外とする。

勤務可否が`UNKNOWN`または`要相談`の場合の扱いは、未解決のP0-4と整合させる必要があるため、このUI仕様だけで応募可否を確定しない。

| 項目 | 仕様 |
| ----- | ----- |
| 件数 | 最大2件 |
| 並び順 | 勤務開始日が近い順 |
| 表示 | 日付・業務名・時間・勤務先 |
| 状態 | 応募受付中 |
| 操作 | 募集詳細へ遷移 |
| 一覧 | 「すべて見る」から募集タブへ |
| 0件 | 現在応募できる仕事はありません |

ホームのカードは応募可能性をサーバー側で判定した結果から表示する。カード表示後に締切や定員が変わる可能性があるため、最終的な応募可否は応募実行時に再検証する。

## **6\. 挨拶・名前の表示**

正式表示は「こんにちは、〇〇さん」。

表示名はスタッフプロフィールから取得し、氏名が取得できない場合は「こんにちは」と表示する。

時間帯で挨拶を切り替える機能は初期実装では不要。名前が長い場合は折り返しまたは省略表示し、レイアウトを崩さない。

## **8\. 権限・セキュリティ**

Workerホームは、認証された本人に許可された情報のみ取得する。

本人以外の応募、配置、勤怠、アクションを表示しない。支店や募集条件によるアクセス制御もサーバー側で行う。

UIで項目を隠すだけでは権限制御とみなさず、既存のRLS・RPC・認可ロジックと照合する。

取得エラーとデータ0件を区別し、認証期限切れの場合は既存の再認証フローへ誘導する。

## **9\. 実装順序**

| 段階 | 作業 | 優先度 |
| ----- | ----- | ----- |
| 1 | 既存ホーム・取得API・RLSの棚卸し | P0 |

| 6 | モバイル・PCのレイアウト調整 | P0 |
| 7 | 遷移・アクセシビリティ・E2E検証 | P1 |

## **10\. 完了判定**

次の条件を満たせば、WorkerホームのUI実装を完了と判断できる。

* 本人のアクションだけが最大3件表示される。  
* 勤務中のシフトが未来のシフトより優先される。  
* 勤務先情報はシフトのスナップショットと一致する。  
* 本人が応募可能な仕事だけが最大2件表示される。  
* 各カードから正しい詳細画面へ遷移できる。  
* データ0件、取得エラー、読み込み中が適切に区別される。  
* スマホとPCで操作でき、既存のナビゲーションが維持される。  
* 認可されていないデータが取得・表示されない。

## **9\. 欠勤・無断欠勤・会社取消**

### **欠勤**

欠勤申告と欠勤確定を区別する。

Workerが欠勤を申し出た時点では、Admin側の処理が完了したとはみなさない。

確定後は「欠勤」と表示し、通常の打刻操作を停止する。

### **無断欠勤**

無断欠勤は、管理者による適切な判定が完了した場合のみ表示する。

単に勤務開始時刻を過ぎた、到着報告がない、打刻がないという理由だけで自動確定しない。

記録に相違がある場合は、対象勤務に紐付けたヘルプリクエストから問い合わせできる。

### **会社取消**

会社側で取消が確定した場合は「会社取消」と表示する。

取消日時とWorkerに公開可能な理由を確認できるようにし、通知から該当勤務詳細へ遷移できるようにする。

本人取消・会社取消・欠勤・無断欠勤の履歴は保持し、監査上必要な記録を削除しない。

## **10\. コンパクトタイムライン**

タイムラインは表示専用とし、操作ボタンを設置しない。

表示する主要イベントは、勤務確定、前日確認、出発・到着、勤務開始、勤務終了。

状態は「予定」「完了」「未記録」「対象外」「取消」などで表す。

予定時刻と実績時刻を同じイベント内に表示する場合は、必ずラベルを付ける。

履歴が多い場合は、初期表示を主要イベントに限定し、「すべての記録を見る」で展開する。

## **11\. 権限・認可**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 本人の勤務閲覧 | 可 | 権限範囲内で可 |
| 前日確認回答 | 受付中のみ | 管理権限に従う |
| 出発・到着報告 | 条件を満たす場合 | 閲覧・管理 |
| 勤務開始・終了打刻 | 条件を満たす場合 | 確認・修正 |
| 本人取消申請 | 可 | 審査 |
| 取消承認・却下 | 不可 | 権限保持者のみ |
| 勤怠確定 | 不可 | 権限保持者のみ |
| 他Workerの勤怠閲覧 | 不可 | 権限範囲内で可 |

Workerの認可は本人の有効なAssignmentと対象勤務へのアクセス権を基本とする。

ただし、取消済みや終了済みの履歴閲覧は、Assignmentが無効になっても本人に必要な範囲で許可する。

UIの非表示だけでアクセスを制限せず、RLS・RPCなどサーバー側で認可を実施する。

| イベント | 通知先 | 内容 |
| ----- | ----- | ----- |
| 勤務確定 | Worker | 勤務日時・勤務先 |

通知の既読状態と業務処理の完了状態は別管理とする。通知を開いただけで前日確認や取消申請が処理済みになることはない。

## **13\. 監査・履歴**

監査対象は、前日確認の回答、出発・到着報告、勤務開始・終了打刻、取消申請、取消承認・却下、勤怠修正、欠勤判定、会社取消など。

記録には、対象勤務、対象Worker、操作者、操作種別、操作日時、変更前後の状態、処理結果、必要に応じて理由を含める。

Workerに公開する履歴と、Admin専用の監査ログは区別する。

勤怠時刻を後から修正した場合も、元の打刻記録を消さずに変更履歴を保持する。

## **15\. エラー・競合状態**

| ケース | 処理 |
| ----- | ----- |
| データ取得失敗 | エラー表示・再試行 |

| 権限不足 | 操作拒否・情報非公開 |
| 通信タイムアウト | 結果再取得・安全な再試行 |

通信失敗時に成功したように表示しない。また、同じ操作を再送した結果、二重の打刻・取消申請・通知が発生しないようにする。

## **3\. SOSの対象勤務**

### **3.1 対象条件**

SOSは、Worker本人がアクセスできる勤務のうち、勤務開始前または勤務中で、正式に取り消されていない勤務を対象とする。

| 勤務状態 | SOS送信 |
| ----- | ----- |
| 勤務確定・開始前 | 可能 |
| 当日・開始前 | 可能 |
| 勤務中 | 可能 |
| 勤務終了済み | 不可 |
| 本人取消確定 | 不可 |
| 会社取消確定 | 不可 |
| 欠勤確定 | 不可 |
| 無断欠勤確定 | 不可 |
| 取消申請中・未承認 | 原則可能 |

取消申請中であっても、正式に取消が確定していなければ勤務は有効なため、SOSを利用できる。

一方、勤務終了後の問題や取消済み勤務については、通常問い合わせから連絡できる。

### **3.2 対象勤務の選択**

勤務詳細からSOSを開いた場合は、対象勤務を自動設定する。

サポートトップから開いた場合は、本人の対象勤務を一覧表示し、1件選択する。

勤務カードには以下を表示する。

* 勤務日・開始終了時刻  
* 案件名・業務名  
* 勤務先  
* 勤務状態

対象勤務が0件の場合は、「SOSの対象となる勤務がありません」と表示し、通常問い合わせを案内する。

対象勤務が複数ある場合は、現在勤務中のものを先頭、その後は開始日時の近い順に並べる。

### **3.3 重要な認可条件**

SOS送信時には、選択したAssignmentが本人のものか、対象勤務が許可された状態か、勤務へのアクセス権があるかをサーバー側で再検証する。

URLの勤務IDを書き換えても、他Workerの勤務に紐付けたSOSを送信できないようにする。

## **4\. SOS作成画面**

### **4.1 入力項目**

| 項目 | 必須 | 内容 |
| ----- | ----- | ----- |

| 困っていること | 必須 | 5分類から1つ |
| 状況 | 任意 | 最大500文字 |
| 緊急時の案内 | 表示 | 直接連絡が必要な場合の注意 |
| 送信確認 | 必須 | 送信内容の確認 |

### **4.2 SOS分類**

| 分類 | 説明 |
| ----- | ----- |
| 現場・集合場所 | 入口や集合場所が分からない |
| 配置・業務指示 | 担当場所や作業内容が分からない |
| 時間・移動 | 交通遅延や到着が難しい |
| 体調・安全 | 体調や安全について伝えたい |
| その他 | それ以外の勤務上の問題 |

状況入力は任意とする。

体調・安全の分類では、病名や詳細な医療情報の入力を要求しない。

### **4.3 SOS送信後**

送信成功時は、共通のヘルプリクエストを作成し、問い合わせ詳細へ遷移する。

初期状態は原則「未対応」、初期優先度は「高」。

画面には「SOSを受け付けました」と表示する。

ただし、受付完了は管理者が内容を確認したことを意味しない。

返信時間や対応開始時刻を保証する表示は行わない。

### **4.4 緊急時の注意**

SOSは緊急通報サービスではない。

差し迫った危険がある場合は、アプリ内の返信を待たずに、現場責任者や適切な緊急連絡先へ直接連絡するよう案内する。

連絡先が登録されている場合のみ表示し、存在しない電話番号は補完しない。

## **7\. 問い合わせ詳細**

問い合わせ詳細は通常問い合わせとSOSで共通化する。

### **7.1 表示項目**

| 領域 | 表示内容 |
| ----- | ----- |
| ヘッダー | 件名・SOSラベル・状態 |
| 基本情報 | 問い合わせ番号・作成日時・種別 |
| 対象勤務 | 勤務日・時間・勤務先・関連リンク |
| 対応状況 | 未対応・対応中・解決済み |
| メッセージ | WorkerとAdminの公開メッセージ |
| 操作 | 返信または再対応依頼 |

担当者が未割当の場合は「担当者確認中」と表示する。

Admin内部メモ、内部的な優先度変更理由、他Workerの情報は表示しない。

### **7.2 メッセージ表示**

メッセージは送信日時の古い順に表示する。

Worker送信とAdmin送信を視覚的に区別する。

送信日時、送信者区分、本文を表示する。

送信失敗時には入力内容を保持する。

## **8\. 問い合わせ状態と返信ルール**

### **8.1 状態遷移**

未対応

問い合わせ受付済み

Workerは追加返信可能

対応中

Adminが対応を開始

WorkerとAdminが返信可能

解決済み

通常返信は停止

Workerは再対応依頼を送信可能

Adminによる再オープン

理由を記録して対応中へ戻す

### **8.2 操作権限**

| 状態 | Worker返信 | Worker再対応依頼 | Admin状態変更 |
| ----- | ----- | ----- | ----- |
| 未対応 | 可 | 不要 | 可 |
| 対応中 | 可 | 不要 | 可 |
| 解決済み | 不可 | 可 | 可 |
| 再オープン後 | 可 | 不要 | 可 |

Workerからの返信は、問い合わせ状態を自動変更しない。

未対応の問い合わせに追加返信しても、状態は未対応のまま。

対応中の問い合わせに返信しても、状態は対応中のまま。

担当者の割当だけでも、状態を自動変更しない。

## **9\. 解決済みへの再対応依頼**

### **9.1 操作**

解決済みの問い合わせ詳細では、通常返信欄を非表示にし、「追加で連絡する」ボタンを表示する。

押すと再対応依頼フォームを開く。

### **9.2 入力項目**

| 項目 | 必須 | 内容 |
| ----- | ----- | ----- |
| 対象問い合わせ | 自動 | 変更不可 |
| 再連絡の内容 | 必須 | 追加対応が必要な理由 |
| 送信確認 | 必須 | 内容を確認 |

### **9.3 送信後の状態**

再対応依頼を送信しても、問い合わせ状態は「解決済み」のまま。

ただし、Workerには「再対応依頼を送信済み」と表示する。

Admin側には再対応依頼が届き、確認対象となる。

Adminが再オープンすると、状態を「対応中」に変更し、理由を監査に記録する。

### **9.4 重複防止**

未処理の再対応依頼が存在する場合、同じ問い合わせに対する重複申請を防ぐ。

Workerには「管理者の確認待ち」と表示する。

Adminが対応不要と判断した場合も、依頼の処理結果を記録し、Workerへ通知する。

再対応依頼の状態は、問い合わせ本体の3状態とは別に管理する。

## **10\. SOSと通常問い合わせの優先度**

| 種別 | 初期優先度 | 初期状態 |
| ----- | ----- | ----- |
| 通常問い合わせ | 通常 | 未対応 |
| SOS | 高 | 未対応 |

SOSであっても、送信しただけで「対応中」にはしない。

優先度はAdminが対応順を判断するための情報であり、Workerが自由に変更することはできない。

Adminが優先度を変更する場合は、変更理由や変更履歴を監査に残す。

### **Admin側の表示**

SOSは通常問い合わせと同じ一覧に表示し、SOSラベルと優先度で強調する。

Adminは種別・優先度・状態で絞り込めるようにする。

ただし、高優先度だからといって、対応開始・担当者割当・解決を自動実行しない。

## **11\. 通知仕様**

| イベント | 通知先 | 通知内容 |
| ----- | ----- | ----- |
| 通常問い合わせ作成 | 対応可能なAdmin | 新規問い合わせ |
| SOS作成 | 対応可能なAdmin | 高優先度SOS |
| Worker追加返信 | 担当Adminまたは対応可能なAdmin | 新しいメッセージ |
| Admin公開返信 | Worker | 管理者からの返信 |
| 対応開始 | Worker | 対応中への変更 |
| 解決 | Worker | 解決済みへの変更 |
| Worker再対応依頼 | 対応可能なAdmin | 再対応依頼 |
| Admin再オープン | Worker | 対応再開 |
| 再対応依頼の対応不要判断 | Worker | 依頼の処理結果 |

### **通知の原則**

* 通知と業務状態は別管理。  
* 通知の既読は問い合わせの解決を意味しない。  
* 同一イベントの重複通知を防止する。  
* 通知失敗によって問い合わせ本体を消さない。  
* 通知から対象問い合わせ詳細へ直接遷移する。  
* Admin内部メモの内容をWorker通知へ含めない。

SOSは通常問い合わせより目立つ通知にするが、通知が届いたこととAdminが対応を開始したことは区別する。

## **12\. 権限・セキュリティ**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 通常問い合わせ作成 | 可 | 管理権限に従う |
| SOS作成 | 対象勤務がある場合 | 管理・確認 |
| 本人問い合わせ閲覧 | 可 | 管理範囲内 |
| 他Worker問い合わせ閲覧 | 不可 | 管理範囲内 |
| 未対応・対応中への返信 | 可 | 可 |
| 解決済みへの通常返信 | 不可 | 状態管理に従う |
| 再対応依頼 | 可 | 受付・判断 |
| 再オープン | 不可 | 権限保持者のみ |
| 担当者変更 | 不可 | 権限保持者のみ |
| 優先度変更 | 不可 | 権限保持者のみ |
| 内部メモ閲覧 | 不可 | 権限保持者のみ |

### **セキュリティ要件**

認証・認可はUIだけでなく、RLS・RPCなどサーバー側で実施する。

Workerが閲覧できるのは本人の問い合わせと、その問い合わせに含まれる公開情報のみ。

勤務に紐付いた問い合わせでは、対象Assignmentへのアクセス権も検証する。

Adminの権限は既存の拠点・担当範囲に従う。

問い合わせの公開メッセージと内部メモは、保存・取得・通知の各段階で公開範囲を分離する。

## **13\. 監査・履歴**

監査対象は次の操作とする。

| 操作 | 記録する内容 |
| ----- | ----- |
| 問い合わせ作成 | 種別・対象・操作者・日時 |
| SOS作成 | SOS分類・対象勤務・日時 |
| 返信 | 送信者・日時・対象問い合わせ |
| 担当者割当・変更 | 変更前後・操作者 |
| 優先度変更 | 変更前後・理由 |
| 状態変更 | 変更前後・操作者 |
| 解決 | 解決日時・操作者 |
| 再対応依頼 | 依頼者・日時・内容 |
| 再オープン | 理由・操作者・日時 |
| 再対応不要判断 | 判断者・日時・結果 |

問い合わせのメッセージ履歴と監査ログは区別する。

Workerには公開メッセージと必要な状態変更履歴のみ表示し、内部監査情報は公開しない。

メッセージ本文などの機微情報は、汎用監査ログに無制限に複製しない。

## **9\. 通知の状態管理**

通知の状態は、原則として以下の2つとする。

未読

まだ開いていない

既読

開いた・既読操作済み

### **9.1 既読にするタイミング**

通知カードを選択した時点で、既読処理を実行する。

処理順序は次のとおり。

1. Workerが通知を選択する。  
2. 本人宛ての通知であることを検証する。  
3. 既読状態を保存する。  
4. 関連画面へ遷移する。

既読保存に失敗した場合は、成功したものとして確定表示せず、再試行可能にする。

関連画面が削除・アーカイブ・権限変更などで閲覧できなくても、通知を開いた事実は既読として保持する。

### **9.2 すべて既読**

「すべて既読」を押すと、本人の未読通知を一括で既読にする。

他Workerの通知は更新しない。

すでに既読の通知に対して再実行しても問題がない、冪等な処理とする。

一括処理が失敗した場合は、未読件数をサーバーから再取得する。

### **9.3 未読件数**

通知ベルには未読通知数を表示する。

| 件数 | 表示 |
| ----- | ----- |
| 0 | バッジなし |
| 1〜99 | 実件数 |
| 100以上 | `99+` |

未読件数は通知一覧と共通のデータを参照する。

別々のロジックで集計して件数が食い違うことを防ぐ。

## **10\. 通知イベント一覧**

| 勤務先・集合場所変更 | 対象Worker | 勤務詳細 |

また、応募承認と勤務確定が同じ業務処理で発生した場合は、Workerに同じ内容の通知が2件届かないようにイベント契約を整理する。

### **通知の重要な制約**

通知を開いても、以下の操作は自動実行しない。

* 応募の承認・取消  
* 勤務の前日確認  
* 勤務開始・終了打刻  
* 勤務取消申請  
* SOS・問い合わせの解決  
* Adminによる承認

通知はあくまで入口とする。

## **11\. LINE連携**

LINEはOpsCueの補助通知チャネルとする。

業務イベント発生

OpsCue内通知を作成

アプリ内

本人の通知一覧

LINE

連携・配信条件を確認

### **11.1 LINE送信条件**

LINE配信は、以下をすべて満たす場合に行う。

* WorkerがLINEアカウントを連携済み。  
* 対象通知カテゴリのLINE配信が有効。  
* LINE配信に必要な連携状態が有効。  
* イベントがLINE配信対象。  
* 同一イベントの重複送信でない。

### **11.2 LINEの役割**

LINEには、通知の概要とOpsCueへのリンクを含める。

勤務の確定・変更・取消、前日確認、打刻、問い合わせ返信などの正式な操作はOpsCue内で行う。

LINEでメッセージを読んだだけでは、OpsCue内通知を既読にしない。

LINEからOpsCueの通知を開いた場合は、ログイン後に該当通知を開き、その時点で既読処理を行う。

### **11.3 配信失敗**

LINE配信に失敗しても、OpsCue内通知と業務イベントは保持する。

配信失敗をWorkerの勤務状態変更などに波及させない。

認証トークンやLINEの識別子を画面や通知本文に表示しない。

## **12\. 権限・セキュリティ**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 公開中のお知らせ閲覧 | 公開対象者のみ | 管理権限に従う |
| お知らせ作成 | 不可 | 権限保持者のみ |
| お知らせ編集 | 不可 | 権限保持者のみ |
| お知らせアーカイブ | 不可 | 権限保持者のみ |
| 本人宛て通知閲覧 | 可 | 管理権限に従う |
| 他Worker宛て通知閲覧 | 不可 | 原則不要、特別権限時のみ |
| 通知既読変更 | 本人のみ | 原則不可 |
| 通知イベント生成 | 不可 | 信頼されたサーバー処理 |
| LINE配信設定変更 | 本人のみ | 原則不可 |

### **必須のセキュリティ要件**

1. お知らせの閲覧権限は、公開対象スナップショットと現在の認証状態で判定する。  
2. 通知は宛先Worker IDで制限する。  
3. 既読更新は本人の通知にのみ許可する。  
4. 通知内の参照IDを変更しても、他Workerのデータを取得できない。  
5. 通知から遷移した先でも、独立して権限を再検証する。  
6. Admin内部メモや機密情報を通知本文に含めない。  
7. Workerに許可されていない管理画面のURLを通知リンクに使用しない。

### **2.2 カレンダーのルール**

* 1日に複数の時間帯を登録できる。

* カレンダー上のマーカーは1日全体の可否を保証しない。

### **3.1 日跨ぎ**

例えば、10月24日22:00から10月25日06:00まで働ける場合。

開始日：10/24  
開始時刻：22:00  
終了時刻：06:00  
翌日終了：ON  
勤務可否：勤務可能

実際の登録期間  
10/24 22:00 ───────── 10/25 06:00

翌日終了OFFの場合は、終了時刻が開始時刻より後でなければ保存不可。

翌日終了ONの場合は、翌日の終了日時として解釈する。

終了日時は開始日時より後であることを必須とする。24時間以上の登録を許可するかは既存のAvailability契約に合わせ、初期仕様では1登録の期間を24時間以内に制限する。

### **3.2 過去日時の扱い**

現在時刻を基準として、開始日時が過去の登録は編集・削除不可とする。

登録期間が現在進行中の場合も、履歴整合性のためWorkerからの編集・削除は不可とする。

新規登録では、過去の開始日時を指定できない。

表示上のボタン非表示だけでなく、サーバー側でも制限する。

## **4\. 重複登録の禁止**

同じWorkerの勤務可能時間は、状態に関係なく重複を禁止する。

時間帯は `[開始日時, 終了日時)` の半開区間として扱う。

| 登録A | 登録B | 判定 |
| ----- | ----- | ----- |
| 09:00〜12:00 | 12:00〜18:00 | 許可 |
| 09:00〜15:00 | 13:00〜18:00 | 不可 |
| 22:00〜翌06:00 | 翌05:00〜09:00 | 不可 |
| 09:00〜18:00 | 09:00〜18:00 | 不可 |

重複は日付単位ではなく、実際の開始・終了日時で判定する。

同じ状態の時間帯でも重複登録は禁止する。

編集時は編集中のレコード自身を重複判定から除外する。

重複チェックはサーバー側で実施し、同時登録でも矛盾するレコードが作成されないようにする。

### **エラー表示**

> すでに登録されている時間帯と重複しています。登録内容を確認してください。

重複先の登録を閲覧できる場合は、その日時を表示して修正しやすくする。

# **5\. UNKNOWNと勤務可否判定**

勤務可能時間の判定は4種類に整理する。

| 判定 | 意味 |
| ----- | ----- |
| AVAILABLE | 対象時間帯全体が勤務可能 |
| CONSULT | 相談が必要な時間帯を含む |
| UNAVAILABLE | 勤務不可の時間帯を含む |
| UNKNOWN | 未登録の時間帯を含む |

### **5.1 判定優先順位**

1つの勤務時間帯に複数状態が含まれる場合、次の優先順位で代表判定する。

UNAVAILABLE → UNKNOWN → CONSULT → AVAILABLE

ただし、代表判定だけでは情報が失われるため、判定結果には各状態の該当区間も保持できる契約にする。

例えば、09:00〜18:00の勤務に対して、

| 登録 | 代表判定 |
| ----- | ----- |
| 09:00〜18:00 勤務可能 | AVAILABLE |
| 09:00〜12:00 勤務可能、12:00〜18:00 未登録 | UNKNOWN |
| 09:00〜12:00 勤務可能、12:00〜18:00 相談可能 | CONSULT |
| 09:00〜12:00 勤務可能、12:00〜18:00 勤務不可 | UNAVAILABLE |

### **5.2 勤務時間との照合**

勤務の開始・終了日時を対象区間とする。

集合時間や移動時間をAvailability判定に含める場合は、勤務開始時間との違いを明示し、Admin・Workerで共通の契約を使う。

WorkerのUI側で独自の判定式を作らず、サーバー側の共通判定結果を表示する。

# **6\. 応募・配置判定との関係**

Availabilityの状態と、実際の応募可否・配置可否は別概念とする。

| Availability | 応募・配置の扱い |
| ----- | ----- |
| AVAILABLE | 他条件を満たせば候補 |
| CONSULT | 要相談。自動確定しない |
| UNAVAILABLE | 原則不可 |
| UNKNOWN | 未確認。自動的に可能とは扱わない |

### **6.1 募集画面との整合**

既に確定した募集画面の仕様に従い、公開中の募集は、応募できない場合でも一覧に表示する。

応募できない場合は理由を表示する。

例：

* 勤務不可の時間帯が含まれています。  
* 勤務可能時間が未登録です。  
* 勤務可能時間の確認が必要です。  
* 必要な資格が確認されていません。

ただし、UNKNOWN・CONSULTを必ず応募禁止にするか、応募を受け付けてAdmin確認へ回すかは、既存の応募・配置契約との整合が必要。

本仕様では、UNKNOWN・CONSULTを自動的にAVAILABLEへ格上げしないことを確定し、最終的な応募受付ルールは共通のサーバー判定に委ねる。

これにより、Worker UIだけで応募可否を勝手に決定しない。

### **6.2 希望条件との関係**

希望条件は応募可否を直接制限しない。

例えば、希望曜日が土日でも、平日の募集は閲覧可能であり、希望曜日だけを理由に応募不可としない。

Admin側の配置候補検索では希望条件を絞り込みや参考情報に利用できるが、希望条件とAvailabilityを混同しない。

# **7\. 確定済み勤務との競合**

確定済み勤務と矛盾する勤務可能時間も、警告後に保存可能とする。

例として、10月25日09:00〜18:00に確定済み勤務がある場合、その時間帯を勤務不可として登録することもできる。

ただし、保存前に確認ダイアログを表示する。

## **確定済み勤務があります**

登録する時間帯に、確定済みの勤務が含まれています。

イベント運営スタッフ

10月25日 09:00〜18:00

勤務可能時間を変更しても、確定済みの勤務は取り消されません。勤務できなくなった場合は、勤務詳細から取消申請または管理者への連絡を行ってください。

戻って確認  
理解して保存  
警告ダイアログのイメージ。実際の勤務データや保存処理には接続していません。

### **保存時のルール**

* 競合する確定済み勤務をサーバーで再確認する。  
* 対象勤務の概要を表示する。  
* Workerの明示的な確認後に保存する。  
* 保存してもAssignment状態を変更しない。  
* 勤務取消申請を自動作成しない。  
* 勤務変更が必要な場合は勤務詳細へ案内する。  
* 警告を確認して保存した事実を監査に残す。

警告後に保存できることと、確定済み勤務から離脱できることは別である。

保存失敗時は入力内容を保持する。

別端末やAdminによって同時変更が発生した場合は、競合を検出して最新情報を再取得する。

# **3\. LINE認証・友だち追加フロー**

1. OpsCueで本人認証  
   ログイン済みWorkerのセッションを確認する。  
2. LINE連携を開始  
   サーバー側で一時的な連携要求を作成し、LINE認証へ遷移する。  
3. LINEで認証・同意  
   LINE Loginを利用して本人のLINEアカウントを認証する。  
4. 認証結果を検証  
   コールバックで認証コード、`state`、`nonce`など必要な値を検証する。  
5. LINEアカウントを紐付け  
   検証済みLINEユーザーIDとOpsCue Workerを安全に紐付ける。  
6. 公式アカウントの友だち状態を確認  
   友だち追加済みで、通知送信の前提条件を満たしているか確認する。  
7. LINE通知を有効化  
   認証・紐付け・友だち状態の条件を満たした場合のみ通知利用可能にする。

### **3.1 重要な区別**

次の3つは別々の状態として管理する。

| 状態 | 意味 |
| ----- | ----- |
| 認証成功 | LINEアカウント本人の認証が成功 |
| 紐付け成功 | OpsCue Workerとの対応が確定 |
| 通知利用可能 | 友だち状態などの送信条件を満たす |

LINE認証成功だけで通知利用可能と表示しない。

友だち追加待ちの場合は紐付けを保持できるが、LINE通知は送信しない。

LINE側の友だち状態を確認できない場合も、通知利用可能と推定しない。

なお、友だち追加済みであっても、ネットワーク障害やLINE側の制限により、個々のメッセージの到達まで保証できるわけではない。

# **4\. 連携状態の最終仕様**

| 内部状態 | Worker表示 | LINE送信 |
| ----- | ----- | ----- |
| `UNLINKED` | 未連携 | 不可 |
| `LINKING` | 連携処理中 | 不可 |
| `FRIEND_REQUIRED` | 友だち追加が必要 | 不可 |
| `ACTIVE` | LINE通知を利用できます | 可 |
| `UNAVAILABLE` | LINE通知を受信できません | 不可 |
| `RELINK_REQUIRED` | 再連携が必要 | 不可 |
| `UNLINKING` | 解除処理中 | 不可 |

連携失敗は別途エラー理由として保持する。

一時的な配信エラーが発生しただけで、即座に`UNAVAILABLE`や`RELINK_REQUIRED`へ遷移させない。

### **状態遷移**

UNLINKED  
   │ 連携開始  
   ▼  
LINKING  
   │  
   ├─ 認証失敗 ───────→ UNLINKED  
   │  
   ├─ 認証・紐付け成功  
   ▼  
FRIEND\_REQUIRED  
   │  
   ├─ 友だち追加確認 → ACTIVE  
   └─ 連携解除 ─────→ UNLINKED

ACTIVE  
   ├─ 受信不可を確認 → UNAVAILABLE  
   ├─ 再認証が必要 → RELINK\_REQUIRED  
   └─ 解除 → UNLINKING → UNLINKED

`UNAVAILABLE`から友だち状態などが再確認できれば`ACTIVE`へ戻せる。

`RELINK_REQUIRED`では認証を再実行する。

# **5\. LINE通知設定**

## **5.1 基本方針**

OpsCue内通知は常時有効。

Workerが変更できるのは、LINE通知のカテゴリ別ON/OFFのみ。

### **初期設定**

「重要カテゴリのみON」は次のように具体化する。

| カテゴリ | 初期設定 | 理由 |
| ----- | ----- | ----- |
| 応募結果 | ON | 応募結果の見落とし防止 |
| 勤務確定・変更 | ON | 勤務に直接影響 |
| 前日確認 | ON | 確認期限の見落とし防止 |
| 勤務リマインダー | ON | 勤務忘れ防止 |
| サポート返信 | ON | 現場の問題対応 |
| 重要なお知らせ | OFF | 任意で受信を選択 |

重要なお知らせを初期OFFとするのは、業務連絡を優先し、LINE通知の過剰配信を避けるため。

ただし、OpsCue内のお知らせ・通知は従来どおり利用できる。

### **設定の保存ルール**

* LINE未連携でも設定値は保持できる。  
* LINE通知をOFFにしてもOpsCue内通知は生成する。  
* LINE連携解除後も設定値は保持する。  
* 再連携時は保存済み設定を復元する。  
* 新しい通知カテゴリが追加された場合は、既定値を明示して管理する。  
* 保存失敗時は変更前の状態へ戻すか、再試行を案内する。  
* 同時更新があれば最新設定を再取得する。

重要カテゴリであっても、WorkerがLINE通知をOFFにすることは可能。

# **6\. LINE通知の対象イベント**

LINE通知はOpsCue内通知に紐付けて生成する。

| 業務イベント | LINEカテゴリ |
| ----- | ----- |
| 応募承認・不承認 | 応募結果 |
| 勤務確定・重要変更 | 勤務確定・変更 |
| 勤務取消申請の承認・却下 | 勤務確定・変更 |
| 前日確認依頼 | 前日確認 |
| 勤務開始前リマインダー | 勤務リマインダー |
| サポート返信・重要な状態変更 | サポート返信 |
| お知らせ公開・重要更新 | 重要なお知らせ |

SOSに関係するサポート返信は優先度の高いイベントとして扱うが、LINEの即時到達を保証しない。

SOSの安全確保や緊急対応をLINE通知の到達だけに依存させない。

お知らせの軽微な編集では通知を生成しない。

同じ業務結果から重複した通知が作成されないよう、イベントIDで冪等性を担保する。

# **7\. LINEメッセージの内容**

LINEには必要最小限の情報だけを送信する。

OpsCue

勤務が確定しました

新しい勤務が確定しました。日時や集合場所などの詳細をOpsCueで確認してください。

OpsCueで確認する →

通知メッセージの構成例。実際のLINE画面ではありません。

### **メッセージのルール**

* タイトルは簡潔にする。  
* 個人情報や詳細な相談内容を含めない。  
* Admin内部メモを含めない。  
* 業務操作をLINE上で完了させない。  
* 詳細確認はOpsCueへのリンクを使用する。  
* リンク先では必ず認証・権限を再確認する。

通知に付けるリンクは、通知IDを基点にOpsCueへ遷移する方式を推奨する。

対象業務データへのアクセス権限が失われている場合は、適切な非公開・閲覧不可画面を表示する。

# **8\. LINE既読とOpsCue既読**

既読状態は完全に独立させる。

| 操作 | OpsCue通知の状態 |
| ----- | ----- |
| LINE通知を受信 | 変更なし |
| LINE通知を読む | 変更なし |
| LINE内のリンクを押す | 変更なし |
| OpsCueで通知を開く | 既読 |
| OpsCueで「すべて既読」 | 対象通知を既読 |

LINEのリンクを押しただけでは、OpsCue通知を既読にしない。

ログイン後に通知詳細を開き、通知の所有権確認と既読保存が成功した時点で既読とする。

また、通知が既読になっても、前日確認・打刻・取消申請・問い合わせ返信などの業務操作は完了しない。

# **9\. テスト通知**

## **9.1 利用条件**

連携状態が`ACTIVE`の場合のみ送信可能。

テスト通知はWorker本人がLINE通知を受信できるか確認するための機能。

### **UI**

テスト通知

LINEにテストメッセージを送信して、通知を受け取れるか確認できます。

テスト通知の内容

OpsCueのLINE通知テストです。メッセージが届いていれば、通知を受け取れる状態です。

テスト通知を送信するテスト通知のUI例。ボタンは仕様確認用で、実際のLINE送信は行いません。

### **9.2 送信制限**

乱用や不要な送信コストを防ぐため、次の制限を採用する。

| 項目 | 仕様 |
| ----- | ----- |
| 送信可能状態 | ACTIVEのみ |
| 連続送信 | 60秒以上の間隔 |
| 1日の上限 | 5回 |
| 送信先 | 連携中の本人LINEのみ |
| メッセージ内容 | 固定文 |
| OpsCue内通知 | 作成しない |
| 監査 | 送信要求・結果を記録 |

上限はサーバー側で強制する。

送信APIが成功しても、端末への実際の到達を保証しない。

### **9.3 テスト通知の結果**

| 結果 | Worker表示 |
| ----- | ----- |
| 送信要求受付 | テスト通知を送信しました |
| 一時的な失敗 | 送信できませんでした。時間をおいて再試行してください |
| 友だち状態に問題 | LINE公式アカウントの状態を確認してください |
| 上限超過 | 本日の送信上限に達しました |
| 未連携 | LINE連携が必要です |

UI上の「送信しました」は、送信処理が受け付けられたことを意味し、LINE端末への到達確認ではない。

# **10\. 配信失敗・再試行**

LINE配信はOpsCueの業務処理から分離する。

業務イベント  
    │  
    ▼  
OpsCue内通知作成  
    │  
    ▼  
LINE配信対象？  
    │  
    ├─ NO → 終了  
    ▼ YES  
LINE連携ACTIVE？  
    │  
    ├─ NO → 送信なし  
    ▼ YES  
カテゴリ設定ON？  
    │  
    ├─ NO → 送信なし  
    ▼ YES  
配信ジョブ作成  
    │  
    ▼  
送信直前に状態を再確認  
    │  
    ▼  
Messaging API送信  
    │  
    ├─ 成功 → 結果記録  
    └─ 失敗  
         ├─ 一時的 → 再試行  
         └─ 恒久的 → 停止・状態更新

### **配信ルール**

* 業務イベントとOpsCue内通知の作成を先に確定する。  
* LINE配信は非同期で実行する。  
* LINE送信失敗で勤務確定や問い合わせ返信をロールバックしない。  
* イベントIDと配信先で重複ジョブを防ぐ。  
* 送信直前に連携状態とカテゴリ設定を再確認する。  
* 解除済み・受信不可のアカウントには送信しない。  
* 一時的な失敗のみ、回数制限付きで再試行する。  
* 再試行が重複配信を生まないように設計する。

配信結果は、APIへの送信要求の成功・失敗と、実際の端末到達を区別する。

# **11\. LINE連携解除**

連携解除はWorker本人が実行できる。

解除前に確認ダイアログを表示する。

| 項目 | 解除後 |
| ----- | ----- |
| LINE通知 | 停止 |
| OpsCue内通知 | 継続 |
| 勤務予定・履歴 | 維持 |
| サポート履歴 | 維持 |
| 通知設定 | 保持 |
| LINE紐付け | 無効化 |
| 再連携 | 可能 |

解除処理はサーバー側で実行し、紐付け情報を無効化する。

送信待ちのLINE通知も、送信直前の再検証で停止する。

解除が失敗した場合は、実際の連携状態を再取得し、解除済みと誤表示しない。

# **12\. セキュリティ・権限**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 本人の連携状態閲覧 | 可 | 必要最小限 |
| LINE連携 | 本人のみ | 不可 |
| LINE解除 | 本人のみ | 原則不可 |
| LINE通知設定変更 | 本人のみ | 原則不可 |
| 他WorkerのLINE情報閲覧 | 不可 | 原則不可 |
| LINE通知送信 | 不可 | サーバー処理のみ |
| LINE認証情報取得 | 不可 | 不可 |
| テスト通知 | 本人のみ | 不可 |

### **必須の安全対策**

* OAuthの`state`と連携要求を紐付けて検証する。  
* IDトークンの署名、発行者、対象クライアント、期限、`nonce`を検証する。  
* 利用可能な認証方式に応じてPKCE等を採用する。  
* LINEユーザーIDをクライアント申告値だけで信用しない。  
* 同じLINEアカウントを複数Workerに同時紐付けしない。  
* チャネルシークレット・アクセストークンをブラウザへ公開しない。  
* Webhookを使用する場合は署名を検証する。  
* 認証コードやトークンをログに残さない。  
* 連携・解除・設定変更・テスト通知にレート制限を設ける。  
* 連携解除後に古い認証要求が再利用されないようにする。

LINE連携のアカウント紐付けと通知配信は、信頼されたサーバー処理で実施する。
