# **OpsCue Admin 勤怠管理 UI 最終仕様**

## **1\. 確定した設計方針**

| 項目 | 最終仕様 |
| ----- | ----- |
| 勤怠詳細 | 独立ページ |
| 勤怠確定 | 個別確定＋一括確定 |
| 欠勤操作 | 一覧行の「…」メニュー |
| 勤怠修正 | 右ドロワー |
| 修正申請レビュー | 右ドロワー |
| 欠勤・確定などの重要操作 | 確認ダイアログ |
| 勤怠一覧 | 既存テーブルを改善 |
| スタッフ詳細 | 既存の5タブを維持 |
| 配置・休憩編集 | シフト運用側の専用ワークスペース（既定のB案） |
| デザイン | 白・ライトグレー・青 `#2563EB` |

この仕様はUI・業務フローの確定版。現在のDB・RPC・RLSに対応機能が存在することまでは確認していないため、バックエンド実装は別途照合してから進める。

### **フィルター確定仕様**

* 日付は単日を基本とし、期間指定は「勤怠集計」で提供する。  
* 「前日・今日・翌日」は日付選択のショートカット。  
* 勤務状態、確認状態、確認対象、スタッフ・案件・業務・勤務先の検索を提供。  
* 「表示する」で検索条件を適用する。  
* フィルター適用後はURLにも条件を保持できるようにする。  
* ページ移動や条件変更時は一括選択を解除する。

### **集計カード**

既存の「勤務予定・未確定・確定・訂正済み・欠勤／無断欠勤」を尊重しつつ、要確認件数も見えるようにする。

ただし、訂正済みは確定済みと重なる場合があるため、カードの件数を単純合算しない。欠勤と無断欠勤の包含関係もDB定義に合わせる。

## **4\. 勤怠詳細**

独立ページで、1人 × 1勤務の実績を管理する。

### **ページ内構成**

| 領域 | 表示項目 |
| ----- | ----- |
| ヘッダー | 氏名・勤務日・勤務状態・確定状態 |
| 基本情報 | 案件・業務・勤務先・シフトへのリンク |
| 予定と実績 | 出勤・退勤・休憩・実働の比較 |
| 確認事項 | 打刻漏れ、遅刻疑い、未処理申請 |
| 打刻履歴 | 出勤・退勤・休憩の時刻と記録元 |
| 操作履歴 | 管理者修正、申請承認、確定・解除 |

PCでは上部に予定と実績の比較カードを配置し、その下に確認事項と履歴を表示する。

ページ上部のアクションは「勤怠を修正」「勤怠を確定」。欠勤などはその他メニューに入れる。

### **勤怠修正ドロワー**

幅520pxを基準とする。

入力項目は、出勤日時、退勤日時、休憩開始・終了、修正理由。

変更前と変更後を並べて確認できるようにする。保存前に時間の前後関係、休憩の重複、勤務中かどうかなどを検証する。

確定済みの勤怠は通常修正せず、訂正フローに進む。

## **5\. 修正申請**

「修正申請」は勤怠一覧と分離したタブにする。

| 列 | 内容 |
| ----- | ----- |
| 申請日時 | スタッフが申請した日時 |
| スタッフ | 氏名 |
| 勤務日 | 対象の勤務 |
| 申請内容 | 出勤・退勤・休憩など |
| 変更内容 | 変更前 → 変更後 |
| 状態 | 申請中・承認済み・差し戻し・却下 |
| 操作 | 詳細 |

申請行をクリックすると右ドロワーを開く。

ドロワーでは申請理由・打刻履歴・関連シフトを確認でき、承認、差し戻し、却下を実行できる。

差し戻しと却下では理由を必須にする。承認時はサーバー側で最新状態と権限を再確認する。

## **6\. 勤怠確定の操作**

確定方式は、今回の決定どおり個別確定＋一括確定。

### **個別確定**

勤怠詳細  
  ↓  
「勤怠を確定」  
  ↓  
確定可能条件を検証  
  ↓  
確認ダイアログ  
  ↓  
確定  
  ↓  
履歴記録・画面更新

### **一括確定**

勤怠一覧  
  ↓  
対象をチェック  
  ↓  
「選択を確定」  
  ↓  
確定可能件数・対象外件数を表示  
  ↓  
管理者が確認  
  ↓  
確定可能な勤怠のみ処理  
  ↓  
成功・失敗・スキップを結果表示

一括確定では、対象件数が多い場合でも全件成功を前提にしない。サーバーが返した個別結果を表示し、失敗した勤怠を再確認できるようにする。

### **確定できない条件**

* 退勤記録がない、または勤務が完了していない。  
* 休憩や打刻の時刻が不整合。  
* 未処理の修正申請がある。  
* 重大な確認事項が未解決。  
* 欠勤など、通常の勤務実績として確定できない状態。  
* 既に確定済み。

## **7\. 状態遷移**

勤怠の状態は、勤務状態・確定状態・申請状態を別々に扱う。

勤務状態

勤務前→勤務中→退勤済みが基本。欠勤は管理者の確認による別分岐。無断欠勤は欠勤理由・区分として扱う案。

確定状態

未確定  
確定  
訂正済み  
訂正済みは確定状態そのものではなく、訂正履歴を示す属性として管理することを推奨。訂正後の再確定要否はバックエンド契約で確定する。

修正申請状態

申請中  
承認 / 差し戻し / 却下

状態遷移はUI側だけで成立させず、すべてサーバー側で検証する。

## **8\. 操作権限**

OpsCueにはSystem Admin・Manager・Workerの役割があるため、次の権限モデルを採用する。

| 操作 | System Admin | Manager | Worker |
| ----- | ----- | ----- | ----- |
| 勤怠一覧・詳細の閲覧 | 許可範囲内 | 担当支店内 | 自分の記録 |
| 勤怠修正 | 許可範囲内 | 権限付与時 | 不可 |
| 修正申請 | 審査可能 | 権限付与時 | 自分の申請 |
| 個別確定 | 権限付与時 | 権限付与時 | 不可 |
| 一括確定 | 権限付与時 | 権限付与時 | 不可 |
| 欠勤登録 | 権限付与時 | 権限付与時 | 不可 |
| 確定後の訂正 | 専用権限 | 専用権限 | 不可 |
| CSV出力 | 権限付与時 | 権限付与時 | 不可 |

これは採用する権限設計案であり、既存の実装済み権限を表す表ではない。

Managerの支店アクセスは、PR-02で対応中の `has_branch_access` を含め、最新の権限状態をサーバーで検証する。画面でボタンを隠すだけではアクセス制御にならない。

特に、支店をまたぐ勤怠閲覧・修正・一括確定を許さないことが重要。

## **9\. シフト・スタッフ管理との連携**

| 起点 | 操作 | 遷移先 |
| ----- | ----- | ----- |
| 勤怠一覧 | スタッフ名 | スタッフ詳細 |
| 勤怠一覧 | 詳細 | 勤怠詳細 |
| 勤怠詳細 | シフト | シフト詳細 |
| 勤怠詳細 | スタッフ | スタッフ詳細 |
| スタッフ勤務履歴 | 勤怠 | 勤怠詳細 |
| シフト配置 | 勤怠 | 勤怠詳細 |
| 修正申請 | 対象勤怠 | 勤怠詳細 |

予定休憩と実績休憩は別管理。シフト運用の配置・休憩ワークスペースで予定を変更しても、勤怠の実績を自動で上書きしない。

## **10\. 実装順序**

Phase 1

既存画面の整理

P0

勤怠一覧のフィルター・集計・テーブル改善、スタッフリンクと勤怠詳細リンクの分離

Phase 2

勤怠詳細ページ

P0

予定・実績・確認事項・打刻履歴・操作履歴を表示。まず読み取り専用で接続

Phase 3

安全な操作UI

P1

欠勤確認ダイアログ、勤怠修正ドロワー、権限・状態による操作制御

Phase 4

確定処理

P1

個別確定、一括確定、対象外判定、結果表示、監査履歴

Phase 5

修正申請

P1

申請一覧、レビュードロワー、承認・差し戻し・却下

Phase 6

集計・出力

P2

スタッフ別・案件別・期間別の集計、CSV出力

各Phaseで、既存のDB・RPC・RLS・権限を読み取り調査し、実装済み機能と未実装機能を分ける。既存の状態遷移を無断で変更せず、必要なDB変更は別PRで審査する。

## **11\. 完了条件**

UI実装完了の判定には、以下を使う。

* 勤怠一覧から勤怠詳細へ移動できる。  
* スタッフ詳細・シフト詳細からも同じ勤怠詳細へ移動できる。  
* 予定と実績が明確に区別されている。  
* 未打刻・勤務中・欠勤などの状態が誤表示されない。  
* 勤怠修正に理由が必要で、変更履歴が残る。  
* 個別確定と一括確定が権限・状態を検証する。  
* 欠勤操作は「…」メニューから確認ダイアログを経由する。  
* 支店をまたぐ不正な閲覧・操作が拒否される。  
* エラー・空状態・読み込み中の表示がある。  
* PC・スマホ双方で利用できる。
