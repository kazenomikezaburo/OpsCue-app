# **OpsCue Worker「お知らせ・通知」最終UI/UX仕様書**

## **1\. 最終決定事項**

| 項目 | 確定仕様 |
| ----- | ----- |
| 画面構成 | お知らせ・通知は独立ページ |
| ナビゲーション | Workerの5タブは維持 |
| お知らせ公開対象 | Admin公開時に確定したWorker |
| アーカイブ | Workerのお知らせ一覧から非表示 |
| 公開後の更新 | 重要な変更のみ通知 |
| お知らせ既読 | 初期リリースでは管理しない |
| 通知既読 | 通知を開いた時点 |
| 通知一覧 | すべて・未読の2タブ |
| 通知並び順 | 作成日時の新しい順 |
| 通知ベル | 未読件数を表示 |
| LINE | OpsCue内通知を補完する外部チャネル |
| 業務操作 | 必ずOpsCue内で実行 |

重要な原則：通知を既読にしても、関連する業務の確認・承認・対応は完了しない。

### **3.1 一覧の表示項目**

| 項目 | 表示ルール |
| ----- | ----- |
| 重要度 | 通常・重要 |
| タイトル | 最大120文字 |
| 本文プレビュー | 2行程度、省略表示 |
| 公開日時 | 日本時間で表示 |
| 更新日時 | 公開後に編集された場合 |
| 更新ラベル | 公開後に変更された場合 |
| 操作 | カード全体から詳細へ |
| 並び順 | 公開日時の新しい順 |

公開後の編集によって並び順は変更しない。更新日時は別途表示する。

同じ公開日時の場合は、IDなど安定したキーで順序を固定する。

### **3.2 表示対象**

Workerに表示するのは、以下をすべて満たすお知らせのみ。

1. Adminによって公開済みである。  
2. 現在アーカイブされていない。  
3. Worker本人が公開時の対象者スナップショットに含まれている。  
4. 現在の認証・閲覧権限を満たしている。

公開時の対象者スナップショットは、Admin側の確定仕様に従う。

公開後に登録されたWorkerを、既存のお知らせへ自動追加しない。

### **3.3 アーカイブ**

Adminがお知らせをアーカイブすると、Worker一覧から非表示にする。

既に通知が存在する場合でも、その通知を自動削除しない。ただし、アーカイブ後に通知からお知らせを開こうとした場合は、本文を表示せず、次の案内を表示する。

> このお知らせは現在公開されていません。

一覧へ戻る導線を設ける。

これにより、通知履歴を維持しながら、アーカイブ済み本文の閲覧を防止する。

### **4.3 既読管理**

お知らせ自体の既読・未読は管理しない。

そのため、次の機能は初期リリースで実装しない。

* お知らせの既読バッジ  
* お知らせの閲覧済みチェック  
* Adminによる閲覧率集計  
* お知らせを読んだ日時の保存

ただし、お知らせ公開に伴って作成された通知の既読状態は別途管理する。

## **5\. お知らせの状態**

Admin側の状態とWorker表示の対応を明確にする。

| Admin状態 | Worker一覧 | Worker詳細 |
| ----- | ----- | ----- |
| 下書き | 非表示 | 閲覧不可 |
| 公開中 | 対象者に表示 | 閲覧可能 |
| アーカイブ | 非表示 | 閲覧不可 |

公開中のお知らせを編集した場合、同じお知らせIDの新しいバージョンを表示する。

編集履歴はAdmin側に保持し、Workerには現在公開されている内容を表示する。

Worker向けの過去バージョン切替機能は初期リリースでは実装しない。

## **6\. お知らせ更新通知**

今回の決定により、公開後の更新通知は重要な変更のみ送信する。

### **6.1 通知対象**

| 操作 | 通知 |
| ----- | ----- |
| 新規公開 | 原則送信 |
| 公開後の軽微な誤字修正 | 送信しない |
| 表現の微調整 | 原則送信しない |
| 勤務に影響する重要な変更 | 送信 |
| 必要な対応内容の変更 | 送信 |
| 重要な日時・場所の変更 | 送信 |
| アーカイブ | 原則送信しない |

### **6.2 重要な変更の判定**

自動的な文章差分だけで重要度を決めない。

Adminがお知らせを更新するときに、\*\*「対象Workerへ更新通知を送信する」\*\*という選択肢を設ける。

変更内容に応じてAdminが判断し、重要な変更では送信を選択する。

通知を送る場合は、変更内容の要約を入力させる。

更新通知の宛先は、公開時に確定した対象者スナップショットから決定する。公開後に新規登録されたWorkerへ自動拡大しない。

### **6.3 二重通知防止**

同じお知らせバージョン・同じWorker・同じ通知イベントに対して、重複通知を作成しない。

保存処理の再試行によって通知が複数件作成されないようにする。

## **9\. 通知の状態管理**

通知の状態は、原則として以下の2つとする。

未読

まだ開いていない

既読

開いた・既読操作済み

### **9.1 既読にするタイミング**

通知カードを選択した時点で、既読処理を実行する。

処理順序は次のとおり。

1. Workerが通知を選択する。  
2. 本人宛ての通知であることを検証する。  
3. 既読状態を保存する。  
4. 関連画面へ遷移する。

既読保存に失敗した場合は、成功したものとして確定表示せず、再試行可能にする。

関連画面が削除・アーカイブ・権限変更などで閲覧できなくても、通知を開いた事実は既読として保持する。

### **9.2 すべて既読**

「すべて既読」を押すと、本人の未読通知を一括で既読にする。

他Workerの通知は更新しない。

すでに既読の通知に対して再実行しても問題がない、冪等な処理とする。

一括処理が失敗した場合は、未読件数をサーバーから再取得する。

### **9.3 未読件数**

通知ベルには未読通知数を表示する。

| 件数 | 表示 |
| ----- | ----- |
| 0 | バッジなし |
| 1〜99 | 実件数 |
| 100以上 | `99+` |

未読件数は通知一覧と共通のデータを参照する。

別々のロジックで集計して件数が食い違うことを防ぐ。

また、応募承認と勤務確定が同じ業務処理で発生した場合は、Workerに同じ内容の通知が2件届かないようにイベント契約を整理する。

### **通知の重要な制約**

通知を開いても、以下の操作は自動実行しない。

* 応募の承認・取消  
* 勤務の前日確認  
* 勤務開始・終了打刻  
* 勤務取消申請  
* SOS・問い合わせの解決  
* Adminによる承認

通知はあくまで入口とする。

## **11\. LINE連携**

LINEはOpsCueの補助通知チャネルとする。

業務イベント発生

OpsCue内通知を作成

アプリ内

本人の通知一覧

LINE

連携・配信条件を確認

### **11.1 LINE送信条件**

LINE配信は、以下をすべて満たす場合に行う。

* WorkerがLINEアカウントを連携済み。  
* 対象通知カテゴリのLINE配信が有効。  
* LINE配信に必要な連携状態が有効。  
* イベントがLINE配信対象。  
* 同一イベントの重複送信でない。

### **11.2 LINEの役割**

LINEには、通知の概要とOpsCueへのリンクを含める。

勤務の確定・変更・取消、前日確認、打刻、問い合わせ返信などの正式な操作はOpsCue内で行う。

LINEでメッセージを読んだだけでは、OpsCue内通知を既読にしない。

LINEからOpsCueの通知を開いた場合は、ログイン後に該当通知を開き、その時点で既読処理を行う。

### **11.3 配信失敗**

LINE配信に失敗しても、OpsCue内通知と業務イベントは保持する。

配信失敗をWorkerの勤務状態変更などに波及させない。

認証トークンやLINEの識別子を画面や通知本文に表示しない。

## **12\. 権限・セキュリティ**

| 操作 | Worker | Admin |
| ----- | ----- | ----- |
| 公開中のお知らせ閲覧 | 公開対象者のみ | 管理権限に従う |
| お知らせ作成 | 不可 | 権限保持者のみ |
| お知らせ編集 | 不可 | 権限保持者のみ |
| お知らせアーカイブ | 不可 | 権限保持者のみ |
| 本人宛て通知閲覧 | 可 | 管理権限に従う |
| 他Worker宛て通知閲覧 | 不可 | 原則不要、特別権限時のみ |
| 通知既読変更 | 本人のみ | 原則不可 |
| 通知イベント生成 | 不可 | 信頼されたサーバー処理 |
| LINE配信設定変更 | 本人のみ | 原則不可 |

### **必須のセキュリティ要件**

1. お知らせの閲覧権限は、公開対象スナップショットと現在の認証状態で判定する。  
2. 通知は宛先Worker IDで制限する。  
3. 既読更新は本人の通知にのみ許可する。  
4. 通知内の参照IDを変更しても、他Workerのデータを取得できない。  
5. 通知から遷移した先でも、独立して権限を再検証する。  
6. Admin内部メモや機密情報を通知本文に含めない。  
7. Workerに許可されていない管理画面のURLを通知リンクに使用しない。

### **13.2 通知**

| 操作 | 記録内容 |
| ----- | ----- |
| 通知生成 | 種別・宛先・参照先・日時 |
| 通知既読 | 既読日時 |
| 一括既読 | 対象・処理結果 |

通知の既読日時は通知データの状態として保持する。

すべての既読操作を別の詳細監査ログに重複保存する必要はないが、管理上重要な変更と障害調査に必要な情報は残す。

ログの保持期間は既存のOpsCue監査・Retention方針と統一する。

## **14\. エラー・空状態・競合**

| ケース | UI・処理 |
| ----- | ----- |
| お知らせ0件 | 「現在のお知らせはありません」 |
| 通知0件 | 「通知はありません」 |
| 未読0件 | 「未読の通知はありません」 |
| お知らせがアーカイブ済み | 公開終了の案内 |
| お知らせ閲覧権限なし | 本文を表示しない |
| 通知の参照先が存在しない | 閲覧できない旨を案内 |
| 通知の参照先の権限なし | 情報非公開・安全な戻り先 |
| 既読保存失敗 | 再試行可能 |
| 一括既読失敗 | 最新件数を再取得 |
| 通知生成失敗 | 業務イベントを保持し再試行 |
| LINE送信失敗 | アプリ内通知を維持 |
| 通信切断 | エラー表示・再取得 |
| 二重操作 | 冪等に処理 |

通知生成は、業務データの確定後に信頼されたイベントから実行する。

重要な通知では、イベントの取りこぼしを防ぐため、永続的な送信キューやOutboxなどの信頼できる仕組みを採用する。

## **16\. 実装順序**

Phase 1：既存実装の棚卸し（P0）

お知らせ、公開対象スナップショット、通知、既読、LINE連携のDB・RPC・RLS・画面を確認する。既存の契約を優先し、不必要なテーブルやRPCを増やさない。

Phase 2：お知らせ一覧・詳細（P0）

公開対象判定、一覧表示、詳細表示、アーカイブ非表示、更新表示を実装する。

Phase 3：通知基盤（P0）

通知イベント契約、宛先、参照先、重複防止、既読状態、未読件数を統一する。

Phase 4：通知一覧UI（P0）

すべて・未読タブ、通知カード、通知ベル、既読、一括既読、空状態を実装する。

Phase 5：各機能との連携（P0）

募集・勤務・前日確認・取消申請・サポート・お知らせのイベントと遷移先を接続する。

Phase 6：権限・監査・通知信頼性（P0）

RLS・RPC、公開対象、本人既読、重複イベント、失敗時再試行、監査を検証する。

Phase 7：LINE連携（P1）
