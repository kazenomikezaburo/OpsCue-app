## 1. 設計原則と情報構造

### 1.1 目的
管理者が募集から現場終了まで、案件・業務・シフト・応募・配置・勤怠・問い合わせを一貫して扱えること。ホームは状況把握、要対応は優先順位付け、各業務画面は実行と監査を担う。安全な権限境界を守り、操作結果を誤認させない。

### 1.2 正規の業務構造
```text
取引先マスタ（複数案件から参照可能）
  └─ 案件（1案件の取引先は原則1件）
       └─ 業務（各業務は勤務先マスタ1件を参照）
            └─ シフト（日時・人数・募集・応募・配置・確認）
                 ├─ Assignment（スタッフとシフトの紐付け）
                 ├─ 配置・ポジション・休憩ローテーション
                 ├─ 前日・当日確認
                 └─ 勤怠・打刻・訂正・確定
勤務先マスタ（複数業務から参照可能）→ 業務 → シフトの勤務先情報スナップショット
スタッフ → スキル・資格／勤務条件／勤務履歴
ヘルプリクエスト → スタッフ・関連勤務・管理者担当
お知らせ → 公開時点で確定した対象Worker集合
```
取引先と勤務先は直接の親子関係にしない。「シフト運用」はデータ階層の親ではなく、複数案件のシフトを横断する作業画面。勤務先マスタの更新は既存シフトの確定情報を自動上書きしない。

### 1.3 情報設計の責任境界
| 対象 | 主責務 | 編集場所 |
|---|---|---|
| 取引先 | 発注元・案件との関連 | マスタ一覧＋右ドロワー |
| 案件 | 案件名・取引先・期間・説明・状態 | 案件独立ページ |
| 業務 | 仕事内容・勤務先・業務条件 | 案件詳細の右ドロワー |
| シフト | 日時・募集・必要人数・応募・配置・確認 | シフト独立ページ |
| 配置・休憩回し | ポジション・時間軸・休憩 | 専用ワークスペース |
| 勤怠 | 打刻・修正・確認・確定 | 勤怠詳細＋ドロワー |
| スタッフ | 人員状態・技能・勤務履歴 | スタッフ詳細＋ドロワー |
| 勤務先 | 場所・交通・集合案内 | マスタ一覧＋右ドロワー |
| 連絡 | 双方向問い合わせ／一方向お知らせ | それぞれ独立した業務画面 |

## 2. 共通ナビゲーション

### 2.1 画面骨格
- ヘッダー：画面全幅に固定、高さ **68px**。左にOpsCueロゴ・サイドバー開閉、右に通知ベル・アカウントメニュー。ロゴはサイドバー内に置かない。
- PCサイドバー：展開 **248px**、縮小 **64px**、メニュー高さ **44px**、アイコン **20px**。クリックで開閉し、縮小時のホバーPeekはメイン領域を押し広げないオーバーレイ。
- 画面幅 **1024px未満**ではサイドバーをモバイルドロワーに変更。ホバーに依存せず、キーボード・タッチでも操作可能。
- 通知ベルはイベント通知、要対応は業務上の処理待ち。未読通知数と未処理件数を混同しない。
- 設定は最下部。未実装機能に操作可能なダミーリンクを出さない。

### 2.2 正式な共通ナビゲーション原典
**共通ナビゲーション最終仕様書**にあるグループを基準とする。
```text
メイン：ホーム／要対応
案件・勤務管理：案件／シフト運用／勤怠
人員・取引先：スタッフ／取引先／スキル・資格
連絡・サポート：ヘルプリクエスト／お知らせ
システム：設定
```
**要決定 NAV-01：** 勤務先マスタの独立入口は共通ナビにない。一方、勤務先管理の独立一覧ページは確定済み。統合提案は「取引先画面のマスタ切替タブまたはマスタ内導線から勤務先へ遷移」。サイドバーへの勤務先追加は、共通ナビ原典の変更承認がある場合のみ行う。旧案の「マスタ管理」グループへ無断変更しない。

## 3. 共通デザイン・レスポンシブ・コンポーネント

### 3.1 デザイン
白・ライトグレーを基調とし、主操作と選択状態に **#2563EB**。背景 **#F9FAFB**、カード **#FFFFFF**、境界線 **#E5E7EB**、標準カード角丸 **12px**。緊急・破壊的操作は警告色を使い、色だけで意味を伝えずラベル・アイコンを併用。過剰な影・アニメーションは避ける。

### 3.2 ブレークポイントと余白
| 項目 | スマホ（〜767px） | タブレット（768〜1023px） | PC（1024px〜） |
|---|---|---|---|
| 基本構成 | 1列・カード | 1〜2列 | テーブル・複数列 |
| 左右余白 | 16px | 24px | 32px |
| ナビ | ドロワー | ドロワー | 固定サイドバー |
| KPI | 1〜2列 | 原則2列 | 2〜4列 |
| 編集ドロワー | 全画面 | 幅に応じて調整 | 右480〜560px |
| 操作領域 | 原則44×44px以上 | 同左 | キーボード対応 |

メイン領域の推奨最大幅は **1440px**。シフトの配置・休憩回しや大型テーブルは例外的に幅制限を外せる。ページ全体の不要な横スクロールを避ける。

### 3.3 共通コンポーネント
- `PageHeader`：タイトル、説明、必要時のパンくず、右側主要アクション。
- `SummaryCard / KPICard`：対象期間・集計条件を明示。数値は権限範囲内で計算。
- `StatusBadge`：状態と重要度を別概念として表示。
- `DataTable`：検索・フィルター・ソート・ページネーション・行アクション。スマホではカード化。
- `FilterBar`：適用・リセット・URL条件復元を画面ごとに定義。
- `Drawer`：編集、関連情報、変更履歴。下部固定アクション、未保存離脱警告。
- `ConfirmDialog`：公開・確定・無効化・欠勤・アーカイブ等の重大操作。
- `Toast/InlineAlert`：成功、失敗、競合、部分成功を明確に区別。
- `Skeleton/Empty/Error/Forbidden`：読み込み・0件・障害・権限不足を混同しない。

**統合ルール UI-01：** ページ内のKPIとフィルターの前後は画面別仕様を優先。ホームと一覧で必ず同順に統一する必要はない。共通コンポーネントの見た目・操作体系は統一する。

## 5. ホーム・要対応

### 5.1 ホーム
**目的：** 今日の稼働状況と管理者の直近の判断事項を素早く把握する。

表示順：①ページヘッダー ②「対応が必要」（最大5件、優先度順）③「今日のサマリー」④「今日の現場」。対応事項のカードから対象業務へ遷移し、ホーム上で状態を直接更新しない。現場の表示は権限内の本日対象シフトに限定し、勤務日・案件・業務・勤務先・時間・配置・不足・状況などを示す。日付・タイムゾーンの業務基準を明示する。

### 5.2 要対応
**目的：** 未対応・期限超過・不足・要確認など、管理者の処理が必要な項目を横断集約する。種類、件名、対象勤務、緊急度、発生日時、詳細遷移を表示。既存の業務状態を読み取って分類し、要対応画面だけの独立した真実の状態を作らない。権限外項目・件数は表示しない。解決操作は原則として元の業務画面で実行する。

## 6. 案件管理・業務管理

### 6.1 案件一覧
KPI：全案件・進行中・下書き。検索、状態・取引先・期間などの絞り込み。PC列：案件名＋コード／取引先／期間／業務数／シフト数／状態／操作。スマホカード。案件名から詳細へ。

### 6.2 案件詳細
独立ページ。ヘッダーに案件名・状態・取引先・編集。概要KPIの下に **概要／業務／シフト／履歴** の4タブ。業務タブから右ドロワーで追加・編集し、シフトタブからシフト詳細へ遷移。

### 6.3 案件作成・編集
基本情報：案件名（必須）、取引先（必須）、案件コード（自動）、開始・終了日、説明、状態。**業務0件でも下書き保存可**。進行中への遷移などは既存業務ルールに従って必要な業務・期間を検証。取引先は有効マスタから選択。業務は案件に紐づき、勤務先は有効マスタから選択または新規登録。

### 6.4 業務追加・編集
右ドロワー480〜560px。業務名・種別・勤務先・説明／業務条件を扱い、参照済み業務の削除・勤務先変更は関連シフトや応募への影響を確認。参照を持つ業務を安易に物理削除しない。案件内で作成した勤務先はマスタ登録後に業務フォームへ戻して選択状態を復元する（接続方式は実装時確認）。

## 7. シフト運用・配置・確認

### 7.1 シフト一覧
全案件を横断し、**一覧／週／月**を切替。KPI：対象シフト・募集不足・配置未完了・要確認。PC列：勤務日、案件・業務、勤務先、勤務時間、必要人数、応募、配置、人数不足、状態、操作。月表示は1日最大3件＋残件数。不足人数の基本式は `max(必要人数 - 有効配置人数, 0)`。時間帯別の充足は別途評価。

### 7.2 シフト作成
独立ページ。案件→業務を選択し勤務先を読み取り表示。単日・複数日・期間／曜日指定、開始・終了、休憩、必要人数、応募締切、募集状態、備考。重複日付・案件期間外・時刻矛盾を確認プレビューで検証してから確定。二重送信防止。

### 7.3 シフト詳細・編集
詳細は **概要／応募／配置／確認** タブ。編集は独立ページで1シフトずつ。日時・人数・募集条件の変更時は応募・配置・確認回答・通知への影響を事前に示す。シフトの勤務先は業務から継承するが、Worker向けの確定案内はシフトスナップショットを正とする。

### 7.4 配置・休憩回し（B案）
**専用の全幅ワークスペース**を採用。時間軸の15分／30分刻み、スタッフ行、ポジション配置、休憩ブロック、ドラッグ・リサイズ、競合・充足表示、右ドロワー編集。シフト詳細の配置タブは概要とワークスペースへの入口。スタッフとシフトのAssignmentと、シフト内のポジション・休憩を混同しない。

### 7.5 前日・当日確認
シフト運用内の横断タブから回答状況を一覧確認。確認状態と勤怠実績は別概念。Worker回答やAdminの対応は既存権限・監査契約に従う。

## 8. 勤怠管理

### 8.1 一覧
単日を基本に前日／今日／翌日ショートカット、勤務状態・確認状態・確認対象・スタッフ／案件／業務／勤務先検索。適用ボタンとURL条件復元。KPI：勤務予定・未確定・確定・訂正済み・欠勤／無断欠勤・要確認。**訂正済みと確定などは重複し得るため、KPIを単純合算しない。**

### 8.2 勤怠詳細
独立ページで「1人×1勤務」の実績を表示。予定／実績、打刻、休憩、実働、確認事項、打刻履歴、操作履歴。上部に「勤怠を修正」「勤怠を確定」、欠勤操作は一覧行・詳細の「…」メニュー。IDは既存DBの勤怠識別子と照合。

### 8.3 修正・申請・確定
修正ドロワーは約520px、出退勤・休憩・理由、変更前後比較。修正申請は専用一覧からレビュー用ドロワーへ。**個別確定と一括確定**を提供し、未処理申請・時刻矛盾等がある場合は確定を制限。複数件処理は対象件数・失敗件数・再試行可能な結果を表示。欠勤・確定・解除は確認と監査を必須にする。

### 8.4 勤怠集計
期間別・スタッフ別・案件別の実績とCSV。集計基準・タイムゾーン・権限スコープを明示する。CSVも同じ権限制御を適用。

## 9. スタッフ管理

### 9.1 一覧
既存登録・招待フローを維持。KPI：登録スタッフ／稼働可／休止・停止。検索：氏名・スタッフID、所属・状態フィルター。PC列：氏名＋ID、支店、状態、次回勤務、直近勤務、詳細。サーバーページング25件初期、25／50／100切替。取消済み配置は次回勤務に含めない。

### 9.2 詳細
独立ページ。共通ヘッダーと5タブ：**概要／スキル・資格／勤務条件／勤務履歴／基本情報**。タブはURLクエリで復元。
- 概要：次回勤務・直近勤務・勤務回数・欠勤等。
- スキル・資格：スキルと資格・期限を区別。Manager閲覧のみ、明示権限を持つSystem Adminが編集。
- 勤務条件：Worker本人が編集、Adminは閲覧のみ。「不明」を「勤務可能」とみなさない。
- 勤務履歴：PCテーブル・スマホカード、シフト／勤怠詳細へリンク。
- 基本情報：ID・氏名・所属・状態・登録・Auth/Profile連携状況。未確認の連絡先を捏造しない。

### 9.3 編集
右ドロワー480〜560px。権限に応じて編集項目を限定。稼働状態など重要変更は確認・監査。支店権限と個人情報の最小表示を徹底する。

## 10. ヘルプリクエスト管理

### 10.1 一覧
KPI：未対応・対応中・本日解決。初期状態フィルターは未解決。検索、カテゴリ・優先度・担当者・受付日時。PC列：受付日時／優先度／件名・冒頭／スタッフ／関連勤務／状態／担当者／最終更新／詳細。緊急かつ未対応を優先。

### 10.2 詳細・やり取り
独立ページ。左側に問い合わせとWorker/Adminの時系列メッセージ、右側約320pxに担当・状態・優先度・スタッフ・関連勤務。**双方向返信**と**管理者専用内部メモ**はUI・データ・取得APIを分離。返信失敗時は入力を保持し、二重送信を防止。

### 10.3 状態・担当
状態：**未対応 → 対応中 → 解決済み**、再オープンは解決済み→対応中。担当は管理者が手動指定。担当指定だけで状態を自動変更しない。対応開始・解決の条件、再オープン理由、優先度（通常／緊急）変更を監査する。解決済みの返信は再オープン後に許可。

### 10.4 通知
新規受付、緊急、担当変更、Admin返信、Worker返信、解決、再オープン。通知は権限確認付きで対象詳細へ遷移。内部メモをWorkerへ絶対に送信しない。

## 11. お知らせ管理

### 11.1 一覧・作成
一覧タブ：**すべて／下書き／公開中／アーカイブ**。PCテーブル・スマホカード。タイトル、本文概要、重要度、状態、支店、対象人数、作成者、公開・更新日時。

新規作成・編集は独立ページ。タイトル最大120文字、本文最大5,000文字、重要度通常／重要、公開対象支店、Worker向けプレビュー。下書きは空欄保存可。初期実装では下書き保存→詳細ページ→公開確認の二段階方式。

### 11.2 公開・対象固定
**公開時点の対象Workerをサーバー側で確定し、対象者IDの集合を固定する。** 公開確認で支店・対象人数・重要度を表示。対象0人は原則公開停止。公開後の支店・対象者変更は不可。新規登録Workerへ過去のお知らせを自動公開しない。アカウント停止等のアクセス制御は引き続き優先。

### 11.3 公開後編集・履歴
公開中でもタイトル・本文・重要度を編集可能。変更前後、変更者、時刻、バージョンを保存。対象者スナップショットは変えない。Workerには最新版と更新日時を表示。状態：**下書き→公開中→アーカイブ**。アーカイブからの再公開は初期実装対象外。公開中の物理削除は禁止。

### 11.4 通知・既読
初回公開と実質的な公開後編集で対象Workerへ通知。冪等性・再試行を確保。**既読人数・既読率・個別閲覧履歴は初期実装に含めない。**

## 12. 取引先・勤務先マスタ

### 12.1 共通
一覧は独立ページ、追加・編集・関連情報・履歴は右ドロワー。**独立詳細ページは作らない。** 状態は有効／無効。物理削除は原則しない。無効化前に影響件数と既存参照を警告し、権限のある管理者が確認後に無効化可能。無効化しても既存案件・業務・シフト・勤怠を消さない。新規参照候補から除外し、再有効化を許可。

### 12.2 取引先
一覧：取引先名・メモ・状態・関連案件数・更新日時・操作。登録：取引先名必須、メモ任意、支店・状態は既存フォーム／DB契約と照合。名称重複は警告するが、名称一致だけで同一法人と断定しない。関連案件は案件一覧の取引先フィルターへ遷移。

### 12.3 勤務先
一覧：勤務先名・住所・状態・関連業務数・未来シフト数・更新日時・操作。登録：勤務先名、住所、交通案内、アクセス補足、集合案内、状態。**要決定 MASTER-01：既存の勤務先画面にある支店・郵便番号を最終マスタ仕様の入力項目へどう復元するか。** 既存DBとの照合まで削除扱いにしない。支店は作成後に変更できない設計が元画面に存在するため、変更可否を調査して確定する。

### 12.4 スナップショット
シフト作成時に勤務先名・住所・交通・アクセス・集合案内・参照元バージョン等の確定値を保存。**マスタ編集だけで既存シフトを更新しない。** 未来シフトへは影響確認→対象選択→差分確認→反映確定。配置済みWorkerへの案内変更は通知。勤務開始済み・完了済み・取消済みは通常反映不可。過去記録の訂正は別の監査付き手順。

**要決定 SNAP-01：** 業務の勤務先変更、シフト複製、日時変更、取消復旧、複数日一括作成の際に、スナップショットを再作成する条件と手動上書きの優先順位。実装前に明文化する。

### 12.5 監査
マスタの作成・編集・無効化・再有効化は変更前後・操作者・時刻を記録。シフトへのスナップショット反映は、マスタ変更履歴と別にシフト側の変更履歴を記録。関連件数は権限外のデータを漏らさず、全影響を確認できない場合は高権限者による実行を要求する。

## 13. スキル・資格マスタ・設定

### 13.1 スキル・資格マスタ
**未確定。** ナビゲーション項目とスタッフ詳細での閲覧・編集方針は存在するが、マスタの一覧・登録・分類・有効期限・廃止・スタッフ付与・資格証明の取扱いについて独立した最終仕様がない。既存DB・権限・スタッフ詳細と整合するまで、新しい更新機能を勝手に確定しない。

### 13.2 設定
**未確定。** サイドバー最下部に入口を設ける方針はあるが、機能の内訳は未決定。未実装の設定を操作可能に見せない。

## 14. 権限・状態・監査・通知の横断規則

### 14.1 権限
- Manager：管理対象支店・業務・スタッフに限定。支店外の行・KPI・検索候補・集計値・エクスポートを漏らさない。
- System Admin：ロール名だけで無条件の全権限を仮定しない。明示的な権限・スコープを優先。
- Worker：自身の勤務・条件・対象通知・問い合わせ等、Worker側で許可された範囲のみ。
- UIのボタン非表示は補助策。実際の認可はサーバー/RPC/RLSで強制。安全な既存更新経路がなければ操作を有効化しない。

### 14.2 重要な状態
| 対象 | 主な状態・遷移 |
|---|---|
| 案件 | 下書き／進行中／終了（詳細条件は案件・Backend契約） |
| シフト | 募集中／締切／終了等（既存定義を優先） |
| 勤怠 | 勤務状態と確定状態を分離。訂正済みは別属性になり得る |
| スタッフ | 稼働可／休止／停止 |
| 問い合わせ | 未対応→対応中→解決済み、再オープン可 |
| お知らせ | 下書き→公開中→アーカイブ |
| 取引先・勤務先 | 有効⇄無効 |

### 14.3 監査・競合・通知
- 重大操作：操作者、対象ID、日時、変更前後、必要な理由、結果を記録。時刻はサーバー基準。
- 保存・公開・確定・配置更新・無効化は二重送信と同時編集を検出する。成功応答前に成功したように見せない。
- 通知は元データの保存結果と分けて再試行できるようにする。通知失敗を「元の処理も失敗」と誤表示しない。
- 通知からのディープリンクも再度認可する。非公開メモ・権限外の個人情報を通知本文に含めない。

## 15. エラー・空状態・アクセシビリティ

全画面で **Loading / Empty / Filtered-empty / Error / Forbidden / Conflict / Partial-success** を区別。取得エラーを0件として扱わない。保存失敗時は入力値・編集中の差分を保持。危険操作は対象・影響・結果を明示する。スマホの全画面ドロワーでキーボードに保存操作を隠さない。フォーカス表示、Escで閉じる場合の未保存確認、スクリーンリーダーのラベル、44pxタッチ領域、テキストと色の併用を守る。
