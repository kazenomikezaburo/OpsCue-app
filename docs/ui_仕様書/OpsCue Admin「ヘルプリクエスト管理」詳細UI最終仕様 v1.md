# **OpsCue Admin「ヘルプリクエスト管理」詳細UI最終仕様 v1.0**

## **1\. 確定事項**

| 項目 | 正式仕様 |
| ----- | ----- |
| 一覧画面 | 既存UIを改善して維持 |
| 詳細画面 | 独立ページ |
| スタッフとの連絡 | 詳細内のスレッド形式 |
| 担当管理者 | 手動割り当て |
| 状態 | 未対応・対応中・解決済み |
| 優先度 | 通常・緊急 |
| 内部メモ | 管理者のみ閲覧可能 |
| スタッフ・シフト連携 | 関連画面へのリンク |
| 通知 | 新規・返信・担当変更・解決・再オープン |
| 操作履歴 | 状態変更・担当変更などを記録 |

ここでいう「確定」はプロダクトのUI・業務仕様を指す。実装済みのDB・RPC・RLS・通知基盤との適合性は、実装前に確認する。

## **5\. 画面操作**

| 操作 | UI | 結果 |
| ----- | ----- | ----- |
| 詳細を見る | 一覧行クリック | 詳細ページへ |
| 担当者を設定 | 右パネルの選択欄 | 担当変更・履歴記録 |
| 対応開始 | ヘッダーのボタン | 対応中へ |
| スタッフに返信 | 返信欄 | メッセージ送信 |
| 内部メモを追加 | 内部メモ欄 | 管理者用履歴に保存 |
| 優先度変更 | 右パネル | 通常・緊急の切替 |
| 解決する | ヘッダーのボタン | 解決済みへ |
| 再オープン | 解決済み画面のボタン | 対応中へ |
| スタッフを見る | スタッフ名リンク | スタッフ詳細へ |
| シフトを見る | 関連シフトリンク | シフト詳細へ |

担当者変更と優先度変更は保存が成功したときだけ表示に反映する。失敗した場合は元の値を維持し、再試行可能なエラーを表示する。

### **返信時のルール**

* 空白のみの返信は送信不可。  
* 送信中は二重送信を防止する。  
* 送信失敗時は入力内容を保持する。  
* 返信の時刻はサーバーで記録する。  
* スタッフへ公開した返信を、管理者が無断で書き換えない。  
* 解決済みでは通常の返信入力を停止し、再オープン後に返信可能とする。

リアルタイム更新は望ましいが、初期実装では再取得でも成立するように設計する。

再オープンすると「対応中」に戻る。履歴は保持。

### **状態変更の条件**

| 現在 | 操作 | 次の状態 | 条件 |
| ----- | ----- | ----- | ----- |
| 未対応 | 担当者を設定 | 未対応 | 担当だけ先に設定可能 |
| 未対応 | 対応開始 | 対応中 | 担当者が設定済み |
| 対応中 | 担当変更 | 対応中 | 変更履歴を記録 |
| 対応中 | 解決 | 解決済み | 解決確認ダイアログ |
| 解決済み | 再オープン | 対応中 | 再開理由を記録 |

優先度は状態と独立させる。緊急だからといって自動的に対応中にはしない。

解決操作では、必要に応じて解決メモを入力できるようにする。再オープン時は理由を必須にする。

担当者未割当のまま対応開始・解決する操作は許可しない方針とする。

## **7\. 担当管理者の割り当て**

手動割り当てを正式採用する。

### **担当者選択の仕様**

右パネルの「担当管理者」をクリックすると、アクセス可能な管理者の候補を表示する。

候補には氏名と所属支店を表示する。対象問い合わせへのアクセス権がない管理者は候補に含めない。

担当変更時は次の情報を記録する。

* 変更前の担当者  
* 変更後の担当者  
* 操作者  
* 変更日時

担当者が退職・無効化された場合でも、過去の担当履歴は保持する。

担当者の変更だけで問い合わせの状態を自動変更しない。

## **8\. 操作権限**

既存のManagerとSystem Adminを基本に、次の権限方針とする。

| 操作 | Manager | System Admin | Worker |
| ----- | ----- | ----- | ----- |
| 問い合わせ一覧 | 許可範囲 | 許可範囲 | 自分の問い合わせ |
| 問い合わせ詳細 | 許可範囲 | 許可範囲 | 自分の問い合わせ |
| スタッフへ返信 | 対応権限がある場合 | 対応権限がある場合 | 自分の問い合わせに返信 |
| 担当者変更 | 許可範囲 | 許可範囲 | 不可 |
| 優先度変更 | 許可範囲 | 許可範囲 | 不可 |
| 内部メモ | 許可範囲 | 許可範囲 | 不可 |
| 解決・再オープン | 対応権限がある場合 | 対応権限がある場合 | 再開依頼は別途検討 |
| 操作履歴 | 許可範囲 | 許可範囲 | 公開可能な情報のみ |

担当者でない管理者でも、権限があれば閲覧可能とする。ただし返信・解決は原則として担当者に限定し、System Adminなどの例外操作は専用権限で制御する。

UIでボタンを非表示にするだけでなく、DB・RPC・RLS側でアクセスと更新を制御する。

## **9\. 通知仕様**

通知はOpsCue内のお知らせとは別に、既存の通知機能を通して配信する。

| イベント | 通知先 | 内容 |
| ----- | ----- | ----- |
| 新規問い合わせ | 対象支店の対応可能管理者 | 新しい問い合わせ |
| 緊急問い合わせ | 対応可能管理者 | 緊急対応が必要 |
| 担当者設定 | 新担当者 | 担当に設定された |
| 担当者変更 | 新担当者 | 担当が変更された |
| 管理者の返信 | 問い合わせ元Worker | 返信が届いた |
| Workerの返信 | 担当管理者 | 新しい返信が届いた |
| 解決 | 問い合わせ元Worker | 問い合わせが解決された |
| 再オープン | 担当管理者 | 問い合わせが再開された |

### **通知のルール**

通知から該当ヘルプリクエスト詳細へ遷移できるようにする。

管理者用とWorker用では遷移先を分け、双方が自分に許可された画面だけを開けるようにする。

通知送信に失敗しても、問い合わせ本体や返信の保存結果を誤って成功扱い・失敗扱いしない。通知は再試行可能な処理として設計する。

緊急通知についても、外部SMS・メール・プッシュ通知を初期段階から必須とはしない。まずは既存のアプリ内通知と連携する。

## **10\. エラー・空状態**

| 状況 | UI |
| ----- | ----- |
| 問い合わせ0件 | 「ヘルプリクエストがありません」 |
| 絞り込み結果0件 | 「条件に一致する問い合わせがありません」 |
| 担当者未設定 | 「未割当」 |
| 返信履歴なし | 初回問い合わせ本文を表示 |
| 詳細取得失敗 | 再試行ボタン |
| 権限なし | アクセス不可 |
| 返信送信失敗 | 入力内容を保持 |
| 担当変更失敗 | 元の担当者を表示 |
| 同時更新 | 最新情報の再取得を促す |
| 解決済み | 返信入力を停止し再オープン操作を表示 |

取得失敗を空データとして扱わない。

## **12\. 実装順序**

Phase 1

既存機能の調査

P0

DB・RPC・RLS・通知・Worker画面・状態定義を確認。未実装の機能を特定。

Phase 2

一覧画面の改善

P0

既存の集計・検索を維持し、担当者・優先度・最終活動日時を追加。

Phase 3

詳細ページ

P0

問い合わせ本文、関連勤務、対応情報、履歴、状態表示を実装。

Phase 4

担当者・状態変更

P0

手動割り当て、対応開始、解決、再オープン、操作履歴。

Phase 5

双方向メッセージ

P1

AdminとWorkerの返信、送信失敗・二重送信対策、内部メモの分離。

Phase 6

通知連携

P1

新規受付、返信、担当変更、解決、再オープン通知と遷移。

Phase 7

結合テスト・仕上げ

P1

権限、支店分離、同時更新、スマホ表示、エラー・空状態の確認。

新しいメッセージ・担当者変更・内部メモなどに必要な安全な更新経路が存在しない場合は、UIから直接テーブル更新する迂回実装はしない。

既存のPRやDB変更とは切り離して、必要なバックエンド変更を別途レビューする。

## **13\. 完了条件**

* 既存の一覧・検索・集計が維持されている。  
* 問い合わせ詳細を独立ページで開ける。  
* 担当者を手動で割り当てられる。  
* 状態遷移が定義どおりに制御される。  
* AdminとWorkerが同じ問い合わせでやり取りできる。  
* 内部メモがWorkerに漏れない。  
* スタッフ・案件・シフト詳細へ移動できる。  
* 通知から該当問い合わせを開ける。  
* 支店・担当・ロールによる権限がサーバー側で保証される。  
* 操作履歴が残る。  
* 送信失敗・同時更新・再オープンを適切に処理できる。  
* PCとスマホの両方で操作できる。
